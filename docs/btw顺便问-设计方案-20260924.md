# /btw(顺便问一句)设计方案(定稿;2026-09-24)

**目标**:和 Claude Code 的 `/btw` 一样 —— agent 正在干活时,用户顺手问一句,**不打断它、不进对话历史**,答案单独显示,看完就关;需要的话一键把这个问题**转成后台子 agent**,带着整段对话和全部工具接着查。

**原则**:能照 CC 做的一律照做(机制、提示词原话、答案的取法、fork 的继承规则);只在 yoma 的架构或安全约束逼出来的地方偏离,每一处列在 §6,附理由。**发动机(`packages/{agent,ai}`,哈希锁定)一个字不改**,改动全在宿主(`packages/kernel/src/host`)和界面(`packages/app`)。

**参照物**:CC 2.1.88 还原源码 `D:/MyCode/claude-code-sourcemap/restored-src/src/`(下文写作 `CC:<路径>:<行>`);官方文档 interactive-mode 页「Side questions with /btw」、sub-agents 页「Fork the current conversation」(v2.1.206 起的 fork 规则)。

**基线**:分支 `btw`,worktree `D:/MyCode/yoma/yoma-pi-btw`,从 origin/develop `c22d6dd`(v0.3.3)开出。上游路径相对 `packages/agent/src/`,kernel 路径相对 `packages/kernel/src/`,app 路径相对 `packages/app/src/`。发动机两个包与 `host/tasks.ts`、`host/domain/agents/`、`build-request-parts.ts`、`server-session.ts` 从草稿依据的 `7beaf91` 到 `c22d6dd` 逐字未变。

## 0. 用户定的(2026-09-24)

1. **思考档位跟会话走**(照 CC:档位是缓存键的一部分)。
2. **边生成边显示**。
3. **能带附件**:图片、行内评论,跟普通消息同一套。
4. **后续 /btw 看不到之前的 /btw 问答**;`/btw` 关键字**不另做样式**,跟其他斜杠命令一样;**转成后台子 agent 照 CC 做**。
5. 在 worktree 上改;提交、合并等用户再说。

## 1. 结论先行

1. **本质是一次旁路模型调用**:拿主会话此刻的上下文,末尾追加一条包好的问题,单发一次;不占 lane、不写 JSONL、不发任何 `message.*` 事件。仓里现成的模板是自动起名(`host/session-title.ts`)。
2. **请求前缀和主轮逐字相同**,供应商的前缀缓存才会命中:系统提示词取主轮最后一次请求的原字符串、工具定义照带、思考档位不改。长会话动辄十万 token,命中与否差着十倍的价钱。
3. **缺口在发动机的导出**:把会话分支拼成模型上下文的 `buildSessionContext`(`harness/session/context.ts:47`)没有导出,宿主抄一份(约 30 行),再用"和主轮请求逐字比对"的测试当哨兵,上游一改就红。
4. **跑到一半时**末尾会挂着还没出结果的工具调用;pi-ai 会自动补 `"No result provided"` 并标成**出错**。宿主先给它们补一句"还在运行"的占位结果,再追加问题。
5. **附件**:界面照普通消息那样编 `PromptInput`(正文 + 评论 + 图片),内核的图片压缩抽成 `prompt()` 与 /btw 共用的一个函数。图片只出现在请求末尾,不影响缓存前缀。
6. **转成后台子 agent(fork)**:照 CC 的 fork 规则 —— 继承父会话的上下文 + 这次的问答、父会话此刻的系统提示词原字符串、同一份工具定义、同一个模型与思考档位,一律后台,跑完照常以 `<task-notification>` 通知主 agent。yoma 的两条安全规则保留:fork 不能再派子 agent、不能碰硬件工具 —— 为了缓存,工具**定义照带**,调用时拦下。
7. **界面**:在提交入口把 `/btw …` 截走,答案流式画在输入框正上方的新坞里;坞上有复制、转后台、关闭;Esc 先关坞,再按才停 agent。

### 2.2 fork(文档 v2.1.206+ 与 2.1.88 源码)

- **触发**:`/btw` 浮层里按 `f`,"Start a forked subagent that inherits the parent conversation plus this question and answer, so it can continue with full tool access. You stay in the current session and find the fork in the panel below your prompt."(仅本地会话)
- **继承**:完整对话历史、会话当前的系统提示词(不是子 agent 自己的)、主对话完全相同的工具集、主对话的模型、思考与 effort 设置。
- **运行**:"A fork always runs in the background";跑完或失败时 "Claude receives a completion notification with the fork's final output",由 Claude 决定要不要引用;面板里能打开它的记录、停掉它、续跑它。v2.1.206 起 fork 可以在深度上限内再派子 agent。
- **2.1.88 的实现**(`CC:tools/AgentTool/forkSubagent.ts`):合成的 `FORK_AGENT`(`tools: ['*']` + `useExactTools`,"for cache-identical API prefixes";`model: 'inherit'`;`maxTurns: 200`);系统提示词用父会话**已渲染的原字节**("Reconstructing by re-calling getSystemPrompt() can diverge … and bust the prompt cache");子 agent 首条消息是一段 `<fork-boilerplate>` 守则(10 条规则 + 固定的报告格式)加 `Your directive: …`;界面把带 `<fork-boilerplate>` 的用户消息单独渲染(`CC:components/messages/UserTextMessage.tsx:190-204`)。

## 4. 设计

### 4.1 对用户是什么样

- 输入框里打 `/btw 问题` 回车;可以同时带图片、行内评论。agent 在跑也照样能用,不打断、不排队。
- 答案出现在输入框正上方的"顺便问"坞里,边想边出字。坞上:复制、**转成后台任务**、关闭(× 或 Esc)。还在答的时候关掉 = 取消这次请求。
- 看得到:截至此刻已经落盘的对话。看不到:agent 正在写的那条、之前的 /btw 问答;还没出结果的工具只知道"还在运行"。
- 不能用工具。问答不进对话历史、不写 JSONL,主 agent 永远看不到 —— 除非用户点了"转成后台任务"。
- 一个会话同时只有一条;新问的顶掉旧的(旧的还在跑就取消)。
- 边界:只有 `/btw` 没有问题 → 提示用法、输入框不动;新会话页(还没有会话)→ 提示先开始对话;子会话页没有输入框。

### 4.2 内核:请求怎么拼(逐字对齐主轮)

新文件 `host/btw.ts`(纯函数)+ `SessionManager` 上的方法。

| 字段 | 主轮 | /btw |
|---|---|---|
| 模型 | 开跑时捕获的 `configuration.model` | `inspectExecution().current?.capturedModel ?? configuredModel` → `models.getModel()`;拿不到就失败 |
| 系统提示词 | 每次请求现算 | **主轮最后一次请求的原字符串**:`openEntry` 把 `systemPrompt` 函数包一层,每次返回前记到 `entry.lastSystemPrompt`;还没发过请求时调同一个函数现算(CC 同款退路) |
| 工具 | `activeToolNames` 的顺序 | `lane.getActiveTools()` 的顺序 + `harness.getTools()`,取同样四个字段;**照带,不执行** |
| 消息 | `readBoundedContext` | `lane.findEntries({ stopAtType: "compaction", order: "newestFirst" })` 反转 → 抄来的 `contextMessages()` → `convertToLlm` |
| 思考档位 | `configuration.thinkingLevel` | `lane.getThinkingLevel()`,不是 off 时给 `reasoning`(用户定 1) |
| 请求选项 | `createRequestOptions` + `sessionId` | 照它的字段从 `harness.getStreamOptions()` 抄;`sessionId` 给**同一个** `<会话 id>:main`(缓存路由);不给 `deferred`;`signal` 用这次 /btw 自己的 |
| 尾巴 | —— | ① 最后一条 assistant 里**还没有结果的工具调用**逐个补一条 toolResult:"This tool call is still running in the main conversation; its result is not available yet."(`isError: false`);② 再追加一条 user 消息:CC 的 `<system-reminder>` 原话 + 问题正文(含评论),附上处理过的图片 |

- **只动尾巴**:历史中间悬空的工具调用不碰 —— 两条路都会被 pi-ai 补成一样的东西,前缀照样逐字相同。
- **不先 `setModel`**:要的是主轮**正在用**的那个模型,换了就吃不到缓存。
- 抄来的 `contextMessages()` 只做三件事:找最近一次压缩;滤掉三种 stopReason 的 assistant;把 compaction / branch_summary 转成摘要消息。custom 条目给空(宿主没配 projector)。

### 4.3 附件(用户定 3)

- **界面**:截到 `/btw` 之后,用去掉 `/btw` 前缀的正文照常调 `buildRequestParts`,得到和普通消息同形的 `PromptInput`:行内评论已经拼进正文,图片是 `data:` URL,`@文件` 是 `file://` 提及件。
- **内核**:把 `prompt()` 里那段图片处理抽成一个函数 `prepareImages(files, signal)`,返回 `{ images, notes, omitted, dropped }`,`prompt()` 与 /btw 共用,`prompt()` 的行为不变。/btw 这边:说明照样跟着正文进模型;没送到的图、非图片的 `data:` 附件**不发 `kernel.error`**,写进坞上的提示(`BtwView.notices`)。
- **`@文件` 与目录**:跟普通消息一样只带路径 —— 普通消息里是 agent 自己用 read 去读;/btw 没有工具,模型读不到文件内容,只能靠对话里已有的内容回答(CC 同样如此)。想让它看到内容,就截图或把片段贴进来,或者转成后台任务。
- **缓存**:图片只在最后一条消息里,前缀不受影响。不支持图片的模型由 pi-ai 换成 "(image omitted: model does not support images)",与主轮同一条路。

### 4.4 内核:生命周期

- `session.btw({ sessionID, input })`(`input` 与 `session.prompt` 同形)**立即**回 `{ btwID }`,之后全部走事件。不走 `admit` / lane,不受忙闲、排队、压缩影响,不改会话状态。
- 状态放在 `entry.btw = { id, question, images, controller, status, answer? }`;新的一条先 abort 旧的;`delete`、`closeEntry`、`disposeAll` 都 abort。结果回来时 `entry.btw` 已经不是同一个对象就丢掉。开跑时刷 `entry.touched`,免得被 LRU 关掉。
- 流式:`models.streamSimple(...)`;进入思考阶段发一次 `thinking`;正文按"前沿立即、之后每 100 ms 一次、结束补发"节流,每次发整段快照。
- **零写入**:不 `recordUsage`、不 `appendCustomEntry`、不 `setName`;测试钉住"/btw 前后 JSONL 逐字节相同"。
- **失败不发 `kernel.error`**,错误只进坞。
- `session.btwCancel({ sessionID, btwID })`:对得上就 abort、发 `cancelled`;对不上什么都不做。
- 子会话调 `session.btw` 直接抛错(同 `prompt` 的 `subagentSession`)。

### 4.5 答案怎么取(照 CC 的 `extractSideQuestionResponse`)

- 所有 text 块用空行拼起来,去首尾空白;thinking 块不要(界面只显示"思考中…")。
- 没有字、但有工具调用 → "模型想调用 X,没有直接回答。换个问法,或者转成后台任务。"
- `stopReason: "error"` → 失败,带上 `errorMessage`;`"aborted"` → 取消;什么都没有 → "没有收到回答"。

### 4.6 转成后台子 agent(fork,用户定 4:照 CC)

**触发**:坞上"转成后台任务"按钮(CC 是浮层里按 `f`;yoma 的焦点留在输入框,字母键要留给打字)。按钮是 `fork` 图标、不带文字(用户 2026-09-24 定),名字在 aria-label 与悬停说明里;不用 agent 卡片上"转后台"那颗 `arrow-down-to-line` —— 那是把在跑的 agent 挪到后台,这里是新派一个。只在答案已经出来(`done`)时可点。点了之后坞关掉,fork 出现在输入框上方的子 agent 坞里(CC:"find the fork in the panel below your prompt")。

**`session.btwFork({ sessionID, btwID })` → `{ taskID }`**:

| 继承什么 | 怎么拿 |
|---|---|
| 对话历史 | 此刻重新读一遍父会话的上下文(同 §4.2 的消息部分,含"还在运行"的占位) |
| 这次的问答 | 一条 user 消息:问题原文(不带 /btw 的 `<system-reminder>`,那段"不许用工具"会和 fork 的目的冲突)+ 图片;一条 assistant 消息:/btw 的答案正文 |
| 指令 | 一条 user 消息:`<fork-boilerplate>` 守则(照 CC 2.1.88 的 `buildChildMessage`,改动见下)+ `Your directive: …` |
| 系统提示词 | 父会话的 `lastSystemPrompt` 原字符串,写进子会话的 `yoma/fork` 值(重开时照用) |
| 工具 | 与父会话**同一份定义、同一个顺序**:子会话按主会话的方式装工具(含四个子 agent 工具,门面换成一律拒绝的桩),激活名单抄父会话此刻的 |
| 模型 / 思考 | 父会话在用的模型与思考档位 |
| 其他 | 一律后台;`maxTurns: 200`(同 CC 的 `FORK_AGENT`);跑完照常 `task-notification` 进父会话收件箱 |

- **合成的 `fork` profile**:不进 `BUILTIN_AGENTS`,agent 工具选不到它;`childProfile` 认出 `fork` 直接给它,不走"找不到定义就落回 general-purpose"那条路。
- **两条 yoma 的规则照留**:fork 的 `before_tool` 拦下四个子 agent 工具与五个硬件工具,回一句"forked agent 不能派子 agent / 不能碰硬件,请直接用别的工具完成"。工具**定义照带**是为了缓存:少一个工具,fork 的第一次请求就和父会话的前缀对不上。
- **守则的改动**(相对 CC 2.1.88):第 1 条改成"不要派子 agent,直接干"(yoma 的子会话本来就不能再派);第 5 条"改了文件先 commit"改成"改了哪些文件列在报告里,不要 commit"(仓里的规矩:git 操作等用户说);加一句"硬件工具与子 agent 工具会被拒绝"。报告格式(`Scope:` / `Result:` / `Key files:` / `Files changed:` / `Issues:`)原样保留。
- **指令正文**(CC 没公开 /btw fork 的原话,yoma 自拟):"The user asked the side question above and it was answered from the conversation alone, without tools. Continue from there with your tools: check the answer against the actual project files and toolchain, fill in what it could not know, and correct it if it was wrong."
- **首轮怎么种进去**:`createChild` 把种子(继承的消息 + 问答 + 指令)挂在 `entry.child.fork` 上(内存),`runChild` 首轮的 `firstMessages` 认出 fork 就交出这一串,一次 `accept` 全部落盘。种子不落盘:进程在排队期间重启,这个 fork 起不来 —— 任务以失败落定并说明原因。
- **子会话页**:会显示继承来的整段历史(它确实是 fork 的上下文);以 `<fork-boilerplate>` 开头的那条用户消息只显示 `Your directive:` 之后的指令(照 CC 单独渲染的做法)。**实现时改在内核投影器里做**(`projector.ts` 的 `userText`,live 与重放同一条路),不动 app 的时间线代码 —— app/AGENTS.md 要求改时间线先量生产基准,而那套 Playwright 基准的场景 2026-08-13(`7c470b7`)就删光了,量不了。
- **不能 fork 的时候**:宿主不能后台(bench / 信箱工位端,`subagents.background === false`)→ 报错;答案还没出来或已被顶掉 → 报错。

### 4.7 协议

```ts
// protocol.ts —— KernelMethods
"session.btw": { params: { sessionID: string; input: PromptInput }; result: { btwID: string } }
"session.btwCancel": { params: { sessionID: string; btwID: string }; result: void }
"session.btwFork": { params: { sessionID: string; btwID: string }; result: { taskID: string } }

// protocol.ts —— KernelEvent
| { type: "session.btw"; btw: BtwView }

// types.ts
export interface BtwView {
  id: string
  sessionID: string
  question: string
  status: "thinking" | "answering" | "done" | "failed" | "cancelled"
  /** 到目前为止的正文(整段快照) */
  text: string
  /** failed 的原因,或"模型想调用工具"那句说明 */
  note?: string
  /** 附件的提示:缩过的图、没送到的图、忽略的非图片附件 */
  notices?: string[]
  startedAt: number
  endedAt?: number
}
```

另:`ids.ts` 的 `PREFIXES` 加 `btw`;`client.ts` 加三个方法;`host/index.ts` 加三条处理;`tasks.ts` 的 `ChildSpec` 加可选的 `fork`、`toolCallId` 改成可选,`TaskManager` 加 `fork()`。事件用**专门的类型**,不复用 `message.part.*`(否则会落进 transcript 的 store,还会被 bench 的 `turn.ts` 当成这一轮的输出)。

### 4.8 界面

## 6. 与 CC 的差异(每条都有理由)

| 差异 | 理由 |
|---|---|
| 系统提示词**每次请求**记快照,CC 是每轮结束记 | yoma 能挂手的地方在请求层,记在这里更准:一轮中途 agent 改了项目记忆,/btw 用的也是最近一次请求那份 |
| 末尾没结果的工具调用补"还在运行"的占位 | 不补的话 pi-ai 会补成"出错",模型会据此说"那个工具失败了" |
| 不做 `skipCacheWrite` | pi-ai 锁定,改不了打标记的位置;DeepSeek / OpenAI 的缓存自动、写入不加价;Anthropic 上只是为问题那一小段多写一次缓存 |
| 流式显示 | 用户定;桌面缺省思考档是 max,一次 /btw 可能要想几十秒 |
| 能带图片与行内评论 | 用户定;图片只在末尾,不影响缓存 |
| 触发更严:`/btw` 后面必须是空白或结尾 | 跟 @ 提及那次的取舍一致 |
| Esc 先关坞再停 agent;没有 Enter / 空格关;转后台用按钮不用 `f` | CC 的浮层抢焦点;yoma 的焦点留在输入框,字母、Enter、空格都要留给打字 |
| 没有 harness 那层重试 | 旁路调用不经过 harness 的退避重发;SDK 自带的那层照旧;流静默断掉有 `withStreamGuard` 的 90 s 看门狗 |
| fork 不能再派子 agent、不能碰硬件工具(定义照带,调用时拦) | yoma 的子 agent 硬规则:没有嵌套任务树;探针与采集设备是进程级独占的。CC v2.1.206 的 fork 可以在深度上限内再派 |
| 用户不能在 fork 的记录里打字续跑 | yoma 的子会话页没有输入框(子 agent 只听主 agent);续跑走主 agent 的 `send_message` |
| fork 守则去掉"先 commit" | 仓里的规矩:git 操作等用户说 |
| 不做:之前的问答当上下文、最近 5 条列表、Tab 切换、`/btw` 重开上一条 | 用户定 4 / 暂不需要 |

## 9. 风险与坑

- **抄来的上下文拼法会漂**:上游改了 `buildSessionContext`,/btw 与 fork 的前缀就和主轮对不上 —— 不报错,只是缓存不命中、钱变多。§5 第 1、9 条是哨兵。
- **快照会旧**:会话重开后第一次 /btw 没有快照,只能现算;这期间项目记忆变过就对不上。这时供应商的缓存多半也过期了,损失有限。
- **一轮中途换了思考档位**(界面在排队发消息前也会 `setModel`):`lane.getThinkingLevel()` 是新档位、在飞那轮是旧档位 —— 只影响这次命不命中缓存。
- **并发请求变多**:主轮和 /btw 同时打同一个供应商,可能撞 429;/btw 失败就显示原因,主轮有自己的重试。
- **长上下文、冷缓存**:一次 /btw 就是一次全价的整段请求;fork 更是把整段上下文复制进一个新会话文件。
- **fork 的子会话页很长**:继承来的整段历史都会画出来;先接受,嫌长再做折叠。
- **fork 的种子只在内存里**:排队等并发槽期间进程重启,这个 fork 起不来,任务以失败落定。
- **fork 的缓存路由键不同**:发动机按 `<会话 id>:main` 给 `sessionId`,子会话的 id 和父会话不同,而这个值由发动机定、宿主改不了。按会话亲和或 `prompt_cache_key` 路由缓存的供应商(OpenAI 一类)上,fork 的第一次请求命中率会低一些;DeepSeek 按前缀自动缓存,不受影响。
- **Anthropic 与图片**:文档说"prompt 里任何位置增删图片会让消息段缓存失效",/btw 带图时在 Anthropic 上可能吃不到消息段缓存;DeepSeek / OpenAI 按前缀算,不受影响。
- **别复用 `message.part.*`**(§4.7)。
- **Esc 的顺序**(§4.8):改错了,用户想关答案却把 agent 停了 —— 对正在烧录的板子是实打实的损失。
