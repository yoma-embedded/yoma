## 1. 「只显示 bash / ls」的三个原因与修法

| # | 原因 | 修法 |
|---|---|---|
| a | `basic-tool.tsx` 在 pending / running 时整个藏起副标题(命令)。pending 从模型写这个调用一直到整条回复写完、工具开跑;running 是整个执行期。跑几十秒的 make / openocd 从头到尾只有一个闪着的「调用了 \`bash\`」(反引号是字面画出来的) | 通用卡的行:命令一有就显示,不看状态。投影器在 `toolcall_end` 就把完整参数放进 `input` 了 |
| b | 通用卡自己按键名表挑副标题,不用契约的 `summary()`(契约里的 summary 本来就是为卡片副标题写的)。`ls` 不带 path → 空;grep / find 带了 path → 显示 path,pattern 被整个丢掉(`args()` 把表里的键全滤了) | 新 `tool-summary.ts`:有契约的问契约(`@yoma-desktop/kernel/tools/contracts`),没契约的上游四件套 bash → command、read / write / edit → path,其余照旧按键名兜底 |
| c | 没有结果的调用永远停在 pending / running:模型写调用时被打断、或工具跑到一半关了 app。名字一直闪、命令不显示,pending 还锁着点不开 | 显示层兜底:这一轮已经不在跑(`!workingTurn`)时,还在 pending / running 的通用卡画成「未完成」—— 不闪、能点开、命令照显示。「已探索」组的标题同理不再闪「正在探索」。只动通用卡,硬件卡不动 |

## 2. 紧凑工具行(只给通用卡)

照 pi-agent-desktop 的 `ToolCallBlock`:

- 一行:**工具名**(等宽加粗,按状态着色)+ **摘要**(等宽、单行省略)+ 右侧**耗时** + 展开箭头。
- 整行一个细边框 + 很淡的底色:成功绿、失败红、未完成黄、进行中中性(名字闪)。颜色用 v2 主题的
  `--v2-state-{fg,bg,border}-{success,danger,warning}`,深浅两套主题都有。
- 展开:先是**完整参数**(bash / powershell 是整段命令,其余是顶层标量 `key: value`,同查找的「可搜的字」口径),
  再是**输出**(`data-component="tool-output"`,限高滚动),失败时是**报错全文**,未完成时一句说明。
- **失败也走这张卡**(`ToolPartDisplay` 的 error 分支只留给有专用卡的工具):从前失败的通用工具走 `ToolErrorCard`,
  标题是「Shell」、副标题是报错按 `": "` 切出来的第一段,命令整个看不见。
- 耗时:完成 / 失败 = `time.end - time.start`;进行中每秒走一次(全局一个共享的秒表,有人订才转)。
  格式 `0.4s` / `12s` / `1m 5s`,不翻译(和用量那种读数一样);不到 0.1 秒不画(一排「0.0s」只是噪声)。
- 标题不再是「调用了 \`bash\`」,就是工具名。
- `BasicTool` 新增几个可选 prop,缺省行为不变(硬件卡与 agent 卡都用它,不能让它们跟着变):
  `row` + `tone`(落在 `data-tool-row` / `data-tone` 上,CSS 按属性驱动;`data-variant` 已被 Collapsible 自己占用),
  `revealWhilePending`(pending / running 时也画副标题与 action)。`GenericTool` 一律 `defer`(展开态延迟挂载,
  收着的行一份都不建)。
- 硬件卡在 details 认不出时会回落到 `GenericTool`(旧会话),那种情况下它会跟着变成紧凑行 —— 回落本来就是通用卡,算预期内。

### 耗时的内核修复(`projector.ts`)

重放历史时,`toolPart()` 给每个调用记的开始时间是重放那一刻的 `Date.now()`,结束时间是当年的工具结果时间戳,相减是负数
(`flash-card.ts` 早就因此绕开了 `state.time`)。修法:重放循环把 entry 的落盘时间(`Entry.timestamp`)经
`applyMessage(message, { entryId, timestamp })` 递进来,重放时它就是工具的开始时间 —— assistant 那条 entry 在回复结束、
工具开跑之前落盘(`agent/src/harness/runtime/drive/response.ts`:response entry 与 `at: "tools"` 在同一次提交里),
同一批工具并行,共用这一个开始时间。live 路径不变(`markToolRunning` 在 tool_start 时覆盖)。live 与重放仍走同一个
`applyMessage()`(投影器不变式 1)。

pi-agent-desktop 用的是「工具结果时间 − assistant 消息时间戳」,而 pi-ai 的消息时间戳是**开始请求**那一刻,所以它显示的
耗时含模型生成时间。我们这个不含模型生成时间,但有一处例外(审查抓到的):一批里的调用是逐个开跑的,每个开跑前先过
before_tool,要确认的(烧录、带探针命令的 bash)在那儿等人点 —— 重放出来的耗时含等确认的那段,live 的不含。
transcript 里没有更准的开始时间,接受并写明。

## 3. 「处理详情」折叠(时间线)

### 3.1 一轮怎么切

在 `rows.ts` 的 `constructMessageRows` 里,只对**已经不在跑**的轮次做(`!(isActive && status !== "idle")`);正在跑的
那一轮和今天一样平铺(pi-agent-desktop 的 live tail 同理)—— 跑完那一下行重建一次,就是「跑完自动收」。

1. **最终回答**:这一轮里最后一条有可画 part 的**非 synthetic** assistant 消息,它最后一个非文字 part 之后的那几段文字
   (pi-agent-desktop 的 `splitFinalAssistantBlocks`)。
2. **没有最终回答也折**(最后一条以工具调用收尾):后台子 agent 的通知、排队的用户消息在工具边界插进来会另起一轮,
   前半截就以工具调用收尾,回答在后面那一轮里。整段收起,外面没有回答。(初稿写的是「整轮不折」,审查抓到:后台子 agent
   与排队都是缺省开的,长任务的前半截会永远不收。)
3. **不折的轮次**:被打断的(有 `MessageAbortedError`)与报错收场的(`terminalError`,含重试耗尽)—— 出了什么事都摆在眼前。
4. **过程**:最终回答之前的全部可画 part,照旧先过 `groupParts`(「已探索」组照旧)。
5. **分段**:连着的**可折叠**组合成一段;不可折叠的把段切开、自己原样留在原位。
   - 可折叠:没有专用卡的工具(`!hasDedicatedCard(tool)`)、「已探索」组、说明文字、思考段。
   - 不可折叠:有专用卡的工具(硬件五件 + agent)、compaction 分隔线、synthetic 消息(压缩摘要)里的 part。
6. **一段只有含至少一次工具调用才折**;只有文字 / 思考的段原样平铺(比如烧录卡前面那句「我先烧一下」)。
7. 最终回答之后还有别的消息(罕见:回答之后又来了 synthetic 的压缩摘要)照旧平铺在回答后面。

```
你:烧一下再看波形
▸ 处理详情 · 4 次工具调用
[烧录卡,原样]
▸ 处理详情 · 2 次工具调用 · 1 次失败
[示波器卡,原样]
最终回答……
本轮改动……(原样,在折叠外)
```

## 9. 第二轮:用户试用之后(2026-09-24)

### 9.1 用户看到的问题

1. 同一批里的 `ls` 早就做完了,却一直是白的(在跑)、计时跟着前面那条 `du -sh` 走到 1m 45s。
2. 跑工具的时候底下挂着「思考中」。用户要:**只有模型真的在往外发思考内容时才显示「思考中」**。
3. 「思考中」要小、要淡;「已探索」那一行要小 —— 这些状态信息不能跟模型的正式回复一个样式。

### 9.2 原因

1. 一批工具的结果按调用顺序落定:`agent/src/harness/runtime/drive/tool-placement.ts` 的 `readPlacement` 从第一个没落定的开始,
   只收连着做完的;前面那条没做完,后面做完的也得排着。投影器只在收到结果消息时才标完成。但每个调用真正做完时,发动机会单独发
   一个 `tool_end`(`drive/tools.ts`),里面的 `result` 就是那条结果消息的 content / details(`toolResultFromMessage`)。
2. `rows.ts` 的 `Thinking` 行其实是「这一轮还在跑」的标志:不开「显示思考」时,会话忙就一直挂着,不分在等模型、在出思考、
   还是在跑工具。
3. 那一行是正文字号(14px、medium);「已探索」的标题套的是工具卡片标题的样式(14px)。

### 9.3 改法

1. **工具一做完就收尾**:投影器加 `finishTool(toolCallId, result, isError)`,session-manager 的 `tool_end` 里调它。它和
   `markToolRunning`(tool_start)、`updateToolProgress`(tool_update)一样是 live 专用的路;之后按顺序到的结果消息照旧走
   `applyToolResult`,终态与重放逐字段相同(不变式 1 不受影响)。
2. **底下那一行按阶段显示**(参照 pi-agent-desktop 的 `phaseLabel`:`正在运行 {name}…` / `正在等待模型…`,模型在出字时不显示):
   - 这一轮最新那条 assistant 消息的最后一个 part 是思考段 → **「思考中」**(模型正在出思考内容),后面照旧跟思考的标题;
   - 有工具在跑 → **「正在运行 bash、ls」**(多于 3 个:「正在运行 a、b、c 等 N 个」);
   - 还没有回复、或者这一批工具都已收尾、下一次请求还没出字 → **「等待模型」**;
   - 模型在写正文、在写工具调用的参数、工具在等确认 → **不显示**(正文、闪着的工具行、确认条自己就说明了)。
   判断放在这一行的组件里(新的纯函数 `timeline/activity.ts`),不进行的 memo(规矩 1:行不读工具状态)。这一行改成**只要这一轮
   在跑就出**(从前「显示思考」打开时,第一段内容出来就收掉了);打开「显示思考」时「思考中」不在这里出 —— 思考块自己在闪。
3. **样式**:这一行(连同「正在压缩上下文」)改成 12px、常规字重、最淡的一档字色;「已探索」的标题行改成 12px、淡色,
   只改组标题,不碰组里的工具行。

- 前端:`activity.ts` 单测(五种阶段);rows / timeline-projection 里「这一行只在显示思考关着时才一直挂着」的旧期望跟着改。
