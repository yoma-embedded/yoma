# Yoma 内核全景

> 这是这套学习文档的第一篇。读完它,你应该能在脑子里画出「用户敲一句话 → 模型回话 → 工具真的动了板子 → 结果落进磁盘」的完整链路,并且知道每一跳落在哪个包的哪个文件里。
>
> 后面所有单文件文档都是这张骨架上的一枚钉子。查任何一个文件之前,先回到这里确认它挂在哪一段。

---

## 0. 先说清楚:这三个包是什么关系

Yoma 的内核是三个包,一层套一层:

> **`packages/ai` 定义「怎么跟模型说话」,`packages/agent` 定义「怎么让模型循环着干活」,`packages/coding-agent` 定义「干什么活」。**

```
                        ┌───────────────────────────────────────────────┐
   宿主(不在本套文档) │  packages/kernel/host(桌面端)                │
                        │  packages/coding-agent/src/acp.ts(Zed / ACP) │
                        │  packages/bench(信箱闭环 / 演练台)          │
                        └───────────────────┬───────────────────────────┘
                                            │ new AgentHarness({...})
                                            │ harness.prompt("...")
   ┌────────────────────────────────────────▼────────────────────────────────────┐
   │  packages/coding-agent  =  @yoma/my-pi-coding-agent   「干什么活」          │
   │  ─────────────────────────────────────────────────────────────────────────  │
   │  · 工具集:read / write / edit / bash                                        │
   │           netlist → datasheet → stm32config → flash → log → gdb(嵌入式)   │
   │           toolchain / examples                                              │
   │  · 系统提示词拼装(buildSystemPrompt)、资源发现(AGENTS.md / skills)      │
   │  · ACP 适配器(内核的第一个宿主,也住在这个包里)                          │
   └────────────────────────────────────────┬────────────────────────────────────┘
                                            │ AgentTool[] + systemPrompt
   ┌────────────────────────────────────────▼────────────────────────────────────┐
   │  packages/agent  =  @yoma/my-pi                       「怎么循环着干活」    │
   │  ─────────────────────────────────────────────────────────────────────────  │
   │  · agent-loop.ts       裸循环:一次 prompt → N 轮「请求 + 执行工具」        │
   │  · harness/            会话外壳:相位机、turn 快照、事件落盘、abort         │
   │  · harness/session/    会话树:一切皆条目的追加日志 + 投影                  │
   │  · harness/compaction/ 上下文压缩、分支摘要                                 │
   │  · harness/env/        ExecutionEnv:碰真实机器的唯一出口                   │
   └────────────────────────────────────────┬────────────────────────────────────┘
                                            │ models.streamSimple(model, ctx, opts)
   ┌────────────────────────────────────────▼────────────────────────────────────┐
   │  packages/ai  =  @earendil-works/pi-ai(vendored,pi-minimal)「怎么说话」  │
   │  ─────────────────────────────────────────────────────────────────────────  │
   │  · types.ts     Message / Context / Tool / Model / AssistantMessageEvent    │
   │  · models.ts    Provider / Models 注册表、鉴权解析、计费、思考档位          │
   │  · api/*        三套厂商协议:anthropic-messages / openai-completions /     │
   │                 openai-responses(把统一形状翻成某家的 HTTP 请求体)        │
   │  · auth/ providers/ utils/  凭据、模型目录、EventStream、校验、重试分类     │
   └─────────────────────────────────────────────────────────────────────────────┘
```

三条边界的意义:

- **`ai` 不知道有 agent。** 它眼里只有一个扁平的 `Message[]`,没有「会话树」「压缩」「技能」这些概念。
- **`agent` 不知道有 read/write/gdb。** 它眼里只有 `AgentTool` 这个接口和 `execute()` 这个回调。
- **`coding-agent` 不知道 provider 长什么样。** 它只往 harness 里塞工具和系统提示词。

这三条边界是刻意维护的:任何一个方向的「顺手 import」都会让某个包丧失可替换性。最典型的一处纪律是 `packages/coding-agent/src/index.ts` **刻意不导出 ACP 适配器** —— 桌面端把整个内核 inline 进一个 `kernel.js`,主入口一旦 re-export `acp.ts`,`@agentclientprotocol/sdk` 就会跟着进产物,而桌面端根本不说 ACP。

**读这张图的三个要点:**

1. **只有一个循环。** `agent-loop.ts` 的 `runLoop` 是整套代码里唯一的状态机。harness 没有循环(文件头注释原话:「harness 没有自己的循环,它只是 runAgentLoop 的一个高级调用者」),宿主也没有。所有「多轮」都发生在 ④ 的那两层 while 里。
2. **只有一个 LLM 边界。** ⑤ 的 `convertToLlm` 是 `AgentMessage`(内部形状,可以有自定义角色)变成 pi-ai `Message`(能发给模型的形状)的唯一转换点。想知道「什么进 LLM、什么只进 transcript」,只需要读那 168 行。
3. **只有一个落盘点。** ⑧ 的 `handleAgentEvent` + `flushPendingSessionWrites` 是会话树唯一的写入者(除了 `compact()` / `navigateTree()` 两条 idle-only 的侧枝)。这也是「同一时刻只有一个写者」的唯一保证。

## 2. 三个包各自的定位

### 2.1 `packages/ai` = `@earendil-works/pi-ai` — 契约层与协议层(46 个文件)

**职责:** 把「跟大语言模型说一次话」变成一个统一的、与厂商无关的函数调用。

**它管:** 消息与内容块的形状(`Message` / `TextContent` / `ToolCall` / …)、一次请求的输入形状(`Context`)、流式响应的事件协议(`AssistantMessageEvent`)、模型描述与计费(`Model` / `ModelCost`)、provider 注册表与鉴权解析、三套厂商协议的 HTTP 实现,以及一圈周边工具(异步事件流、参数校验、token 估算、错误分类)。

**它不管:** 会话历史怎么存、什么时候该压缩、工具怎么执行、要不要重试。这些概念在 pi-ai 里根本不存在 —— 它只看到一个扁平的 `Message[]`。

**为什么这样切:** 因为「厂商差异」是一个体量惊人、且与业务逻辑完全正交的问题。光 `api/openai-completions.ts` 一个文件就有 1302 行,其中超过三分之一是 `detectCompat()` 的兼容性矩阵 —— 二十几家「号称兼容 OpenAI」的实现,对 reasoning 参数、max tokens 字段名、`developer` 角色、strict 模式、缓存标记的要求全不一样。把这些封死在一个包里,上层才可能对「这是 Anthropic 还是 DeepSeek」一无所知。读那个文件时,把 `detectCompat` 当成一张**踩坑账本**看最有效:每一个 boolean 背后都是某一家的一次真实报错。

**这个包是 vendored 的:** 从上游 pi 项目复制进来,再按本仓需要裁剪,代号 `pi-minimal`。裁掉的是六套 API 实现整个删文件(azure / bedrock / google / vertex / mistral / codex),以及上游那个全局兼容入口。留下的 provider 工厂只有 `providers/anthropic.ts`、`providers/openai.ts` 和测试用的 `providers/faux.ts`。注意 `KnownApi` 与 `KnownProvider` 这两个字符串联合**没有跟着裁**,依然列着三十来家 —— **类型联合比实现宽**,写一个 `api: "google-generative-ai"` 的模型能通过 typecheck,失败要到运行时才以 `ModelsError("stream")` 的形式从流里冒出来。

**入口:** `src/index.ts`(41 行)是纯 barrel,开头四行注释是 pi-minimal 裁剪的唯一书面记录。它 re-export 了 `types.ts` / `models.ts` / `auth/*` / `utils/*` / `providers/faux.ts` 的全部,以及三个 API 的选项类型。**provider 工厂与 API 实现不走主入口**,改走 `@earendil-works/pi-ai/providers/*` 与 `/api/*` 深引用,保证主入口无副作用、不带生成的模型目录。

**一个必须记住的运行时事实:** 这个包的 `exports` 全部指向 `dist/`,根 `tsconfig.mypi.json` 的 path 也指向 `./packages/ai/dist/index.js`。**改了 `src/**/*.ts` 之后必须 `bun --cwd packages/ai build`**,否则内核跑的还是旧代码,而且一声不吭。

### 2.2 `packages/agent` = `@yoma/my-pi` — 循环、会话与上下文(24 个文件)

**职责:** 把「一次 prompt」变成「一串 LLM 请求 + 工具执行」,并且把这个过程的状态、历史、上下文预算管起来。

四个子系统:

| 子系统 | 文件 | 干什么 |
|---|---|---|
| 裸循环 | `agent-loop.ts` `types.ts` `agent.ts` | 双层 while 的状态机 + 全部契约类型 |
| 会话外壳 | `harness/agent-harness.ts` `harness/types.ts` `harness/messages.ts` | 相位机、turn 快照、事件落盘、abort、hook 分发 |
| 会话树 | `harness/session/*`(7 个文件) | 一切皆条目的追加日志 + 投影 + Repo/Storage 两层抽象 |
| 上下文与环境 | `harness/compaction/*` `harness/env/nodejs.ts` `harness/skills.ts` `harness/utils/*` | 压缩、分支摘要、技能发现、执行环境、输出截断 |

**为什么这样切:** 循环本身是**无状态纯函数**(`runAgentLoop(prompts, context, config, emit, signal, streamFn)` 跑完一次就返回消息数组),而「一个可长期使用的会话对象」需要状态。分开的收益是:循环可以被单测、可以被别的外壳包装;而 harness 里一行 while 都没有,只做「装配 + 冻结 + 回流落盘」。

**入口二分:** `src/index.ts`(49 行)是**浏览器安全**的主入口,`src/node.ts`(4 行)是 Node 专用入口,只多导出一个 `NodeExecutionEnv`。凡是碰 `node:fs` / `child_process` 的实现只从 `./node` 走,保证根入口能进浏览器打包。`index.ts` 里大部分子模块用 `export *`,唯独两个 compaction 模块用具名白名单 —— 于是 `CompactionDetails` / `CompactionResult` / `CutPointResult` / `ContextUsageEstimate` 等类型**从包根拿不到**(见 §7)。

**一个反直觉的事实:** `agent.ts` 里那个 `Agent` 类在本仓库**没有生产调用方**。桌面端与 ACP 都用 `AgentHarness`,而 harness 直接调 `runAgentLoop`。`Agent` 现在的角色是「裸 loop 该怎么被有状态地包起来」的参考实现 + `agent.test.ts` 的被测对象。它的价值在于:harness 的每一样状态管理(队列、单飞行守卫、事件折算回状态)都能在这里找到一个更简单的原型 —— **对照着读收益很大,但改它不会影响桌面端**。

### 2.3 `packages/coding-agent` = `@yoma/my-pi-coding-agent` — 工具、提示词与宿主(50 个文件)

**职责:** 决定「到底有哪些工具、它们叫什么、怎么跟模型说话」,以及把内核接到一个具体协议上。

四块:

| 块 | 文件 | 干什么 |
|---|---|---|
| 工具骨架 + 文件三件套 | `core/tools/{types,index,read,write,edit,edit-diff,bash,path-utils,file-mutation-queue}.ts` | 定义 `ToolDefinition`、两个装配工厂、read/write/edit/bash |
| 嵌入式六件套 | `core/tools/{engines,netlist,datasheet,stm32config,flash,log,gdb,gdb-mi,serial}.ts` | 产品内核:把「板子」变成模型可调用的工具 |
| 项目理解与起步 | `core/{system-prompt,resources}.ts` `core/toolchain/*` `core/examples/*` | 系统提示词、AGENTS.md / 技能发现、工具链对账、厂商例程库 |
| ACP 适配器 | `acp.ts` `acp/{agent,session,models}.ts` | 内核的第一个宿主(给 Zed) |

**为什么这样切:** 因为「有哪些工具」是产品决策,变得最快;而循环和协议变得最慢。工具集的装配面被刻意压到只有两个工厂 —— `createCodingToolDefinitions`(read/bash/edit/write + toolchain + examples)和 `createEmbeddedToolDefinitions`(嵌入式六件套)。「按名挑选」「聚合 Options」这些历史装配面在 2026-08 精简中删掉了;需要特殊装配的场合(桌面端必须显式传 `enginesDir`)直接用各模块导出的单工具工厂。

**嵌入式六件套的顺序就是产品流水线:**

```
netlist(读原理图网表) → datasheet(查手册) → stm32config(生成驱动工程)
   → flash(烧录) → log(看板子真的打了什么) → gdb(日志不够时进去看寄存器与栈)
```

**它有两个宿主。** ACP 适配器(`src/acp/agent.ts`,给 Zed)是内核的**第一个**宿主,桌面端内核 host(`packages/kernel/src/host/session-manager.ts`)是第二个,而且是照着它写的。两边都调 `loadContextFiles` / `discoverSkills` / `collectToolPromptData` / `buildSystemPrompt` —— 这是仓库根 CLAUDE.md 写死的纪律:「从哪些目录找上下文与技能」是产品决策,抄一份的结果就是「Zed 读得到项目的 AGENTS.md、桌面端读不到」。

**入口:** `src/index.ts` 只有 8 行,纯 re-export 四个桶(examples / engines / tools / toolchain),**刻意不导出 ACP**。另有三个「只靠打包别名可达」的深引用被桌面端使用:`/models`(共用 `acp/models.ts` 的 `FileCredentialStore` 与 `resolveModel`)、`/system-prompt`、`/resources`。这三个**不在 package.json 的 exports 里**,改成 workspace 解析之前必须先补 exports。

## 3. 核心概念词典

按「读者第一次会在哪儿撞见」排序。术语给英文原词。这是你的地图钉 —— 后面每篇单文件文档都会假定你认识这些词。

### 第一组:发一次请求就会撞见(pi-ai 契约层)

**Message / Context(消息与上下文)**
`Message = UserMessage | AssistantMessage | ToolResultMessage`,靠 `role` 判别,三者都有 `timestamp`(毫秒 Unix 时间戳)。`Context` 是**一次请求的全部输入**,只有三个字段:`systemPrompt?`(可选)、`messages`(必填)、`tools?`(可选)—— 小到可以背下来。它不是长期存活的状态,而是 agent-loop 每一轮现场拼出来的。注意 agent 包自己的 `AgentContext` 是另一个东西(装 `AgentMessage`),`convertToLlm()` 负责把它降维成这里的 `Message[]`。「会话树」「压缩」这些概念在 pi-ai 这一层根本不存在。

**content part(内容块)**
四种:`TextContent{type,text,textSignature?}`、`ThinkingContent{type,thinking,thinkingSignature?,redacted?}`、`ImageContent{type,data(base64),mimeType}`、`ToolCall{type:"toolCall",id,name,arguments,thoughtSignature?}`。三条容易踩的细节:`UserMessage.content` 可以是**裸字符串**(简写);`AssistantMessage.content` 里**没有** ImageContent;`ToolResultMessage.content` **可以有图片**(所以 datasheet 的 `view_figure` 能直接把图给模型看)。`ToolResultMessage` 还有一个泛型槽 `details`,Yoma 的工具卡片就靠它。

**StopReason(停止原因)**
五个取值:`stop`(说完了)/ `length`(撞 maxTokens 被截断)/ `toolUse`(停下来是为了调工具)/ `error`(请求或运行时失败,`errorMessage` 里有人话)/ `aborted`(被 AbortSignal 掐掉)。流事件协议把这五个值切成两半并在类型层钉死:`{type:"done", reason}` 只接受 stop|length|toolUse,`{type:"error", reason}` 只接受 aborted|error。**关键:`error` 和 `aborted` 是正常返回的数据,不是抛出的异常。**

**失败是数据不是异常(errors as data)**
这是整套代码最重要的一条设计,后面每一层都会重复它。`StreamFn` 的契约明确写着:请求失败、模型不存在、网络断了、被 abort 了,**都不许抛异常**,必须编码成流里的 error 事件 + 一条 `stopReason: "error"|"aborted"` 的 assistant 消息。于是循环永远只有一条正常路径:拿到一条 assistant 消息,看它的 `stopReason` 决定下一步。三个直接后果:(1)`harness.prompt()` 在 abort 之后是 **resolve 而不是 reject**;(2)provider 失败会作为一条消息进 transcript 与会话文件;(3)「重不重试」变成了应用层的决定。实现手法有两种:chat 侧靠 `lazyStream` 的 `.catch` 兜底,图片侧靠函数体整个包在 try/catch 里 —— 手法不同,契约相同。

**AssistantMessageEventStream / EventStream(事件流)**
`EventStream<T,R>`(`ai/src/utils/event-stream.ts`,88 行)是一个「队列 + 等待者列表」的极简异步迭代器,推拉合一:`push(e)` 时若有消费者正 await 就直接把值交给它,否则进队列;所以「生产快消费慢」和「消费快生产慢」两种节奏都不丢事件。构造时注入 `isComplete`(哪个事件算终结)与 `extractResult`(从终结事件取结果)两个函数把它参数化 —— pi-ai 侧钉成「done/error 终结」,agent 侧钉成「agent_end 终结」。消费方有两个通道:`for await` 拿逐个事件,`await stream.result()` 拿最终结果。

**partial 的引用语义**
事件协议是一条严格时序:`start` → 若干 `text/thinking/toolcall` 的 `_start`/`_delta`/`_end` → 终局 `done` 或 `error`。关键细节:**每个事件都带 `partial`,而它始终是同一个 `output` 对象的引用,不是快照。** 消费者要么立刻读、要么自己深拷贝。这条性质直接决定了桌面端投影器「快照始终从 `partial.content` 重算、delta 只是叠加」的做法是对的。

**Model / Api / Provider**
`Model<TApi>` 是**发一次请求需要的全部信息**:id / name / api / provider / baseUrl / reasoning / thinkingLevelMap / input / cost / contextWindow / maxTokens / compat。`Api` 不是枚举而是 `KnownApi | (string & {})` —— 这个 TypeScript 惯用法让编辑器补全出九个已知值,同时**允许任意字符串**,于是自定义 provider 不用改这个包。运行时真正的派发靠 `model.api` 这个**值**:`createProvider` 的 `apiFor()` 拿它去 `byApi` 映射里取实现。注册表里存的模型一律退化成 `Model<Api>`,要恢复精确类型用类型守卫 `hasApi(model, "anthropic-messages")`。

**ThinkingLevel(思考档位)**
两个同名类型必须分清:pi-ai 的 `ThinkingLevel = minimal|low|medium|high|xhigh|max`(**不含 off**),`ModelThinkingLevel = "off" | ThinkingLevel`(七档);而 `packages/agent/src/types.ts` 自己定义的 `ThinkingLevel` **含 off**。`Model.thinkingLevelMap` 的语义:缺键 = 用 provider 默认值,`null` = 该档不支持,字符串 = 发给上游时替换成这个值。`getSupportedThinkingLevels(model)` 过滤时有两套相反的默认:**xhigh 和 max 要求映射不是 undefined(必须显式声明才算支持)**,其余五档默认支持除非写了 null。`clampThinkingLevel` 的方向容易记反:**先往更高档找,找不到再往低档降**(宁可想得更多);认不出的字符串直接返回第一档。

**Usage / cost(计费)**
`Usage` 记 token 账,两处子集关系不要重复计算:`reasoning` 是 `output` 的子集,`cacheWrite1h` 是 `cacheWrite` 的子集。`calculateCost(model, usage)` 是**原地修改**的:写满 `usage.cost` 五个字段再返回同一个对象,并且**不计算 `totalTokens`**(那个由各 API 实现自己填)。分层计价里的 `inputTokens = input + cacheRead + cacheWrite`(包含缓存部分),命中 `inputTokensAbove` 严格小于它、阈值最高的那一档,整体替换费率。

**Credential 判别联合与凭据解析**
`Credential = ApiKeyCredential | OAuthCredential`,靠 `type` 字段判别。`resolveProviderAuth` 的三层顺序:**override(调用方显式传的 apiKey)> 存储凭据(按 type 分派到 oauth 或 api_key 解析器)> ambient(环境变量等)**。任何一层命中就返回,不叠加。OAuth 分支还有一套**双重检查锁**:锁外先乐观判过期(覆盖「大多数请求 token 还没过期」的常见情形),过期才进 `credentials.modify()` 的串行锁,锁内再确认一次(可能已被并发请求刷过),这样并发请求撞上同一个过期 token 时只发一次刷新网络调用。

**pi-minimal(裁剪版)**
本仓对上游 pi-ai 的裁剪代号。裁掉两类东西:六套 API 实现整个删文件(azure / bedrock / google / vertex / mistral / codex),以及上游那个全局兼容入口(provider 工厂改走 `/providers/*` 深引用)。留下三套协议、两个真 provider 工厂 + 一个 faux。**副作用:类型联合没跟着裁**,`KnownApi` / `KnownProvider` 依然列着几十个名字。

### 第二组:agent 循环

**run / turn / tool batch 三级节奏**
一次 run 从 `agent_start` 到 `agent_end`,可能包含多个 turn。一个 turn = 一条 assistant 消息 + 它请求的那批工具调用及其结果,以 `turn_start` 开头、`turn_end` 结尾(载荷里带 `message` 和 `toolResults`)。一批工具(tool batch)是同一条 assistant 消息里的全部 toolCall 块,它们要么一起串行要么一起并行,**不会跨消息混批**。10 种 `AgentEvent` 严格对应这三级,前端投影器就是照着这个节奏建卡片的。

**AgentContext vs AgentState**
两个都叫「状态」,寿命完全不同。`AgentContext` 是**一次运行的输入快照**,只有 systemPrompt / messages / tools 三个字段;它被 loop 就地修改(流式消息 push 进 messages、工具结果也 push 进去),运行结束就扔。`AgentState` 是**长命状态**,住在 `Agent` 类(或 harness)里,除了模型、档位、工具、transcript,还有 isStreaming / streamingMessage / pendingToolCalls / errorMessage 这些 UI 要看的实时字段。开跑时从 State 复制出 Context,跑的过程中靠事件把变化折算回 State —— **两边不是同一个数组,这是刻意的**。

**AgentTool 与 `execute` 的签名**
`execute(toolCallId, params, signal?, onUpdate?) => Promise<AgentToolResult<TDetails>>`。`params` 是已经过 `validateToolArguments` 校验与 `Value.Convert` 转换的对象;返回 `{content, details, addedToolNames?, terminate?}` —— `content` 是回给模型的,`details` 是给日志与 UI 的结构化数据(桌面端和 Zed 的工具卡片吃它)。契约是**失败要 throw 而不是把错误编进 content**:agent-loop 会 catch 住,用 `createErrorToolResult(err.message)` 造一条 isError 的结果。`onUpdate` 用于流式部分结果,只在本次 execute 期间有效。

**steering(飞行中插话)vs follow-up(将停时追加)**
两个队列的差别只有一处:被**拉取的时机**。`getSteeringMessages()` 在 run 开始前拉一次、以及每个 `turn_end` 之后(过了 `prepareNextTurn` 与 `shouldStopAfterTurn`)各拉一次 —— 只要模型还在干活,插话就会在下一次请求前进入 transcript,当前这轮的工具照常执行、不被跳过。`getFollowUpMessages()` 只在内层循环已经退出(没有待执行工具、也没有插话)、agent 本来就要停下来的那一刻拉一次;有货就当成新的待注入消息再进内层,于是又是一轮完整的 turn。一句话:**steering 是「插队」,follow-up 是「续摊」**。`QueueMode`("all" / "one-at-a-time")决定每次拉取是清空队列还是只取最老的一条,两个队列各有各的模式,默认都是 one-at-a-time。

**executionMode 与 terminate**
`executionMode: "sequential"` 是**批级传染**的:这一批 toolCall 里只要有一个工具标了 sequential,整批(包括同批的 read/bash)就退成串行。而且它**只能单向升级**:标 `"parallel"` 并不能把配置的 sequential 拉成并行。`terminate: true` 的判定是**全票通过**:`finalizedCalls.length > 0 && every(f => f.result.terminate === true)` —— 必须整批每一个都为 true,只要有一个工具没表态循环就照常继续。这是刻意的:模型常在一条消息里既调 `exit_plan_mode` 又调别的工具,少数派不该替多数派叫停。

**parallel 模式里的两种顺序**
并行执行时有两条不同的顺序同时存在,别混:**完成序** —— 每个工具跑完就地 emit `tool_execution_end`,谁先跑完谁先出,UI 因此能第一时间画出已完成的卡片;**源序** —— `Promise.all` 全部落定之后,才按 assistant 消息里 toolCall 块的原始顺序逐条造 `ToolResultMessage` 推进 transcript(很多 provider 对此有要求)。另外准备阶段(参数校验 + beforeToolCall)是**串行 await** 的,只有 `execute` 才并发。

**`stopReason === "length"` 的失败处理**
输出被 token 上限截断时,最后那个 toolCall 的 JSON 参数很可能只写了一半 —— 但 JSON 解析器可能照样给出一个结构合法的对象,直接执行等于拿残缺参数动板子/改文件。所以循环分叉走 `failToolCallsFromTruncatedMessage`:给每个调用照常 emit `tool_execution_start`(UI 卡片形状不变),然后直接造一条 isError 的结果说「本次未执行:响应触到输出 token 上限,参数可能被截断,请带完整参数重发」,`terminate: false` 保证循环必然再跑一轮让模型自己重发。**反面:如果被截断的消息里没有工具调用,循环不做任何补救,直接按正常结束处理。**

**prepareNextTurn / shouldStopAfterTurn 的次序**
`turn_end` 发出之后,循环先调 `prepareNextTurn`(可以整个换掉 context、换模型、换思考档位,返回 undefined 表示不动),再调 `shouldStopAfterTurn`(返回 true 就 emit `agent_end` 并 return,**两个队列都不拉**)。**次序不能反**:`prepareNextTurn` 拿到的是「刚跑完这一轮」的现场,而 `shouldStopAfterTurn` 的入参 context 是替换后的那份 —— 判断该不该停要看新 context 的大小。桌面端的自动压缩正是靠这一对:在 `prepareNextTurn` 里换上压缩后的 context,而不是在下一次请求里临时裁剪。注意 `transformContext` 的返回值**只喂给本次请求、不写回 context**,想让裁剪持久生效必须走 `prepareNextTurn`。另外 `thinkingLevel` 为 `"off"` 时会把 `config.reasoning` 整个置 undefined,也就是把 reasoning 从请求选项里摘掉。

**CustomAgentMessages(声明合并)**
`AgentMessage = pi-ai 的 Message ∪ CustomAgentMessages 的所有值类型`。`CustomAgentMessages` 是一个默认为空的 interface,应用侧用 `declare module` 往里塞字段,联合类型就全局变宽了。本仓在 `harness/messages.ts` 注册了四个:`bashExecution` / `custom` / `branchSummary` / `compactionSummary`。它们进 transcript、进会话文件、进 UI,但在 LLM 边界由 `convertToLlm` 投影成 user 消息或直接过滤掉。好处是自定义消息不需要包一层 wrapper 就能与原生消息同列;代价有两个:任何拿 `AgentMessage` 做 switch 的地方都必须有 default 分支;而且**只 import 类型也会触发合并**,于是「AgentMessage 到底有哪几个 role」取决于哪些模块被编译进来。

### 第三组:会话外壳与会话树

**harness 与裸 loop 的关系**
`agent-loop.ts` 提供两个无状态纯函数:`runAgentLoop(prompts, context, config, emit, signal, streamFn)` 从一批新消息开跑,`runAgentLoopContinue(context, ...)` 从已有上下文的最后一条可续消息接着跑。多轮循环、工具批执行、队列轮询全在 loop 内部。harness **不重写这些**,而是通过 `AgentLoopConfig` 的六个回调把手伸进 loop:`transformContext` / `beforeToolCall` / `afterToolCall` / `prepareNextTurn` / `getSteeringMessages` / `getFollowUpMessages`。核实结论:harness 全类里没有任何 while/for 驱动轮次的代码,`runAgentLoop` 只在 `executeTurn` 里被调一次,`runAgentLoopContinue` 只在 `retryLastTurn` 里被调一次。

**turn 快照(turn state)**
进入一轮时由 `createTurnState()` 冻结的一份 `{messages, resources, streamOptions, sessionId, systemPrompt, model, thinkingLevel, tools, activeTools}`。**本轮所有 provider 请求只读它。** setter(`setModel` / `setThinkingLevel` / `setTools` / …)改的是 harness 配置字段,不动快照 —— 所以「说话中途换模型」这一轮不生效,要到下一个 save point 由 `prepareNextTurn` 重建快照才被看见。这是「turn 快照冻结」这条不变式的全部实现。

**相位机(phase machine)与 busy 语义**
`phase ∈ {idle, turn, compaction, branch_summary, retry}`。`prompt` / `skill` / `promptFromTemplate` / `retryLastTurn` / `compact` / `navigateTree` 六个方法开头都是**同步的** `if (this.phase !== "idle") throw busy` —— 在第一个 await 之前生效,这就是「相位机而非锁」的意思:忙的时候确定性抛错,**绝不排队**。反向的两个:`steer()` 和 `followUp()` 要求 phase **不是** idle(idle 时抛 invalid_state),而 `nextTurn()` 任何相位都能排。phase 回到 idle 有两条路:正常路径由 `handleAgentEvent` 处理 `agent_end` 时置位,异常路径由各入口的 catch 块置位。

**挂起写入(pending session writes)**
idle 时 setter 直写 session,非 idle 时 push 进 FIFO 队列,由 `flushPendingSessionWrites()` 在三个点(turn_end / agent_end / prepareNextTurn)加上 `runLoopToCompletion` 的 finally 排空。flush 是「peek 队头 → 写成功 → 才 shift」,失败的写留在队头,队列不会烂在半路。这个队列同时也是**「同一时刻只有一个写者」的唯一保证** —— 直接用 `Session` 的调用方需要自己保证串行。

**emitOwn / emitAny / emitHook**
三个私有分发器共用一张 `handlers: Map<string, Set<handler>>`。`emitHook` 按 `event.type` 取桶、依次 await、最后一个非 undefined 的返回值胜出(这是 `on()` 注册的类型化 hook,**返回值被消费、能改行为**,共 6 种活的:context / tool_call / tool_result / before_agent_start / session_before_compact / session_before_tree);`emitAny` 只遍历 `"*"` 桶(`subscribe()` 注册的通配 listener,纯观察);`emitOwn` 本意是发 harness 自有事件 —— **但它的函数体与 `emitAny` 逐字节相同**,也就是说凡是走 emitOwn 发的 **11 种**事件,用 `on(type, handler)` 注册的 handler **永远不会被调用**。这就是「内核事件只能用 `subscribe()`」这条纪律的物理原因。另有 `before_provider_request` / `before_provider_payload` 两个 hook 不走 emitHook 而各有专用方法,它们是活的。

**会话树(session tree)与条目(entry)**
会话不是消息数组,而是一棵树。每个节点是一条条目,统一带 `{type, id, parentId, timestamp}`,`parentId === null` 的是根。11 种条目类型:`message` / `custom_message` / `compaction` / `branch_summary` / `model_change` / `thinking_level_change` / `active_tools_change` / `label` / `session_info` / `custom` / `leaf`。关键设计是**一切皆条目、只追加、永不删改** —— 换模型是一条条目,压缩是一条条目,打标签是一条条目,连「把光标挪到别处」本身也是一条 `leaf` 条目。于是整个会话就是一份纯追加日志,树只是这份日志里 `parentId` 指针拉出来的形状。

**leaf 光标与「追加即前进」**
树上有唯一一个游标 `leafId` 指向当前对话的末端。「当前对话」= `getPathToRoot(leafId)`,从 leaf 沿 `parentId` 一路走到根;其余分支仍在文件里、只是不在这条路径上。每个 `append*` 都做同一件事:`id = createEntryId()`、`parentId = 当前 leafId`,写完新条目自动成为新 leaf。所以顺序对话就是一条直链。**分支只在一种情况下产生:`moveTo(entryId)` 把 leaf 挪到树中间的某个旧条目上**,此后再 append,新条目就挂在那个旧条目下,原来那条尾巴变成另一条分支 —— 一条都没被删。

**leaf 条目:把光标本身也写成数据**
`setLeafId(x)` 不是改内存变量,而是**追加一条 `{type:"leaf", targetId:x}` 条目**。原因只有一个:JSONL 是追加日志,重开文件要靠逐行重放恢复光标,如果光标只活在内存里,重开就永远回到「最后一条条目」而不是用户上次真正停留的位置。重放规则就是 `leafIdAfterEntry`:普通条目让 leaf 指向自己,`leaf` 条目让 leaf 指向它的 `targetId`。有个反直觉推论:`leaf` 条目虽然进了 `entries` 和 `byId`,却**永远不会出现在任何一条 `getPathToRoot` 路径里** —— 它是纯粹的日志侧枝。

**投影(projection)不是历史**
整套代码里最重要的一条咒语,后面会反复出现。压缩不删任何东西:`appendCompaction` 只是往树上追加一条 `{summary, firstKeptEntryId, tokensBefore}` 条目。真正「变短」发生在**读的时候**:`defaultContextEntryTransform` 找出路径上**最后一个** compaction,把结果重排成 `[compaction 摘要, firstKeptEntryId..compaction 之间, compaction 之后的一切]`。文件里原文一字不少,回放、导出、往上翻都看得到。同理 `retryLastTurn()` 摘掉尾部的 error 消息也是「改的是投影,不是历史」。这条设计还有一个漂亮的副作用:`deriveSessionContextState` 扫的是**完整**路径,所以被压掉那段里的 `model_change` 依然生效。

**Repo / Storage 两层抽象**
`SessionStorage` 管「一个会话怎么读写」(getMetadata / getLeafId / setLeafId / createEntryId / appendEntry / getEntry / findEntries / getLabel / getPathToRoot / getEntries),`SessionRepo` 管「一堆会话怎么建/列/开/删/fork」。两层都各有 JSONL(落盘,生产用)与 InMemory(测试/浏览器用)两套实现,接口完全一致。收益很实在:`Session` 类只依赖 `SessionStorage` 一个接口,树的语义(谁当谁的父、什么时候推进 leaf)只写一遍就同时适用于内存和磁盘;而 `JsonlSessionStorage` 只依赖 `FileSystem` 的 4 个方法(readTextFile / readTextLines / writeFile / appendFile),窄到可以被任何环境实现。

**JSONL 追加日志格式**
一个会话 = 一个 `.jsonl` 文件。第一行是 header(`{type:"session", version:3, id, timestamp, cwd, parentSession?, metadata?}`),由 `create()` 用 `writeFile` 写下,是这个文件生命中**唯一一次覆盖写**。之后每条条目 `JSON.stringify` 成一行 `appendFile`,永不回头改。三个好处:写入 O(1) 且不需要读全文、崩溃时最多丢最后一条、`list()` 只读第一行(`readTextLines({maxLines:1})`)就能列出所有会话的元数据。

**fork 与 LCA(最深公共祖先)**
`repo.fork(source, {entryId, position})` 建一个新会话文件,把源会话的一段条目重放进去,`parentSession` 记下源文件路径。`position:"at"` 含目标条目本身,默认的 `"before"` 表示「回到发这句话之前」,因此**强制要求目标是一条 user 消息**,取的是 `target.parentId`。而 `navigateTree` 把 leaf 挪走时,被抛下的那条分支不会消失但会离开投影,所以 `collectEntriesForBranchSummary` 先求旧 leaf 路径与目标路径的**最深公共祖先**,把从旧 leaf 到 LCA 这段收集出来做成摘要,挂在新 leaf 下面。

**ExecutionEnv 的「永不 throw」契约**
`FileSystem`(17 个文件操作)+ `Shell`(exec / cleanup)= `ExecutionEnv`。每一个方法都返回 `Promise<Result<T, FileError|ExecutionError>>`,**实现方不许抛异常、不许 reject**,连意外的后端错误也要接住转成 Result。`NodeExecutionEnv` 用 `toFileError` 把 Node 的 errno 映射成后端无关的错误码(ENOENT→not_found、EACCES/EPERM→permission_denied、EISDIR→is_directory、ABORT_ERR→aborted…)。这么设计是为了让工具层可以无脑 `if (!result.ok) return 错误结果给模型`,而不必到处 try/catch;也让「换一个远程/沙箱后端」在类型上是可能的。

### 第四组:上下文管理(压缩、技能、截断)

**token 估算三件套**
`estimateTokens(message)` 是**单条消息**的字符启发式(各类 content 的字符数相加再除以 4,图片按固定 4800 字符 ≈ 1200 token 计);`calculateContextTokens(usage)` 是**provider 报的权威值**(优先 `usage.totalTokens`,没有就四项相加);`estimateContextTokens(messages)` 是给整段上下文用的**混合算法** —— 倒着找最后一条**有效** assistant 消息的 usage 当基准,再对它之后新增的消息(工具结果、下一条 user)逐条估算,两者相加。返回值还带 `lastUsageIndex`,应用层靠它判断「有没有真实 usage」。

**为什么优先用真实 usage**
字符除以 4 是个很粗的近似,它看不见系统提示词、工具 schema、缓存写入这些同样占窗口的东西,通常严重低估。`getAssistantUsage` 还做了三重过滤:stopReason 是 aborted 或 error 的消息不算(那次请求根本没走完,数字不可信)、usage 必须存在、算出来必须 > 0。**缺了这层过滤,一次网络失败就会让估算塌回 0,于是本该压缩的会话一路撑到撞窗口。** 桌面端与 ACP 的自动压缩都据此加了一个 guard:`lastUsageIndex === null` 时不猜、不压。

**合法切点(valid cut point)与孤儿工具结果**
压缩的切点只能落在「用户可见的消息条目」上:user / assistant / bashExecution / custom / branchSummary / compactionSummary 这几种 role,外加 branch_summary 与 custom_message 两种条目类型。**`toolResult` 被显式排除** —— 切在它前面会让上一条 assistant 的 toolCall 失去应答,provider 收到孤儿工具结果会直接拒收整个请求。这是 `findValidCutPoints` 存在的全部理由,也是压缩里最容易写错、错了以后表现为「压完就再也发不出去」的一处。

**split turn:切在一轮中间要两次摘要**
理想情况下切点落在一条 user 消息上 —— 那就是干净的轮边界。但当最近一轮本身就超过 `keepRecentTokens`(20000,一条 user 指令后面跟着几十个工具往返,在长调试里很常见),切点只能落在这一轮中间。这时 `findTurnStartIndex` 往回找到轮起点,把 [轮起点, 切点) 这段单独拿出来,用另一份提示词做一份「前缀摘要」(预算是 reserveTokens 的 0.5,而历史摘要是 0.8),再和历史摘要用 `---` 拼起来。目的是让被保留的后半段不至于「不知道自己在回答什么问题」。

**更新式摘要(previousSummary)与文件清单继承**
连续压缩最大的风险是逐次遗忘。两处对策:(1)`prepareCompaction` 把上一条 compaction 的 summary 取出来当 `previousSummary`,`generateSummary` 检测到它就改用 UPDATE 提示词(明确要求 PRESERVE 既有信息、把 In Progress 挪进 Done),而不是重新总结一遍;(2)`extractFileOperations` 把上一条 compaction 的 `details.readFiles/modifiedFiles` 继承进本次的累加器。少了任何一样,压第三次的时候模型就不知道自己两小时前改过哪些文件了。

**分支摘要(branch summary)vs 普通压缩**
两者都是「把一段对话换成一份摘要」,但触发时机与目的完全不同。压缩是**纵向**的:同一条路径上历史太长,把靠前的一段换成摘要,目的是省窗口。分支摘要是**横向**的:`navigateTree` 把 leaf 移到树上另一处时,原来那条分支整个离开投影,先给它做份摘要挂在新 leaf 下,目的是让模型知道「你刚才在另一条路上探索过什么」。实现上三处差异:用 LCA 界定范围而不是 token 预算切点;**完全丢弃 toolResult**(离开了配对的 toolCall 就没意义);输出上限硬编码 2048,并在摘要前面加一段说明这是「用户探索过的另一条分支」。

**截断:两个上限、两个方向、三种形态**
共享上限是 **2000 行 / 50KB**,谁先撞到谁生效。`truncateHead` 留**头**给 read 工具(你读文件想看开头),保证**永不返回半行**;如果第一行本身就超过字节上限,它返回空内容并置 `firstLineExceedsLimit`,由调用方给模型一句 `sed -n 'Np' file | head -c 51200` 的兜底建议。`truncateTail` 留**尾**给 bash(命令的错误和最终结果都在结尾),是**唯一允许返回半行**的地方(从后往前按字符退,绝不在多字节字符中间切开,切出来的孤立代理项换成 U+FFFD)。超限时全量旁落临时文件,结果里带 `fullOutputPath` 让模型自己去回查 —— **截断必须标注,裸截断是「自信地错」**,比可见地错糟得多。

**技能(skill)的两级注入**
技能不是一次性全灌进上下文的。第一级是**列表**:每轮系统提示词里 `formatSkillsForSystemPrompt` 只放 name / description / location 三样(并做 XML 转义、过滤掉 `disableModelInvocation` 的),外加一句「任务匹配描述时去读全文」。第二级是**全文**:模型自己判断该用哪个,用 read 工具去读那个路径;或者应用调 `harness.skill(name)`,由 `formatSkillInvocation` 把 SKILL.md 正文包成 `<skill>` 块当作用户消息发出去,走的是和普通 prompt 完全一样的 `executeTurn`。**这个两级设计是技能能做得很长而不炸窗口的原因。** 技能与上下文文件都是**建会话时读一次的快照**,不做热重载:改了技能文件要重开会话。

**技能发现的目录约定**
内核只给机制(递归遍历、frontmatter 解析、`.gitignore` 系列 ignore 规则、符号链接解引用),「从哪些目录找」是应用层策略,落在 `coding-agent/src/core/resources.ts` 的 `skillDirsOf`:`<globalDir>/skills`(默认 `~/.my-pi`)与 `<cwd>/.agents/skills`,后者与 pi / Claude Code 共享;**后加载的同名技能覆盖先加载的**(项目技能压过全局技能)。遍历规则:某个目录里只要有 `SKILL.md`,这个目录整体就是**一个**技能不再往下递归;根目录下的散装 `.md` 也各算一个。frontmatter 认三个字段,其中 **`description` 是唯一硬性要求** —— 缺了会被静默丢弃,表现是「我明明放了技能却看不见」。

**上下文文件(AGENTS.md)的发现顺序**
`loadContextFiles` 先在全局目录按 `AGENTS.override.md → AGENTS.md → AGENTS.MD → CLAUDE.md → CLAUDE.MD` 找第一个读得出来的,再从 cwd 一路 `dirname` 走到文件系统根、每层一份,最后反转成「最外层祖先 → … → cwd」。**越具体越靠后,离指令越近权重越高。** 两道去重:canonicalPath(大小写不敏感文件系统上 AGENTS.md 和 AGENTS.MD 是同一个文件)与**内容全等**(git worktree 里主仓与检出副本各有一份同内容 AGENTS.md)。全程不抛错 —— 资源是锦上添花,不能让建会话失败。

### 第五组:工具层

**ToolDefinition vs AgentTool(两层工具形状)**
pi-ai 的 `Tool` 只有 name / description / parameters(给 LLM 发请求用);my-pi 的 `AgentTool` 在它之上加 label / prepareArguments / executionMode / execute(内核运行时契约);coding-agent 的 `ToolDefinition` 再加 `promptSnippet`(系统提示词里的一句话摘要)与 `promptGuidelines`(追加的使用守则)。`wrapToolDefinition` 做的就是「丢掉提示词元数据,交出 `AgentTool`」。**收益:「工具能干什么」和「提示词里怎么描述它」是同一处真源** —— `collectToolPromptData` 从工具定义反推出提示词的三段(名字清单、单行摘要、使用守则),不存在第二份手写清单会漂移。顺带一提:上游 pi 的 ToolDefinition 还带 TUI 渲染器,my-pi 整类砍掉了,因为渲染信息要经协议传给 Zed 与桌面端,靠的是结构化的 `details` 而不是终端字符串。

**能力接口注入(capability injection)**
工具工厂收的第一个参数是 `FileSystem` 或 `ExecutionEnv` 而不是 cwd 字符串,cwd 从 `env.cwd` 拿。所有文件与进程访问都走注入的接口,**不直接 `import node:fs`**。这使同一套工具可以跑在本机、远程或沙箱文件系统上。代价是工具代码里到处要把 `!r.ok` 翻译成给模型看的 Error 文案。上游 pi 用三套可插拔接口(ReadOperations / WriteOperations / BashOperations)达成同样目的,my-pi 用一个能力接口一次覆盖。

**edit 的匹配策略:精确优先、全局唯一、批内不重叠**
`fuzzyFindText` 先 `content.indexOf(oldText)` 精确匹配,失败才把双方都过一遍 `normalizeForFuzzyMatch`(NFKC、逐行 trimEnd、弯引号/破折号/特殊空格折叠)再找。**只要有任意一个 edit 用了模糊匹配,整批就切到模糊空间里做**,最后用 `applyReplacementsPreservingUnchangedLines` 把行级改动叠回原文,让没动过的行保留原始字节。三条安全性质按顺序检查:空 oldText 报错 → 找不到报错 → **出现多处报错**(要求模型给更多上下文);匹配完再按 matchIndex 排序查区间重叠。最后所有替换**倒序应用**,偏移量才不会被前面的替换挪动。整个过程还要保住行尾与 BOM:读进来先 `stripBom` + `detectLineEnding` + `normalizeToLF`,写回前 `restoreLineEndings` 再加回 BOM。

**文件修改队列(file mutation queue)**
同一文件的修改串行化(不同文件仍并行),用模块级 `Map<canonicalPath, Promise>` 做每文件锁链,外加一条 registrationQueue 让「取键 + 挂链」这一步本身也串行。它和 `executionMode: "sequential"` 是**两道独立的防线**:后者管同一批工具调用,前者管同一进程内任何来源的并发(先读后写之间被别人插进来覆盖)。read 工具**不进**这个队列(那条因果对它不成立),所以它可能读到一次并发写的中间态。

**杀进程树而不是杀 shell**
`env.exec` 起的是一个 bash,而模型的命令里常常是 `npm run dev`、`cmake --build`、`openocd` 这类会再 fork 的东西。只杀 bash 会留下一堆孙进程 —— 在这个产品里的具体代价是「**孤儿 gdbserver 攥着探针不放,而报错长得和没插板子一模一样**」。所以 POSIX 下 spawn 带 `detached: true` 让子进程自成进程组,击杀时 `process.kill(-pid, 'SIGKILL')` 一锅端(失败再退回杀单个 pid);Windows 没有进程组,改用 `taskkill /F /T /PID`。超时、abort、以及 stdout/stderr 回调抛错三种情况走的都是同一个 `killProcessTree`。

**串口的 termios 属于设备而不是 fd**
流传甚广的 `stty … && cat …` 是**错的**:termios 设置属于 tty 设备,最后一个 fd 关闭时驱动会把它复位。实测(macOS + ST-Link VCP)`stty -f /dev/cu.usbmodem 921600` 之后立刻回读就是 `speed 9600`,而症状是整屏乱码 —— **看起来像固件坏了**。所以 `prepareSerial` 的顺序是:非阻塞 + `O_NOCTTY` 开第一个 fd → `stty` 走 **stdin**(「设置 stdin 的 tty」是 POSIX 规定行为,而 `-f`/`-F` 两个系统拼写不同)→ 趁第一个 fd 还开着开第二个阻塞 fd → 才关第一个。设备一刻没关过,配置就不会被复位。另外 `O_NOCTTY` 是必需的:`detached` 会 setsid,session leader 自己 open 一个不带 `O_NOCTTY` 的 tty 会让它成为控制终端,**这样的进程收到 SIGTERM 不会死**。

### 第六组:嵌入式与产品层

**探针租约(probe lease)与两层锁**
一个调试探针同一时间只能被一个进程握住。`engines.ts` 用一个**模块级变量**记进程内谁在用,再往 `~/.my-pi/probe.lock` 写一份 `{pid, owner, label, since}` 让跨进程也能说清占用者。`claimProbe(owner, label, isLive?)` 的返回值是**反直觉的:成功返回 undefined,冲突返回当前持有者**。`isLive` 回调是必需的 —— 采集子进程可能自己死了而 stop 从未被调用,没有它后来的人会撞上一个早就没人要的租约。`releaseProbe(owner)` 只在 owner 匹配时生效,避免 A 的清理路径误放 B 的锁。**推论:分片 fork 内核进程会让两个进程各自以为独占探针**(进程内那一半是模块级的),所以桌面端只 fork 一个内核进程。

**「探针被占」不能报成「板子没插」**
烧录器和调试服务器把「被别的进程占着」和「没插板子」打成几乎一样的非零退出(典型是 `0xe00002c5` / `exclusive access` / `open failed`)。模型看到这种字符串最顺手的下一步是让用户去查 USB 线,而线是好的 —— 是 agent 自己的另一个工具占着。这就是 `describeProbeConflict` / `probeFailedHint` 存在的唯一理由,也是一条通用纪律:**错误信息必须指向下一步动作**。

**退出码策略留在调用方**
`runEngine` 只负责跑和收,`assertEngineSettled` 只把**超时/中断**当异常;非零退出码是什么意思由每个工具自己说了算,因为答案完全不同:`stm32kernel` exit 1 = 有 ERROR 诊断(是修复回路的正常一步,stdout 上的 JSON 就是要读的东西);flash 的烧录器非零 = 多半没插板子(也是正常结果,要连提示一起返回给模型);`controller_map` / `board_ir` 非零才是真失败(直接抛)。把退出码策略折进公共层正是文件头注释在防的事。

**MI3 协议的三个反直觉之处**
gdb 的 Machine Interface 第 3 版有三条实测事实决定了 `gdb.ts` 的骨架:(1)**结果记录在它引起的异步记录之后到**(实测 `*stopped` 先于 `20^connected`),所以等停止的 waiter 必须在**发命令之前**用 `expectStop()` 装好,否则会漏掉已经发生的停止然后一路等到超时;(2)`(gdb) ` 提示符在异步停止之后**不发**,拿它当分帧或派发信号会死锁;(3)一个 token 可能收到两条 `^` 记录(`^running` 之后再来 `^error`),派发必须 resolve-once。于是骨架是两条互不相干的通路:带 token 的 `^` → promise 派发,无 token 的 `*running`/`*stopped` → 目标状态机。

**epoch:复位之后什么都作废**
`GdbSession.epoch` 从 1 开始,在复位、意外停止、重连时 +1。它给模型一个明确的失效信号:目标一旦复位,之前缓存的地址、寄存器值、断点命中计数**全部陈旧**。`exec op:"reset-halt"` 的返回文本会直接写出「session epoch is now N」并说明这一点,banner 也把 epoch 印在每次调用的第一行。

**故障现场分析:替模型做它已知会做错的四件事**
Cortex-M 停在故障处理函数里时 backtrace 是垃圾,真正的现场在异常入栈帧(exception stack frame)里。`analyseFault` 依次做四件模型公认会做错的事:(1)从 EXC_RETURN(异常里的 `$lr`)的 bit 2 判断入栈用的是 MSP 还是 PSP;(2)读栈上那 8 个字里的 PC,而不是 handler 自己的 `$pc`;(3)`BFARVALID`/`MMARVALID` 为 0 时**绝不**返回 BFAR/MMFAR(那是陈旧值,报出去会冤枉无辜代码);(4)`IMPRECISERR`(非精确总线错误)置位时连 PC 都不可信,只能明说而不是给个源码行。另外 `HFSR.FORCED` 不是答案,只是「去看 CFSR」的指针。**这四件事做成纯函数而不是写进提示词让模型自己算。**

**上下文预算:折叠 + 骨架采样 + 单行开窗**
log 工具面对刷屏日志的三道机制。**折叠**:连续完全相同的行 → `×N`;只有数字在变的行(传感器刷屏)→ 首行 + `×N` + 末行,这样数值漂移/饱和仍看得出来。**骨架采样**:超预算时保留「头 5 行(启动信息)+ 中间命中 TRIPWIRE 正则的行(hardfault/panic/assert…,从后往前找)+ 尾部(最新状态)」,断裂处插 `… N lines omitted`。两道预算同时卡 —— 行数管「多」,字符数管「长」,只卡行数拦不住 4KB 一行的设备。**单行开窗**:wait 命中时把命中位置一路交到渲染,否则实测会出现「一边断言匹配了、一边 400 字符全是乱码看不见证据」。

**游标语义:预览不消费证据**
`LogCapture` 有一个 `cursor`(下一次 read 的起点)。规矩是:`read` 不带 pattern 时推游标(消费);带 pattern 时**不推**(它是查询不是消费,否则没匹配上的行会被悄悄跳过);`wait` 只有**命中**才推游标,超时/源退出/中断只给 12 行预览而游标原样保留 —— **证据不能因为看了一眼就消失**。

**ELF 与片子里的镜像对不上(verifyImage)**
整套工具里最贵、而且**没有任何错误文本**的失败:改了代码、重编了、忘了烧,然后问 agent 为什么新逻辑不生效。行号偏几行、调用栈看着合理、变量值看着合理,于是模型写出一份完全自洽、完全虚构的根因分析。防线是 flash 在 exit 0 时把 ELF 的 sha256 记进 `<工程>/.my-pi/flash-state.json`,gdb start 时重算比对:不一致则直接 teardown,要求重烧或显式 `allowUnverified: true`。这是 flash 与 gdb 两个工具之间唯一的持久化契约。

**七/六档探测顺序(toolchain resolve)**
`local(项目覆盖) > ledger(本机账本) > env(清单点名的环境变量) > path(PATH 扫描) > well-known(平台已知安装位置表) > registry(Windows 注册表)`。前四档天然只产出一个候选,后两档同一档内可能产出多个(CubeIDE 内置的 arm-gcc 10.3 和独立装的 13.2 并存)。命中不代表定案:还要 `probeVersion` + `satisfies` 判定版本,不满足就继续往后一档找。同一档多候选版本满足情况不一致时报 **ambiguous,绝不悄悄替用户选一个** —— 悄悄选错的代价是「编得过、炸在很远的地方」。

**toolchainSide(mother / runner)**
mother(研发端)有完整项目检出,cmake / arm-gcc 应有尽有;runner(工位端)只有板子和一次性工作目录,连 git 都没有。`manifestForSide` 按 `tool.side ?? "mother"` 筛出这一侧要看的工具子集,并把 providers 表也裁到筛后 tools 还在引用的那些。**不传 `side:"runner"` 的后果**:工位端会把 mother 侧的工具全部拿去探测然后全部 MISSING,把真正缺的那条信息淹没在噪音里;而且系统提示词里是筛过的清单、agent 自己跑 `toolchain check` 却用默认 mother + 真实 `~/.my-pi` + 磁盘清单去答,两边自相矛盾(实测踩过)。清单本身经信箱原样复制、由 `TurnInput.toolchainManifestText` 灌进内核。

**硬过滤 vs 软打分(examples 检索)**
芯片(target)与生态(ecosystem)是**硬约束**,不满足直接排除,绝不进入打分环节 —— 因为它们回答的是「物理是否可用」这个是非问题,STM32 例程永远不该出现在 ESP32 需求的候选列表里,不管语义描述多相似。板名、关键词是**软偏好**,只加分不排除(官方例程钉在官方开发板,用户的板子大概率不同)。`targets` 为空数组是「元数据缺失」不是「不支持」,不排除但在结果里明说 —— 同一条原则也体现在「可读」与「可作底盘」是两个不同承诺上。

**缓存文件的三条纪律**
(1)configDir 类文件是**本机事实的缓存**,读不出来当空/当没有、**绝不抛异常**(重建代价最多是重新探测/重新索引一遍);(2)落盘一律「写临时文件 + rename」**原子写**,rename 到同目录已存在的文件名是文件系统提供的原子替换,半个 JSON 永远不会以最终文件名出现在磁盘上;(3)**逐条容错**,坏一条丢一条,不连累整份文件。临时文件名带 pid + 随机数而不是固定的 `.tmp`,是为了让并发的两次写各自完整落地。**唯一例外是会话 JSONL** —— 那是历史不是缓存,坏一行整个 `open()` 失败(见 §7)。

**富化(enrich)是旁挂缓存,不是索引本体**
索引(`index/<slug>.jsonl`)是脚本秒级可重建的机械抽取产物;富化(`enrich/<slug>.jsonl`)是花过钱的模型产物(LLM 读源码写的资源足迹卡片:引脚/外设实例/链接期符号/任务优先级)。**分开落盘的理由是「重建索引不许把富化冲掉」。** 读侧靠 `(id, commit)` 合流:富化记录的 commit 与当前索引 header 不一致就按陈旧跳过,同 id 多条取最后一条(重富化 = 再追加一行)。「逐行自描述、没有文件头、只追加」的 JSONL 纪律让断点续跑天然成立。

**模型输出必须净化才能落盘**
LLM 的输出不可信,必须过一遍确定性代码校验/裁剪才能进入系统的持久状态。`sanitizeEnrichmentCard` 对 `summaryZh` 缺失整卡拒收,其余字段限长度限数量,`instances`/`symbols` 这些「冲突比对键」强制只收 `\w+` 标识符 —— 挡住模型把提示词示例散文照抄进结构化字段(真实踩坑:预检拿两段中文互相「撞车」)。`generic.ts` 则是「模型提议路径,代码核验存在性」:path 必须 `existsSync` 验证过、loc/files 由代码实测而非模型自报、`buildable` 恒 false。

### 第七组:宿主与协议

**ACP(Agent Client Protocol,智能体-客户端协议)**
Zed 提出的编辑器 ↔ 编码 agent 协议:编辑器把 agent 当**子进程** spawn,双方在 stdin/stdout 上跑 **JSON-RPC**,分帧方式是 **ndjson**(一行一个 JSON 对象)。client → agent 是 6 个请求(`initialize` / `authenticate` / `session/new` / `session/load` / `session/prompt` / `session/set_config_option` / `session/set_mode`)加一条通知(`session/cancel`);agent → client 主要是**一条**通知 `session/update`。本仓用 `@agentclientprotocol/sdk` 1.3.0,`PROTOCOL_VERSION = 1`,声明的能力只有 `loadSession: true`。**stdout 是协议通道 —— 任何一个 `console.log` 的字节都会插进 ndjson 流里毁掉分帧**(表现是 Zed 侧莫名断线,而不是报错),所以 `acp.ts` 第一件事就是把 console 改道到 stderr,调试一律 tail `~/.my-pi/acp.log`。

**session/update:唯一的上行通道**
agent 往编辑器推的东西几乎全部挤在这一条通知里,靠 `update.sessionUpdate` 这个判别字段分流:`agent_message_chunk`(助手文本)、`agent_thought_chunk`(思考)、`user_message_chunk`(重放用户消息)、`tool_call`(新工具卡片)、`tool_call_update`(卡片状态/内容更新)、`available_commands_update`(斜杠命令清单)、`config_option_update` / `current_mode_update`(下拉框)。适配器里所有往上推的动作都收敛成一个 `UpdateSink` 类型 —— `(update) => Promise<void>`。

**live 路径 vs replay 路径**
同一段对话有两条产出更新的路:**live** 消费 harness 的流式事件(`text_delta` 一个 token 一条),**replay** 消费已落盘会话树投影出来的整条消息。两者数据源不同(`event.*` vs `block.*`),所以天然容易漂移 —— 历史上就漂过一次(图片块只在重放时可见)。现在 ACP 把两条路共用的 update 构造收敛成 `toolCallStart` / `toolCallEnd` 两个函数,并有专门的测试钉住 live 路径也能透传图片;桌面端投影器更彻底,live 与 replay 共用同一个 `applyMessage()`。残余的行为差异有三处:replay 不为历史 error 消息补 ⚠️ 文本、replay 没有 `in_progress` 中间态、live 从不发 `user_message_chunk`。

**configOptions 与 modes**
SDK 1.3.0 里没有 `models` 字段、也没有 `session/set_model`,所以 Zed 的模型下拉框和 thinking 下拉框全部由 `session/new` / `session/load` 响应里的 `configOptions` 渲染。适配器同时还发一份 `modes`(currentModeId + availableModes),这是双保险:客户端会二选一渲染,不会画出两个 thinking 选择器。两条路最终都落到 `harness.setThinkingLevel()`。两个 config id 字符串(`"model"` / `"thought_level"`)就是 Zed settings.json 里 `default_config_options` 的键,**改名会让用户配的默认值静默失效**。

**内核只给机制,策略留给应用层**
`compact()` / `retryLastTurn()` / `navigateTree()` 都只是**机制**:什么时候压、重试几次、退避多久,harness 一概不管。桌面端的 `kernel/src/host/compaction.ts`、`kernel/src/host/retry.ts` 与 ACP 的 `acp/agent.ts` 各有一份**同构的第二实现**(重试 3 次 / 2s 起指数退避;压缩的两个 guard:没有真实 usage 不猜、刚压完不重压),**数值必须同步**。刻意重复而不 import 的理由:后者会把整个 ACP 与 SDK 拖进桌面端 bundle。

**善后动作(post-turn housekeeping)**
自动重试和自动压缩都被明确定义为「善后」:它们自身失败只往 transcript 里写一条 ⚠️ 文本,**绝不让这一轮 prompt 失败** —— 用户已经拿到的回答不该被一次压缩异常连坐废掉。两者都必须在 **resolve 路径**上判(不是 catch 路径),因为中断和错误在内核里都是数据不是异常;而且每做完一件要重查一次 `signal.aborted`,用户刚按了停止就不该紧接着又发起新的模型调用。

**faux provider(假模型)**
`ai/src/providers/faux.ts` 不发网络请求,而是把测试代码预先 `setResponses()` 摆好的 `AssistantMessage` 队列取出来,按随机 tokenSize / tokensPerSecond 切块、按延迟逐块 push 成 `start` / `*_delta` / `done` 事件,行为和真实流式响应在事件形状上一致,连 abort 中断与 prompt-cache 命中(按上下文文本公共前缀长度算 cacheRead/cacheWrite)都模拟了。桌面端的 `smoke:mailbox` 与 bench 的 mailbox sim 就是靠它在**零 key 零硬件**下把整条信箱闭环协议跑一遍。

**deferred tools(延迟加载的工具)**
工具表很大时,把全部定义塞进每一轮请求既贵又占缓存。`splitDeferredTools` 扫历史:凡是通过某条 toolResult 的 `addedToolNames` 才出现、且至今没被调用过的工具归入 deferred,其余归 immediate。Anthropic 侧 deferred 工具照样列在 `tools` 里但带 `defer_loading: true`,并在那条 toolResult 的位置插 `tool_reference` 块;OpenAI Responses 侧插一对伪造的检索项。判定完全基于 `addedToolNames` 字段,上游没维护好的话机制会**悄悄失效但不报错**。

### 阶段 1:进入内核(同步守卫 + 冻结快照)

1. **相位守卫。** `harness.prompt(text, {images})` 的第一件事是**同步**检查 `this.phase !== "idle"` 就抛 `AgentHarnessError("busy")`。这一步在第一个 `await` 之前生效 —— 同一个微任务里连发两次 prompt,第二次必定同步炸,不会排队。
   `agent-harness.ts:prompt` **:660**
2. **置相位 + 建 runPromise。** `phase = "turn"`,`startRunPromise()` 建一个可被 `waitForIdle()` await 的 Promise。
   `agent-harness.ts:startRunPromise`
3. **冻结 turn 快照。** `createTurnState()`:调 `session.buildContext()` 拿经压缩投影后的 messages;复制资源数组;取 sessionId;把 tools Map 摊成数组、按 `activeToolNames` 过滤出 activeTools;解析 systemPrompt(字符串直用,函数则带 env/session/model/thinkingLevel/activeTools/resources 调一次);`streamOptions` 深拷一层。
   `agent-harness.ts:createTurnState` **:335**
   - 3a. `session.getBranch()` → `storage.getLeafId()` → `storage.getPathToRoot(leafId)`,拿到 root→leaf 的条目数组。
     `session/session.ts` / `session/jsonl-storage.ts`
   - 3b. `deriveSessionContextState()` 顺序扫**完整路径**推导 model / thinkingLevel / activeToolNames(后写覆盖先写)。
   - 3c. `defaultContextEntryTransform()` 找出路径上**最后一个** compaction,重排成 `[摘要, firstKeptEntryId..compaction 之间, compaction 之后一切]` —— 这就是「压缩只改投影」的兑现处。
   - 3d. `flatMap(sessionEntryToContextMessages)` 把条目映射成 `AgentMessage[]`:`message` 直出,`custom_message`/`compaction`/`branch_summary` 走 `messages.ts` 的三个构造器,配置类条目返回 `[]`。
4. **组装首批消息。** `executeTurn` 先 `createUserMessage(text, images)`;若 `nextTurnQueue` 非空则整队 splice 出来**前置**在用户消息之前。
   `agent-harness.ts:executeTurn` **:564**
5. **before_agent_start hook。** hook 返回的 messages 追加在**后面**,返回的 systemPrompt 可覆盖本轮系统提示词。
   `agent-harness.ts:580`(经 `emitHook`)
6. **建 AbortController 并存进 `this.runAbortController`。**
   `agent-harness.ts:runLoopToCompletion` **:598**
   > 这里有一个窗口:`runAbortController` 到这一步才赋值,而第 3 步的 `createTurnState()` 会做 session I/O。abort 恰好落在这个窗口时什么也打断不了。
7. **把 harness 的手伸进 loop。** `createLoopConfig()` 把六个回调接上:`transformContext`→`emitHook("context")`、`beforeToolCall`→`emitHook("tool_call")`(可 block)、`afterToolCall`→`emitHook("tool_result")`、`prepareNextTurn`→重建快照、`getSteeringMessages`/`getFollowUpMessages`→`drainQueuedMessages`。`reasoning` 字段也在这里落定:`thinkingLevel === "off"` 时传 **undefined**。
   `agent-harness.ts:createLoopConfig` **:422**
8. **包出 StreamFn。** `createStreamFn()` 在每次 provider 调用前跑 `before_provider_request` hook(可返回 streamOptions 补丁,用 `Object.hasOwn` 区分「没提供」与「显式 undefined = 清空」),`onPayload` 接 `before_provider_payload`,`onResponse` 接 `after_provider_response`。
   `agent-harness.ts:createStreamFn` **:381**
   > `streamFn` **不在 `AgentLoopConfig` 里**,它是 `runAgentLoop` 的第 6 个参数。
9. **进循环。** `runAgentLoop(messages, context, config, event => handleAgentEvent(event, signal), signal, streamFn)`。
   `agent-loop.ts:runAgentLoop`

### 阶段 2:循环开局

10. `runAgentLoop` 建两个数组:`newMessages = [...prompts]`(将来返回给调用方)和 `currentContext = {...context, messages: [...context.messages, ...prompts]}`(**新数组**;注意 `runAgentLoopContinue` 用的是 `{...context}`,messages 数组**没有复制**,两个入口的所有权语义不对称)。
    `agent-loop.ts:runAgentLoop`

    `agent-loop.ts` → `agent-harness.ts:handleAgentEvent` **:517**

### 阶段 3:发一次请求

14. **transformContext。** 先跑 `config.transformContext`(harness 转成 `context` hook),**返回值只喂给本次请求的局部变量,不写回 `context.messages`**。
    `agent-loop.ts:streamAssistantResponse` **:266**
15. **过 LLM 边界。** `config.convertToLlm(messages)` 把 `AgentMessage[]` 投影成 pi-ai 的 `Message[]`:`bashExecution` 渲染成 markdown 代码块包 user 消息(`excludeFromContext` 为真则直接丢弃,这是唯一「进 transcript 不进 LLM」的角色)、`custom` 包成 user 消息(**`display` 字段被忽略**)、两种摘要拼上各自的 PREFIX/SUFFIX、user/assistant/toolResult 原样通过、其余 default 分支返回 undefined 被过滤掉。
    `agent/src/harness/messages.ts:convertToLlm` **:124**
16. **拼 Context 并解析 apiKey。** `{systemPrompt, messages: llmMessages, tools}`;apiKey 解析 `config.getApiKey(provider)` 优先于 `config.apiKey`。然后调 `streamFn`。
    `agent-loop.ts:streamAssistantResponse`
17. **注册表派发。** `ModelsImpl.streamSimple` **同步**返回一个 `lazyStream(model, setup)` 建的流,异步的 setup 在后面跑:`requireProvider(model)`(按 `model.provider` 查表,查不到抛 `ModelsError("provider")`)。
    `ai/src/models.ts:ModelsImpl.streamSimple` → `ai/src/api/lazy.ts:lazyStream`
18. **解凭据。** `applyAuth()` → `resolveProviderAuth(provider, model, credentials, ctx, {apiKey, env})`:override > 存储凭据(按 `type` 分派;OAuth 分支走双重检查锁刷新 token 并回写)> ambient 环境变量。拿到 auth 后按「显式选项逐字段胜出、headers/env 逐键合并」合成 requestOptions,auth 带 baseUrl 时浅拷一个 requestModel。
    `ai/src/auth/resolve.ts:resolveProviderAuth`
    > setup 里任何 throw 都被 `lazyStream` 的 `.catch` 接住,变成 `stopReason:"error"` 的消息 push 进流 —— **`Models.stream()` 这条路永远不 reject**。
19. **懒加载协议实现。** `provider.streamSimple` → `createProvider` 的 `dispatch()` → `apiFor(model)` 取到 `openAICompletionsApi()` 这个 lazy 包装 → 再次 `lazyStream` → `await import("./openai-completions.ts")` 才真正把 1302 行载入内存(两个 SDK 都不小,静态 import 意味着只配了 DeepSeek 也要把 Anthropic SDK 一起加载)。
    `ai/src/api/openai-completions.lazy.ts` → `ai/src/api/lazy.ts:lazyApi`

    `ai/src/api/openai-completions.ts:streamSimple` → `ai/src/api/simple-options.ts:buildBaseOptions` / `ai/src/models.ts:clampThinkingLevel`

### 阶段 4:流式回程

23. **解析 SSE。** `for await (const chunk of openaiStream)`:`chunk.usage` 走 `parseChunkUsage` 算 token 与费用(`calculateCost` 原地写满 `usage.cost`);`finish_reason` 经 `mapStopReason` 落 `stopReason`;`delta.content` 走 `ensureTextBlock()` 追加并推 `text_delta`;三个 reasoning 字段里第一个非空的走 `ensureThinkingBlock()`(**字段名本身被存进 `thinkingSignature` 以便下一轮原样回填**);`delta.tool_calls` 把 arguments 片段拼进 `partialArgs`,每次都用 `parseStreamingJson()` 整体重解一遍覆盖 `block.arguments`(三级兜底、永不抛,好处是 UI 在参数没吐完时就能显示 `path: "src/ma`)。
    `ai/src/api/openai-completions.ts` + `ai/src/utils/json-parse.ts:parseStreamingJson`
24. **收尾四道闸门。** 流结束后逐块 `finishBlock()` 推 `*_end` 并**删掉 `partialArgs`/`streamIndex` 等临时字段**(它们绝不能进会话历史),然后判:signal 已 abort / stopReason 是 aborted / 是 error / **没收到过 finish_reason**,任一命中就 throw 落进 catch;正常则 `push({type:"done", reason, message: output})` + `end()`。catch 里把异常翻译成 `stopReason: "error"|"aborted"` 的终结事件。

    `agent-loop.ts:streamAssistantResponse`
26. **落盘。** harness 的 `handleAgentEvent` 看到 `message_end` → `session.appendMessage()`(**先落盘再 emitAny**)→ 订阅者(桌面端投影器 / ACP 的 `pipeHarnessToAcp`)拿到事件画 UI。
    `agent-harness.ts:handleAgentEvent` **:517**
27. **早退分支。** 回到 `runLoop`:`newMessages.push(message)`。若 `stopReason` 是 `"error"` 或 `"aborted"`,**立刻 emit `turn_end`(toolResults 空)+ `agent_end` 并 return** —— 不碰任何队列、不执行任何工具。

### 阶段 5:执行工具

28. **筛出 toolCall 块。** 从 `message.content` 里筛。`hasMoreToolCalls` 先置 false。
    `agent-loop.ts:runLoop`
29. **length 分叉。** `stopReason === "length"` 时走 `failToolCallsFromTruncatedMessage`:每个调用照发 `tool_execution_start`,造一条「未执行,参数可能被截断,请重发」的错误结果,`terminate: false`。
    `agent-loop.ts:failToolCallsFromTruncatedMessage`
30. **选执行模式。** `executeToolCalls` 看这一批里有没有 `executionMode === "sequential"` 的工具,有就整批走 `executeToolCallsSequential`,否则走 `executeToolCallsParallel`。
    `agent-loop.ts:executeToolCalls` **:356**
31. **准备参数(串行 await)。** `prepareToolCall`:
    - `tool.prepareArguments(toolCall)` —— 校验之前唯一的入参整形钩子(edit 用它把 JSON 字符串的 edits 解析回数组、把旧的单条 oldText/newText 折进数组);
    - `validateToolArguments(tool, toolCall)` —— `Value.Convert` 强转 + typebox 编译校验;schema 不是 TypeBox 编译产物时(靠 `Symbol.for("TypeBox.Kind")` 探测)再跑一遍自制的 `coerceWithJsonSchema` 递归强转(`"3"`→3、`"true"`→true);失败抛带路径的详细错误。
    `agent-loop.ts:prepareToolCall` → `ai/src/utils/validation.ts:validateToolArguments`
32. **beforeToolCall hook。** 可以 `{block: true}` 挡下这次调用。注意 hook 拿到的 `args` 是**校验后的对象本体**,就地改它**不会重新校验**。
    `agent-harness.ts:436`(`emitHook("tool_call")`)
33. **execute。** `tool.execute(toolCallId, args, signal, onUpdate)` 进到具体工具:
    - **文件三件套** —— `resolveToCwd`(含 MSYS `/d/foo` → `D:/foo` 翻译)→ write/edit 走 `withFileMutationQueue` 按 canonical 路径上锁 → `env.readTextFile` / `env.writeFile` → edit 额外做 BOM/行尾归一化、`fuzzyFindText`、倒序应用、生成 unified patch;
    - **bash** —— `executeShellWithCapture(env, cmd, {timeout: timeout ?? 120, abortSignal, onChunk})` → `env.exec` → `getShellConfig` 找 bash → `spawn(shell, ["-c", cmd], {detached})` → 每个 chunk 净化、数字节数行、超 50KB/2000 行就开临时文件旁落全量 → `truncateTail` 算出给模型看的尾巴;

    `agent-loop.ts:finalizeExecutedToolCall`
36. **决定要不要再来一轮。** `hasMoreToolCalls = !batch.terminate`,而 `terminate` 是**全票通过**才为真。

### 阶段 6:轮末与收尾

37. **turn_end 的三步顺序(刻意的)。** harness 收到 `turn_end` 后:先 `emitAny`(订阅者抛的错**暂存**不吞)→ 再 `flushPendingSessionWrites()` FIFO 落盘 → 然后才抛暂存的错 → 都没错才 `emitOwn("save_point")`。**写反了的话订阅者一炸就会丢掉本轮的挂起写入。**
    `agent-harness.ts:handleAgentEvent` **:517** / `flushPendingSessionWrites` **:489**
38. **prepareNextTurn(save point 的另一半)。** flush 挂起写入 → `createTurnState()` 重建快照 → `setTurnState()` 更新闭包 → 把新的 context/model/thinkingLevel 交还给 loop。**这就是「中途改配置下一轮才生效」的实现点,也是桌面端自动压缩换 context 的落点。**
    `agent-harness.ts:455`
39. **shouldStopAfterTurn。** 返回 true 就 emit `agent_end` 并 return,两个队列都不拉。
40. **拉 steering。** 否则 `getSteeringMessages()` 填 `pendingMessages`,回到第 13 步。
41. **外层拉 follow-up。** 内层退出(没工具调用、没插话)后,`getFollowUpMessages()`:非空就塞进 `pendingMessages` 并 `continue`(重进内层,`hasMoreToolCalls` 被重置为 true);空则 `break`。
42. **agent_end。** emit `agent_end{messages: newMessages}`,`runAgentLoop` 返回 `newMessages`。harness 侧:flush → `phase = "idle"` → `emitAny` → `emitOwn("settled")`。
43. **返回给调用方。** `runLoopToCompletion` 从尾往前找最后一条 assistant 消息返回;找不到抛 `invalid_state`。loop 自己炸了则走 `emitRunFailure` 补发完整的 `message_start`/`message_end`/`turn_end`/`agent_end` 四连,**保证订阅者永远看得到 `agent_end`**。`finally` 里再 flush 一次并清 `runAbortController`;`prompt()` 的 finally 里 `finishRunPromise()` 解开 `waitForIdle`。
    `agent-harness.ts:runLoopToCompletion/emitRunFailure` **:598 / :548**

### 阶段 7:善后(宿主策略层,不在三包内但必须知道)

44. **判中断。** 先看 `controller.signal.aborted` —— 取消就直接结束,跳过一切善后。
45. **自动重试。** `shouldAutoRetry(message, attempt)`:stopReason 必须是 error、不能是上下文溢出(那该压缩)、`isRetryableAssistantError` 判可重试(两组正则:先排除配额/账单类,再匹配 429/5xx/网络/流截断)、次数没用尽。满足就 sleep 2s/4s/8s 后 `harness.retryLastTurn()` —— 它会把尾部**连续多条** error assistant 一并从本次上下文里摘掉再 `runAgentLoopContinue`(会话树保留它们,「改的是投影,不是历史」)。
    `kernel/src/host/retry.ts` / `coding-agent/src/acp/agent.ts:shouldAutoRetry` + `ai/src/utils/retry.ts:isRetryableAssistantError`
46. **重查一次 aborted。**
47. **自动压缩。** `estimateContextTokens(messages)` → `shouldCompact(tokens, contextWindow, settings)`(阈值 `contextWindow - reserveTokens(16384)`),加上两个 guard:没有真实 usage 不猜、时间戳早于上次压缩则视为刚压过。过阈值就 `harness.compact()`:相位切到 compaction → `prepareCompaction`(定 boundaryStart / previousSummary → `findCutPoint` 从最新往回累加到 `keepRecentTokens(20000)` 再取之后第一个**合法切点** → 切点不是 user 消息则 `findTurnStartIndex` 定出 split turn → `extractFileOperations` 攒文件清单)→ `session_before_compact` hook(可取消、可直接给现成摘要)→ `compact()` 调模型出摘要(有 previousSummary 时换 UPDATE 提示词)→ **成功之后才** `session.appendCompaction` 落盘。
    `kernel/src/host/compaction.ts` → `agent-harness.ts:compact` **:802** → `agent/src/harness/compaction/compaction.ts`
48. **下一次 `buildContext()` 生效。** 第 3c 步的 `defaultContextEntryTransform` 看到这条新的 compaction 条目,把摘要之前的历史从**投影**里隐去 —— 而磁盘上的 `.jsonl` 一个字节都没少。

> **善后动作的铁律:** 重试和压缩自身失败**只往 transcript 写一条 ⚠️ 文本,绝不让这一轮 prompt 失败**。用户已经拿到的回答不该被一次压缩异常连坐废掉。

### 6.1 `packages/agent`

**循环与契约**

- 【新】`agentLoop()` / `agentLoopContinue()` 里是 `void runAgentLoop(...).then(...)`,**没有 `.catch`**。任何回调抛错 → 一个未处理的 Promise rejection + 一个永远不 `end()` 的 EventStream,`await stream.result()` 直接挂死。这就是 `types.ts` 里几乎每个回调都写着 must-not-throw 的原因。`Agent` 类和 harness 各自补了兜底,**裸 loop 没有**。
- 【新】`runAgentLoopContinue` 用的是 `{...context}` —— **messages 数组没有复制**,循环会直接往调用方的数组里 push;而 `runAgentLoop` 用的是新数组。两个入口的所有权语义不对称,实践中安全只是因为 harness 和 Agent 都提前 slice 了一份。
- 【新】`EventStream.push` 在 `done` 之后**静默返回**。`agent_end` 一被推入就 done,之后再推的事件全部消失、不报错。同理 `end()` 不传 result 且从未推过 done/error 时,`result()` 的 Promise **永久 pending**(不是 reject)。
- 【新】`transformContext` 的返回值只喂给本次请求的局部变量,**不写回 `context.messages`**。想持久生效必须走 `prepareNextTurn`。
- 【新】`streamAssistantResponse` 里所有 delta 分支都在 `if (partialMessage)` 里 —— 某个 provider 的流若没发 `start` 就开始发 delta,**一条 `message_update` 都不会产生**,UI 表现为「一直转圈直到最后一次性出全文」。
- 【新】中途 abort 会留下**悬空的工具批次**:串行和并行在 `if (signal?.aborted) break` 处都是「已处理的有结果、剩下的一条 ToolResultMessage 都不造」。于是 transcript 里存在有 toolCall 却没有对应 toolResult 的 assistant 消息,而 `convertToLlm` 不做补齐 —— 重放这段历史能不能通过取决于 provider 的宽容度(pi-ai 的 `transformMessages` 会补合成结果,算是第二道防线)。
- 【新】`beforeToolCall` 拿到的 `args` 是**校验后的对象本体**,就地改它不会重新校验(`agent-loop.test.ts:383` 专门钉住了这个行为:改成数字也照跑)。要挡就返回 `{block:true}`。
- 【新】`createErrorToolResult` 造的结果 `details` **恒为 `{}`** —— 所有内核侧错误(工具不存在、校验失败、被 block、abort、length 截断、afterToolCall 抛错)的 details 都是空对象,前端别指望从里面读结构化信息。
- 【新】`index.ts` 对两个 compaction 模块用具名白名单,于是 `CompactionDetails` / `CompactionResult` / `ContextUsageEstimate` / `CutPointResult` / `SUMMARIZATION_SYSTEM_PROMPT` **从包根拿不到**(当前没有消费者所以没暴雷)。而且注释写的理由(「compaction 模块内部还定义了与 harness/types.ts 同名的类型」)在现在的代码里**核不上** —— 实测两边零个同名导出。注释是历史残留。
- 【新】`Agent` 类在本仓库**没有生产调用方**;改它不会影响桌面端,typecheck 也不会替你发现语义漂移。
- 【新】`Agent.continue()` 从 assistant 尾巴续跑时已经自己 drain 过一次 steering 队列,所以要靠 `skipInitialSteeringPoll` 这个一次性开关把 loop 的首次拉取吞掉,否则一条消息会被消费两遍。

**harness**

- 【CM】`emitOwn` 与 `emitAny` 函数体逐字节相同(:230-238 vs :240-248),都只遍历 `"*"` 桶 —— 走 emitOwn 的事件用 `on()` 注册永不触发(数量修正见 §6.0)。
- 【新】`PendingSessionWrite` 的**五种变体没有生产者**:`flushPendingSessionWrites` 会处理 custom / custom_message / label / session_info / leaf,但全类里 push 只出现在 message / model_change / thinking_level_change / active_tools_change 四处。这五个分支是死代码(或为未来预留)。
- 【新】`abort()` 在一个窗口里是无效的:`runAbortController` 在 `runLoopToCompletion`(:613)才赋值,而 `prompt()` 要先 await `createTurnState()`(会做 session I/O)。abort 落在这个窗口时什么也没打断,却会 `await waitForIdle()` 一直等到整轮跑完。
- 【修正/新】CLAUDE.md 说「abort() 之后必须 `await abort(); await waitForIdle()`」,但 `abort()` 内部第 1113 行**已经** await 了 `waitForIdle`。严格说单独 `await harness.abort()` 就够;真正的坑是**不 await** abort() 就去看 phase —— 那时它还是 turn。
- 【新】`thinkingLevel` 默认落到 `"off"`,而 `"off"` 会让 `createLoopConfig` 把 `reasoning` 整个设成 undefined。对 reasoning 模型这等于「最强的那一档默认关掉,且没有任何地方提示」—— 这就是桌面端要额外做 `defaultThinkingLevel` 注入的原因。
- 【新】`convertToLlm` **忽略 custom 消息的 `display` 字段**:`display: false` 本意是「不给用户看」,但它照样被投影成 user 消息进 LLM。只有 `bashExecution` 有 `excludeFromContext` 这个真正的「不进 LLM」开关。
- 【新】`messages.ts` 里 `COMPACTION_SUMMARY_SUFFIX` 以换行开头(`\n</summary>`),而 `BRANCH_SUMMARY_SUFFIX` 没有。两条摘要的包裹格式不对称。
- 【新】`messages.ts` 是一个**有副作用的类型模块**:`declare module` 的声明合并让 `AgentMessage` 全局变宽,只 import 类型也会触发。
- 【新】`handleAgentEvent` 处理 turn_end 的顺序是刻意的:先 emitAny(订阅者抛的错**暂存**不吞)→ 再 flush → 然后才抛暂存的错 → 都没错才发 save_point。写反了订阅者一炸就丢掉本轮的挂起写入。
- 【新】`drainQueuedMessages` 在 `emitQueueUpdate` 抛错时会 `unshift` 把消息塞回队头。这类「hook 抛错要回滚」的模式在 `agent-harness.ts` 里出现三次,改动时别漏。
- 【新】`setSteeringMode` / `setFollowUpMode` / `setStreamOptions` 三个 setter **既不写 session 也不发事件**,纯改内存;而 `setModel` / `setThinkingLevel` / `setTools` / `setActiveTools` 都会写 session 并发事件。同名为 setXxx,行为分两类。

**会话树与持久化**

- 【CM】`generateEntryId()` = `uuidv7().slice(-8)` 取的是**纯随机尾部**(`bytes[12..15]`),时间戳在 `bytes[0..5]`、sequence 在 `bytes[6..10]`,一位都没进短 id —— **短 id 只有 32 位纯熵、完全不可排序**。注意 `uuid.ts` 开头那句注释「ID 天然按时间排序」**只对完整 uuidv7(sessionId)成立,对条目 id 是错的**。后果就是投影器不变式 2:前端用 `Binary.search` 按字符串序维护集合,所以投影器不敢用内核的 id,自己另铸一套。

- 【新】`generateEntryId()` 试 100 次全撞车后 `return uuidv7()` —— 返回**完整 36 字符**的 id。同一个会话里可能混着 8 字符和 36 字符两种长度。

- 【新】`defaultContextEntryTransform` 里若 `firstKeptEntryId` 没出现在 compaction 之前的路径上(属于另一条分支、或跨 fork 丢了),**压缩点之前的条目会被整段静默丢弃**,只剩一条摘要。没有任何告警。
- 【新】只有路径上**最后一个** compaction 生效,但被它保留下来的区间里若还有更早的 compaction 条目,那些会照常投影成摘要消息 —— 于是上下文里可能出现多条压缩摘要。这是设计不是 bug。
- 【新】`branch_summary` 的 summary 为空字符串时不产生消息,但条目仍在 `buildContextEntries()` 的返回列表里 —— **「条目列表」和「消息列表」不是一一对应的**。

**压缩、技能、执行环境**

- 【新】`findCutPoint` 的兜底方向是「**少压**」而不是「尽量压」:`cutIndex` 初值是区间里**最早**的合法切点,只有累加到 `keepRecentTokens` 才改。所以历史总量不够 2 万 token、或累加位置之后没有合法切点时,函数返回的是「几乎什么都不压」而不是报错。
- 【新】切点回拽的 while 循环会把 `branch_summary` / `custom_message` 也拽进保留侧 —— 而它们恰恰是合法切点。结果是 `cutEntry` 可能是一条 branch_summary,`isSplitTurn` 为 true 但 `turnPrefixMessages` 是空数组,靠 `compact()` 里 `isSplitTurn && length > 0` 兜住退回普通摘要。读代码时容易误以为会白白多调一次模型。
- 【新】`extractFileOpsFromMessage` 是**约定优于配置**的:只认工具名字面量 `read`/`write`/`edit`,且参数字段名必须叫 `path`。datasheet / flash / gdb / netlist 动过的文件一律不进摘要的文件清单。
- 【新】继承上一次压缩的文件清单时,`modifiedFiles` 被塞进 `fileOps.edited` 而不是 `written`;因为 `computeFileLists` 把两者并成同一个 modified 集合,结果正确但读代码时会觉得对不上。
- 【新】`fromHook` 的 compaction / branch_summary 条目的 `details` **不被继承**(hook 提供的摘要 details 是任意形状,不能假定有 readFiles/modifiedFiles)。
- 【新】`prepareCompaction` 里的 `tokensBefore` 用的是**投影之后**的消息(已应用上一条 compaction),是「压之前这次上下文有多大」,不是「这个会话历史一共多大」。
- 【新】**这一区没有 glob,整个内核也没有。** `FileSystem` 只有 `listDir`,coding-agent 的工具目录里也不存在 glob.ts / grep.ts —— 文件查找全靠模型自己在 bash 里跑 `find` / `ls` / `rg`。写文档时不要凭上游 pi 的印象补一个 glob 章节。
- 【新】`truncate.ts` 的 `truncateLine` 与 `GREP_MAX_LINE_LENGTH` 是上游留下的**死导出**(全仓无调用点,这个 fork 里没有 grep 工具)。
- 【新】`NodeExecutionEnv.cleanup()` **生产路径从来没人调**,全仓唯一调用点是单测;实际靠「一轮一个子进程 / 内核进程退出」这个进程边界兜底。
- 【新】`prompt-templates.ts` 的磁盘加载器**从未实现**,`AgentHarnessResources.promptTemplates` 全仓无人填写,于是 `harness.promptFromTemplate()` 在当前形态下必然抛 `Unknown prompt template`。这个文件是纯样板。
- 【新】`loadSkillsFromDirInternal` 里那个「找到 SKILL.md 就 `return`」的语句在 for 循环内部,直接结束了**这一层目录的全部遍历** —— 这是有意的,但写法很像提前 break 写错了位置。
- 【新】技能校验是**宽松警告式**的(名字大写、与父目录不一致、连续连字符全都只出 diagnostics),唯一会导致技能被丢弃的是 **description 缺失或全空白**。`parseFrontmatter` 是手写的,没有结束标记时不报错、整个文件当 body —— 于是又因为缺 description 被静默丢弃。
- 【新】`skills.ts` 里的路径工具是**纯字符串**实现,刻意不用 `node:path`(路径可能来自非本机的 ExecutionEnv),对 Windows 盘根有特判。别「顺手优化」成 node:path。
- 【新】`shell-output.ts` 的临时全量文件不是从命令第一个字节开始的:写的是**触发那一刻内存里的 tail**。正常情况下不丢(内存 tail 上限 100KB > 触发阈值 50KB),但单个 chunk 就超过 100KB 时开头那段永久丢失,而文案仍然说「Full output: …」。
- 【新】`createProgress()` 的 `truncated` 标志刻意**不信** `truncateTail` 的返回值,而用全程累计量判断 —— 因为 `tailOutput` 早就被裁过了。
- 【新】`utf8ByteLength` 是**手算**的:Bun 1.3 的 `Buffer.byteLength("aa\ud800","utf8")` 返回 4 而 `Buffer.from` 实际编码出 5 字节(Node 返回 5),用 Buffer 会让尾部截断在孤立代理项附近算错边界。顺带让整个文件保持浏览器安全。
- 【新】`exec` 的 settle 判定顺序是**回调错误 > 超时 > 中断 > 退出码**,而且 `settle()` 里 clearTimeout / removeEventListener / 删 pid 三件事在 `if (settled) return` **之前**执行(幂等,但顺序读起来反直觉)。
- 【新】Windows 上系统自带的 WSL 垫片 `C:\Windows\System32\bash.exe` **不接受 `-c`**,只能 `-s` 从 stdin 喂命令。这条分支很难在开发机上触发,改 exec 时容易顺手删掉。
- 【新】`waitForChildProcess` 里的 `EXIT_STDIO_GRACE_MS = 100` 是**空闲**计时器(收到 exit 之后每来一个 chunk 就重新计时),不是固定 100ms 宽限;它兜的是「子进程 exit 了但孙进程还占着管道」。

### 6.2 `packages/ai`

**类型与注册表**

- 【新】**类型联合比实现宽**:`KnownApi` 还列着九个 api、`KnownProvider` 还列着三十来家,但 pi-minimal 之后真正存在的实现只有三套协议 + 三个 provider 工厂。写一个不存在的 api 能过 typecheck,失败要到运行时才以 `ModelsError("stream")` 的形式从流里冒出来。

- 【新】`calculateCost` 是**有副作用的**(原地写 `usage.cost`),而且**不管 `totalTokens`**。分层计价的 `inputTokens` **包含 cacheRead 和 cacheWrite**;1h 缓存写入按命中档位的 `rates.input * 2` 计价,而注释写的是 "2x base input" —— 措辞与实现有出入。

- 【新】`Models.getAuth()` 是这一层**少数会 reject 的 API**:token 刷新失败报 `ModelsError("oauth")`、凭据解析失败报 `ModelsError("auth")`,而「provider 不认识 / 没配」返回的是 **undefined**。状态类 UI 必须把这两种情况分开,否则「需要重新登录」会被显示成「没配置」。

- 【新】`ImagesModel<TApi>` 用 `Omit<Model<Api>, …>` 派生,于是**继承了 `thinkingLevelMap` 和 `input`** 这些对图片模型无意义的字段。
- 【新】`types.ts` 第 428 行中间夹着一句 `import type { TSchema } from "typebox";` —— 上游历史遗留,不是分节标记。
- 【新】`session-resources.ts` 在本仓**是死代码**(全仓零调用),是上游给 provider 侧连接池留的口子。

**协议实现**

- 【新】**`mapStopReason` 的注释和代码相反**:注释写「优雅处理未知 stop reason」,default 分支却是 `throw` —— 未知 stop_reason 会让整轮变成 error。
- 【新】**openai-responses 会丢掉真正的错误信息**:`throw new Error("An unknown error occurred")` 是硬编码,不像 anthropic 那样用 `output.errorMessage ||`。

- 【新】`lazy.ts` 的 `forwardStream` 是一个**未被 await 的 async IIFE 且没有 try/catch**。当前所有 source 都是自身不抛的流所以安全;将来传进一个会抛的 async generator 就是静默的 unhandled rejection。
- 【新】openai-completions **要求必须收到 `finish_reason`**,否则收尾抛 `"Stream ended without finish_reason"` —— 这是对付「代理提前掐断连接、却看起来像正常结束」的闸门。

### 6.3 `packages/coding-agent`

**工具骨架与文件三件套**

- 【新】edit 的「多处」判定**永远在模糊空间里算**(`occurrences` 用归一化后的文本切),即使这次走的是精确匹配。所以文件里有两处「只差弯引号或行尾空格」的文本时,一个精确唯一的 oldText 也会被判成重复而报错。
- 【新】`prepareEditArguments` 在「edits 是 JSON 字符串」那条路上**原地改写**传入对象并返回同一引用,于是修改直接落在 `toolCall.arguments` 上;legacy 那条路返回的是新对象,行为不同。
- 【新】`detectLineEnding` **只看第一处**。混合行尾的文件若首行是 LF,整个文件会被当成 LF,一次 edit 顺手把后面的 CRLF 全改成 LF;反过来判成 CRLF 时,`restoreLineEndings` 会把 newText 里的每个 `\n` 也换成 `\r\n`。
- 【新】edit 的 `details.oldContent/newContent/patch` 全都是**归一化为 LF 之后**的内容,而真正写到磁盘的是 `bom + restoreLineEndings(...)` —— **UI 上看到的 diff 与磁盘字节不是同一个东西**。
- 【新】`applyReplacementsPreservingUnchangedLines` 硬性要求原文与归一化文本**行数相同**,否则直接抛错。这依赖 `normalizeForFuzzyMatch` 不增删换行且幂等(源码里专门论证过,并留话说「往这个函数里加规则之前先确认这条还成立」)。
- 【新】`normalizeForFuzzyMatch` 最后那条正则里是一串**看不见的空格字符**,`stripBom` 里是字面 BOM 字符 —— 极容易被「顺手格式化」掉。
- 【新】`fileMutationQueues` 是**模块级全局 Map**,同一进程里所有会话共用一把锁表。
- 【新】read 工具**不进**文件修改队列,可能读到并发写的中间态;它的中断检查是内联的 `throw new Error("Operation aborted")`,不是 `throwIfAborted`。文案「Operation aborted」是模型看得见的,不能换成 Node 原生的 `signal.throwIfAborted()`(那会抛 DOMException 且消息不同)。
- 【新】bash 的失败一律**抛异常**,而 `formatOutput` 在失败路径上算出来的 `details`(truncation / fullOutputPath)被**丢弃**了 —— 「输出被截断了、全量在哪」这条信息在失败路径上只以文字形式存在。
- 【新】bash 超时秒数是从错误消息里 `split(":")[1]` 抠出来的(约定格式 `timeout:<秒数>`),格式一变提示语里就会印出 `undefined`。
- 【新】`noteDecodeDamage` 只是在输出里发现 U+FFFD 时**追加一段警告**,不是修复。
- 【新】write 的 `details.bytes` 与文案 `Successfully wrote N bytes` 用的都是 `content.length`,那是**字符数不是字节数**,对中文内容是错的。
- 【新】`resolveReadPath` 的四种变体全是 macOS 文件名问题,但代码**不判平台** —— Windows/Linux 上一个不存在的路径会白跑四次 `exists`。
- 【新】系统提示词的技能区块有 read 门控(`tools.includes("read") && skills.length > 0`),传空 `selectedTools` 时整段技能清单消失,而 `<project_context>` 段不受门控。`customPrompt` 只替换正文,四段收尾照拼。
- 【新】`loadContextFiles` 的第二道去重是**内容全等**,于是两个毫不相干的目录里若各有一份一字不差的 AGENTS.md,只会进一份。
- 【新】`discoverSkills` **不沿祖先链找**,monorepo 里从子目录起会话就读不到仓库根上的技能。
- 【CM/新】coding-agent 的 package.json `exports` 只有 `"."`,而 `/system-prompt`、`/models`、`/resources` 三个深引用被 kernel host 实际使用 —— **只靠打包别名可达**,改成 workspace 解析之前必须先补 exports。
- 【CM】`createEmbeddedToolDefinitions(env)` 只收 env、没有 enginesDir 参数,所以桌面端不能用它,而是自己按单工具工厂装配。

**嵌入式工具组**

- 【修正】CLAUDE.md 说「gdb session 表是模块级全局」不够准确:gdb 会话对象是 `createGdbToolDefinition` 闭包里的 `let session`(一个工具实例 = 一个会话),log 的 `capture` 同理。真正模块级的是 `liveSessions` / `liveCaptures` 两个 Set(只给进程退出钩子收尸用)和 `probeLease` 变量。**结论不变**:分片 fork 内核进程仍会让两个进程各自以为独占探针。
- 【新】`claimProbe` 的返回值是反的:**返回 undefined 表示拿到了**。
- 【新】`log.ts` **import 了 `gdb.ts` 的 `parseConnect`** —— 改 gdb 的连接串解析会顺手改掉 log 的 tcp 源。
- 【新】`runEngine` 的 cleanup 里**无条件** `killTree(child, "SIGKILL")`,不只在超时/中断路径。这对「一次性 JSON 生产者」是安全的,但意味着 runEngine **不能**用来起任何需要留守的进程。
- 【CM】`enginesDir()` 的向上查找只认「名字叫 engines 且里面有 bin/」,会跳过空壳但也可能找到上层某个无关的 engines/ —— 生产调用方必须显式传。
- 【新】`stm32config` 的 `describeCoverage()` 和 `datasheet` 的 `promptGuidelines` 都在**工具定义构造那一刻**求值。会话建立之后再设环境变量、再装数据包,当前会话的描述文本与系统提示词都不会变。
- 【新】`datasheet.ts` 里**没有内置服务器 IP**,默认地址住在桌面端主进程。裸跑内核(CLI / 测试 / bench)时 datasheet 默认是「未配置」。
- 【新】`netlist` 的 `outDir` 默认就是 `<工程>/.my-pi`(**不是** `.my-pi/netlist`);`sanitizeStem` 按 Unicode 字母数字保留而不是 ASCII 白名单,否则两张中文名网表会共用同一组文件互相覆盖。
- 【新】`flash` 的非零退出**不抛错**;而且 J-Link Commander 失败时也可能 exit 0,描述文本专门警告「读输出,别只信退出码」。
- 【新】gdb 的 `hygiene()` 里 `mi-async on` **必须回读校验**:它默认 off,而 off 时第一条 `-exec-continue` 之后 gdb 就不再读 stdin,后续所有命令石沉大海,只能 SIGKILL。
- 【新】gdb 的 teardown **顺序不能反**:先 `-gdb-exit` 让 gdb 干净 detach,再杀 server;反过来 gdb 会卡在 remote 等待里。
- 【新】没有任何断点/观察点且没传 `expectRunning: true` 时 `exec op:"continue"` 直接抛错 —— 否则会跑到超时,而超时看起来和挂死一模一样。
- 【新】`--simple-values` 对**结构体只给 type 不给 value**。把它当 `<optimized out>` 会让模型断定「这个变量被优化掉了」,而它其实只是个结构体 —— 两个结论引出的下一步完全不同。
- 【新】`resolveGdbPath` **刻意不走 `engineBin`**:走了会抛「去跑 `bun engines/build.ts`」,而 build.ts 不该编译交叉工具链 —— 模型会照做、会成功、再撞同一个错。报错文本里直接写了「Do NOT run」。
- 【新】`gdb start` 撞上已活着的会话时**返回复用提示而不是抛错**:自动压缩会把会话从上下文里抹掉但会话还活着,抛出去模型会 stop 再 start,拆掉一个本该留着的会话。
- 【新】gdb-mi 的 `frameRecords` **绝不能复用 log 的 `splitChunk`**:后者超 4096 字符会强制断行(对不打换行的串口设备是对的),而 MI 一条 record 就是一行,实测见过 659,751 字节 —— 切断的后果是**静默的**:每段解析失败、token 永不 resolve,模型看到的现象是「目标卡死了」。
- 【新】`parseRecord` 对解析不了的行退化成 `foreign` 而**绝不抛异常**(它跑在 data 回调里);但值语法没吃完整行时标 `partial: true` 而**不**降级成 foreign —— 那会让命令的 promise 永远挂着。
- 【新】MI 的 list 里 key 会重复(`stack=[frame={…},frame={…}]`),塌成对象就丢数据,取用必须走 `unwrapList` 脱包装;MI 的 c-string 是**字节串**,必须先还原成字节再按 UTF-8 解一次。
- 【新】目标跑完正常退出时**根本没有 `*stopped`**,只有 `=thread-group-exited`,所以 `onNotify` 也要唤醒停止等待者,否则一次跑到结束的 continue 会被报成「目标卡死了」。
- 【新】QEMU 的观察点实测返回 OK 但命中后 100% CPU 永久空转,所以在 qemu 上 `break watch` **当场拒绝**;gdb 回落到软件观察点时会警告(它单步整个程序,在 SWD 上和挂死无法区分)。
- 【新】OpenOCD 的就绪判据只能用 `Listening on port N for gdb connections`,**不能**用 4444/6666(那两个在适配器初始化之前就绑上了);而且要**同时收 stdout 和 stderr**(OpenOCD / pyOCD 打 stderr,J-Link 打 stdout)。
- 【CM】Windows PowerShell 5.1 一旦发现 stderr 被重定向就把非 stdout 流序列化成 **CLIXML**,于是每次 Windows 串口采集的第一行都是 `#< CLIXML`。这不是噪声是**假证据**(实测 `log wait pattern:"."` 命中的是 PowerShell 自己)。修法是在 `powershellArgv` 里钉 `$ProgressPreference='SilentlyContinue'`;`-OutputFormat Text` 对它无效。
- 【新】Linux 的 `stty` 只认 termios 的 B 常量表,250000(Marlin 默认速率)在 Linux 上会 `invalid argument`,必须在**碰设备之前**拦下并说清楚 —— 否则模型会改成 115200,那会成功然后吐一屏乱码,于是它去怀疑固件。
- 【新】`log start` 三个源互斥;成功 start **不是**「没有别人在读这个口」的证明(Linux 上第二个读者会静默分走字节流,而且这个工具的 stty 还会改掉对方的波特率)。日志文件存的是**净化后的文本**,二进制协议事后无法从日志文件恢复。

**toolchain 与 examples**

- 【新】`tool.bin` 数组有**两种截然不同的语义**而 schema 没有字段区分:arm-gcc 是「这几个都要有」,arm-gdb 是「随便哪个能跑就行」。resolve 用一条统一规则凑合两种意图,不是真的区分了。
- 【新】`resolveTool` 的 `candidates` 字段语义随 status 变化:ok 时只有多候选才填,version-mismatch 时 bin 是空的、candidates 是唯一能看到「找到了什么、只是版本不对」的地方。
- 【新】`indexer.ts` 的 `buildIndex` **只认 esp-idf 和 stm32cube 两个分支**,generic 生态在 `cli.ts` 里就被分流走了 —— 只读 indexer.ts 会误以为 generic 也走这条路。
- 【新】注释说「工具之间并发」,但 registry 那一档用的是 `spawnSync`,**阻塞事件循环**,所以注册表探测实际仍是串行。
- 【新】`core/examples/index.ts` **没有导出 `sync.ts` 和 `generic.ts`**(它们只被 `cli.ts` 与 `tools/examples.ts` 直接深引用),与该目录「公开面全部经桶文件转发」的注释纪律略有出入。

**ACP 适配器**

- 【新】`pipeHarnessToAcp` 里的 sink 是 **fire-and-forget(`void sink(...)`),不 await**:好处是慢的 notify 不卡 agent 循环,代价是 sink 失败静默、理论上不保证到达顺序。而同一文件里 `setupSession` 的观测日志 subscriber 是 await 的(subscribe 的 listener 抛异常会被包起来往上抛,可以打断一整轮)。
- 【新】`acp/agent.ts:199` 的 `clampThinkingLevel` 与 pi-ai 导出的**同名函数语义不同**(前者是 `includes ? level : supported[0]`,后者是就近取),而这个文件只 import 了 `getSupportedThinkingLevels` —— 两个同名函数在同一个 import 上下文里,极易看混。加上 `kernel/src/thinking.ts` 的 `pickThinkingLevel`,一共三份。
- 【新】**默认 thinking 档位不一定是 "off"**:`clampThinkingLevel(model, "off")` 会按 `thinkingLevelMap` 过滤,kimi-k3 的表里写了 `off: null`,于是新会话默认落到 **"low"**。
- 【新】`acp/agent.ts` 的 `shouldAutoRetry` 没有显式检查 stopReason(桌面端那份有)。行为其实等价(`isRetryableAssistantError` 内部第一句就判),但读起来像分叉。另一处真实差异:桌面端的 retrySleep 对 timer 做了 `unref`,ACP 这份没有。
- 【新】两处同文案的 `"Session <id> not found"` **语义不同**:`requireSession` 说的是「这个进程内存里没开着它」,`loadSession` 说的是「磁盘上找不到」。
- 【新】`pendingPrompt` 必须**先比对再清**:重叠 prompt 时旧轮的 finally 会晚于新轮开始执行,直接置 null 会把新轮的 controller 抹掉,于是 `session/cancel` 变成哑操作。
- 【新】顶替一个在飞的 prompt 必须 `await harness.abort()`,**只 abort AbortController 不够**(harness 是相位机不是锁,phase 非 idle 时 `prompt()` 会同步抛 busy)。
- 【新】`setSessionConfigOption` 必须返回 `{configOptions}`,**不能返回 undefined**(这个方法没有 void→{} 的兜底 mapper,会在响应校验时直接失败)。
- 【新】prompt 的 `stopReason` **只有 `end_turn` 和 `cancelled` 两个值**:模型请求彻底失败(重试用尽)也照样返回 end_turn,失败信息只以 ⚠️ 文本 chunk 出现在 transcript 里 —— **ACP 层面看不出「这一轮其实炸了」**。
- 【新】观测日志刻意跳过 `message_update` 与 `tool_execution_update` 两类高频增量,所以 `~/.my-pi/logs/<sessionId>.jsonl` 里看不到流式细节。这是设计不是漏。
- 【新】`@agentclientprotocol/sdk` 只装在 `packages/coding-agent/node_modules` 下,不在仓库根 —— 跑 `test/acp.test.ts` 时注意工作目录。
