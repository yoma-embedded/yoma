# 调试台:两台 Windows 电脑,从下载到跑起来

> **⚠ 2026-08-10 之后协议已变，这份上手步骤尚未按新形态重写。** 工位端不再有项目检出，也没有判据层。分工（研发改代码 / 工位上板）仍对，具体文件路径和开跑步骤以桌面 `/bench` 和 `CLAUDE.md` 为准。
>
> 面向**研发**(研发端)和**测试**(工位端)两个人。目标是:各自装一个 Yoma,
> 配一次,之后每个调试任务都在界面上完成。
>
> 配套:协议与命令行形态见 `docs/信箱闭环-协议与双机部署.md`。

---

## 0. 先明确两台机器的分工

| | 工位机(测试) | 研发机(研发) |
|---|---|---|
| 连板子 | **是**(ST-Link / 探针 + 目标板) | 否 |
| 装什么 | Yoma + **J-Link 软件或 OpenOCD**(含各自驱动) | Yoma + 目标工程的克隆 + **交叉工具链** |
| 在界面上选的角色 | **工位端** | **研发端** |
| 干什么 | 上板、复现、观察、如实报告 | **改代码、构建**、把产物当附件发出去、决定下一轮、宣布终局 |

**分工的依据是手上有什么**:改代码要工具链和完整检出,那在研发机;上板要探针,那在
工位机。

**工位机没有目标工程的代码。** 它的工作目录是一个一次性目录,里面只有研发端穿过来的
附件(新固件、诊断脚本、参考数据)。所以工位机不需要 clone 工程、不需要
`arm-none-eabi-gcc` / `cmake`,也不需要 Python 之类的脚本运行时 —— 要跑什么脚本,
研发端会当附件送过来。

代价落在研发端身上:**工位端读不到源码,它需要的背景全部由研发端写进指令**
(要看的变量给出地址和宽度,要比对的值给出期望数字,要跑的脚本连用法一起附过去)。
角色提示词里专门交代了这一段,但任务写得含糊照样会浪费轮次。

两边唯一的通信渠道是**一个 git 仓库**(信箱)。它可以是 GitHub/Gitee 私有仓、公司
GitLab、NAS 上的裸仓,甚至局域网共享盘上 `git init --bare` 出来的目录 —— 唯一要求是
**两台机器都能读写**。

## 1. 拿安装包

Windows 安装包由仓库的 GitHub Actions 出:**Actions → desktop-win → Run workflow**
(`engines` 选 `prebuilt`,`channel` 选 `prod`),跑完在该次运行的 Artifacts 里下载
NSIS 安装包。

装的时候 SmartScreen 会拦一下("Windows 已保护你的电脑")——**点「更多信息 → 仍要运行」**。
包目前没有代码签名证书,这是已知且被文档承认的状态,不是出了问题。

**引擎(stm32kernel 等)已经打在包里**,工位机不需要另外装它们。烧录/调试用的探针
软件(J-Link 或 OpenOCD)**不在包里**,见下一节。

---

## 2. 两台机器各自的前置

**工位机**(测试):

1. **探针软件 + 驱动**(2026-08 起 Yoma 不再内置探针栈,agent 直接用你机器上的
   工具链):J-Link 探针装 **SEGGER J-Link Software Pack**(自带驱动与
   JLinkGDBServer);ST-Link / CMSIS-DAP 装 **OpenOCD**(加到 PATH)+ ST-Link 驱动。
   装哪个、装在哪,可以在工程的 `.yoma/toolchain.json` 里声明,agent 会自己探测。
2. **就这些。** 不要工程检出、不要交叉工具链、也不用预装 Python 之类的脚本运行时 ——
   要跑什么脚本,研发端会当附件送过来(送过来的脚本要能在这台机器上跑,那是研发端
   写指令时该考虑的事)。

**研发机**(研发):

1. **目标工程**:`git clone` 到本地,而且**工作树要干净** —— 调试台会在它上面开
   `agent/<任务id>` 分支提交改动,开轮时会检查(脏了直接拒:"agent 的改动必须能和
   你的区分开")。终局通过时推这条分支。
2. **交叉工具链在 PATH 里**:`arm-none-eabi-gcc`、`cmake`、`ninja` 之类 —— 打开
   PowerShell 敲 `cmake --version` 能出版本就行。它要真的能把固件编出来。
3. **不需要**探针和板子。

## 3. 项目模板(每个工程配一次,提交进版本库)

模板告诉调试台**这个工程叫什么、板子是什么、有哪些每次都适用的约束**。放在
`<工程>/.yoma/bench/mailbox.template.json`。

它本身就是一份少了"要修什么"的任务书:出任务时,界面上填的描述会拼到模板的 `task`
后面,其余字段原样带过去。

> 模板**要提交进版本库**。调试台自己写的 `.yoma/.gitignore` 只挡运行产物(轮次输入
> 输出、本地状态),`mailbox.template.json` 是白名单放行的。

参考 final_foc 的那份:

```json
{
  "id": "foc",
  "title": "final_foc(B-G431B-ESC1)",
  "repo": { "name": "final_foc", "ref": "develop" },
  "bench": {
    "board": "B-G431B-ESC1",
    "chip": "STM32G431CB",
    "probe": "0483:374b:066DFF575154657287134352"
  },
  "task": "## 工位与安全约束(每个任务都适用)\n1. 绝不能让电机转动……\n5. 构建命令(研发端用):cmake --build build/Debug",
  "deliver": { "push": true, "remote": "origin" }
}
```

**这份文件里不许出现绝对路径** —— 它要被推进信箱、在另一台机器上读。工程目录是本机
事实,由研发机在配置页填(见第 4 节);工位机根本不需要这一项。

逐个说说这里面真正起作用的字段:

- **`task` 是项目级前置约束**(安全红线、目录禁区、构建命令、已知现象),每个任务
  自动带上,与当次的描述拼在一起。"电机绝不能转"这种事写在这里,不靠人每次记得重复。
  它是两个 agent 唯一的任务来源,两边都会读到。
- **`bench.chip` / `bench.probe` / `bench.board`** 会进工位端的角色提示词。多探针工位
  必须填 `probe`(探针序列号等标识,agent 会把它落进自己的烧录/服务器命令),
  否则 agent 有可能挑错板子。
- **`repo.name`** 给人看,也让两台机器对号入座;`repo.ref` 是研发端建分支时的起点;
  `repo.branch` 缺省是 `agent/<任务id>`。
- **`model` / `mailbox.mother.model`**:上面那份**一个都没写** —— 两端于是都跑调试台的
  默认:`deepseek/deepseek-v4-flash`,思考档位 `max`。这个组合是有意的:Flash 每 token
  只要 V4 Pro 的三分之一,省下的直接换成"想得更狠"(2026-08-11 那场闭环的教训正是
  贵模型不思考,见 `packages/bench/src/job.ts` 的 `DEFAULT_MODEL`)。
  要换就**填全**(providerID + modelID),只填一半整个落回默认;`thinking` 是例外,
  可以单独写(`{"thinking":"high"}` 就是"同一个模型上省着点想")。
  两侧可以不一样:`model` 是工位端的,`mailbox.mother.model` 是研发端的。
  跑之前用 `yoma-bench check <任务书>` 印一眼,它会把落定之后的两端模型都打出来。
- **`deliver.push`** 不开的话,终局通过时交付分支只留在研发机本地。这是显式开关。

**模板里没有判据、没有权限白名单、没有 known-good 固件。** 2026-08-10 起这三样都不存在
了:通过与否由研发端 agent 读工位端的自述来判断,没有独立判分器;agent 想调什么工具就
调什么工具,不问不拦;失败也不会自动回刷固件。

### 于是"怎么知道它真的修好了"

只有一条路:**研发端把自证写进指令**,让工位端报出的**数字本身**能说明问题。

比如不要问"烧进去了吗、好了吗",而是:

> 新固件在附件里,烧进去后 reset,然后用 gdb 读 `0x20000010` 这个 32 位值,原样告诉我
> 是多少;再读两次 `0x200002a8`(间隔 1 秒),把两次的值都贴出来。

第一个地址是这一版的构建指纹 —— 值对得上才说明板上跑的**就是这一版**,而不是"某个
带这个符号的旧固件"。第二个是运行计数,它在涨才说明固件活着。数字是工位端抄回来的,
研发端拿它自己判断,中间没有模型转述。

研发端的提示词里写死了这条纪律,但任务本身写得含糊的话,它只能问出含糊的问题。

## 4. 配一次(两台机器各做一遍)

打开 Yoma → 左侧「**调试台**」→ **配置**页:

1. **信箱远端(git)**:填 git 地址(两台填**同一个**),例如
   `git@github.com:you/your-mailbox.git`;
2. **本机角色**:工位机选「工位端」,研发机选「研发端」;
3. **工程目录(仅研发端)**:研发机填这台机器上目标工程的检出路径,例如
   `D:\work\final_foc`;**工位机留空** —— 它不检出工程。任务书要跨机器传,绝对路径在
   对方那儿没有意义,所以它不在任务书里,由研发机自己说;
4. 分支(默认 main)、轮询间隔(默认 15 秒)按需填;
5. 点**保存**,再点**连通自检**。

自检做的就是 `git ls-remote`。**凭据走系统 git**(SSH key 或 Windows 凭据管理器),
Yoma 不保存也不代管密码。所以自检失败的话,先在 PowerShell 里直接跑一次
`git ls-remote <地址>` —— 那里的报错就是真报错。

**模型凭据**:与 Zed / 命令行共用一份,在 `%USERPROFILE%\.yoma\auth.json`:

```json
{ "deepseek": { "type": "api_key", "key": "sk-…" } }
```

`"type"` 字段不能少 —— 少了会被静默忽略,表现是"我明明配了 key 却说没配"。

## 5. 第一次先跑「本机演练」(强烈建议)

**任务**页 → **本机演练**。

它用一个脚本化的假模型在本机跑一遍完整闭环:不要 key、不碰硬件、不花钱,几十秒出终局。
两个角色是**两个真的子进程**,各自持有各自的信箱克隆,只通过一个本地裸仓通信 —— 跟
生产形态的差别只有远端 URL。

跑通说明这台机器上的守护进程、子进程、事件通道、会话落盘全都是好的。之后真任务出问题,
你就知道问题不在这一层。

## 6. 跑一个真任务

**研发机**(它有工程和工具链,出题也在它这边)→ **任务**页:

1. **项目模板**:填模板文件的完整路径;
2. **要修什么**:用大白话描述 —— 现象、怎么复现、什么样算修好;
4. 点**入箱并开跑**。入箱完成后 main 会自动接起本机角色的守护(这个接力由 main 持有,
   你中途切页面或 reload 窗口都不影响)。

然后**工位机**打开 Yoma → 调试台 → 任务页 → **启动守护**。

之后闭环自转:

1. **研发机**看到信箱里只有任务书(状态"等研发端下发第一轮"),它读任务、必要时先改
   代码、跑构建,把产物写进这一轮的附件,再用大白话写指令 ——"新固件在附件里,烧进去,
   然后读 X 告诉我是多少";
2. **工位机**领到指令和附件。附件已经由调试台放进它的一次性工作目录,**怎么上板由那边
   的 agent 自己定**(用 `flash` 工具烧、跑附件里的脚本、或者别的路子)。它复现、观察、
   如实报告;
3. **研发机**读这份自述 → 继续改 → 下一轮,或者宣布终局。

**裁决全归模型**:跑几轮、花多少、算不算做完,都是研发端 agent 自己判断 —— 没有轮数、
token 或时间上限。闭环跑到它说 `done` 或 `fail` 为止,要提前收工就在进度页按停止。

代码改动都提交在研发机的 `agent/<任务id>` 分支上;终局通过且模板开了 `deliver.push`
时,由**研发机**推交付分支。

> 换成 OTA、或者产物由远端 CI 构建?**协议不用改**。变的只是研发端指令里那句话,
> 和工位端 agent 手上的脚本 —— 附件通道 + 一句人话就是全部机制。

**进度**页看轮次时间线(指令来源、附件、agent 自述与工具统计、裁决与裁决者),
点「打开会话观战」能直接跳进那一轮的完整会话回放(会话在跑它的那台机器上)。
**终报**页在终局后给结论与报告。

## 7. 会遇到的情况

| 现象 | 含义 / 怎么办 |
|---|---|
| 守护日志里出现 `⚠ …(30s 后重试)` | 网络或远端抽风,已在指数退避。**不是任务失败**,跑完没推出去的成果会在恢复后原样送达,不重跑不重花钱。 |
| "另一个 Yoma 实例正在跑这个信箱" | 单实例锁:同一个信箱同一个角色只能有一个守护。关掉另一个,或等它结束。 |
| "本机角色是工位端,不能起研发端守护" | 配置页的角色和你点的按钮对不上。改角色再来 —— 起错角色会得到一个对着同一个信箱说错话的进程,症状是"任务一直没人执行"。 |
| 报"研发端要在本机的工程检出上改代码,但还没配工程目录" | 配置页的「工程目录(仅研发端)」没填。任务书里没有路径是**有意的**。工位机不会报这个。 |
| "守护进程连续 5 次起来就退出" | 永久性故障(产物缺失、node 加载不了),不再重试。看 `userData\logs`。 |
| 想中途停 | 任务页**停止**。守护和它正在跑的 agent 轮会被一起带走(Windows 上 `taskkill /T` 杀整棵进程树)。 |
| 关掉 Yoma / 自动更新重启 | 守护也会被一起停掉 —— 不会留下还在动板子的孤儿进程。 |
| **工位机上交互会话和调试台任务抢探针** | 2026-08-10 起没有互斥锁了。同一台机器上任务在跑时,别再开交互会话动硬件,否则会撞 `exclusive access (0xe00002c5)`,而报错长得和"板子没插"一模一样。 |
| 工位端说它读到的中文是问号 | 子进程默认不按 UTF-8 输出(中文 Windows 是 cp936),而管道按 UTF-8 解。让研发端在指令里要求脚本自己 `sys.stdout.reconfigure(encoding="utf-8")`,或干脆让它只回报数字。 |
| 它一直在 `continue`,停不下来 | 没有预算上限是设计如此(2026-08-10)。按停止,或者把任务书的 `task` 写得更收敛(告诉它什么情况下该认输)。 |

## 8. 灰度:exe 和命令行可以混搭

信箱的文件协议一字没改。所以"一台用 exe、另一台用命令行"完全成立 —— 命令行形态见
`docs/信箱闭环-协议与双机部署.md`。先让一端用 exe 跑起来,另一端慢慢迁,是推荐的
上线路径。
