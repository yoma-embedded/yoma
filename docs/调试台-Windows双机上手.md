# 调试台:两台 Windows 电脑,从下载到跑起来

> 面向**研发**(决策端)和**测试**(工位端)两个人。目标是:各自装一个 Yoma,
> 配一次,之后每个调试任务都在界面上完成。
>
> 配套:协议与 CLI 形态见 `docs/信箱闭环-协议与双机部署.md`;产品设计与施工记录见
> `docs/施工指南-信箱调试台桌面端.md`。

---

## 0. 先明确两台机器的分工

| | 工位机(测试) | 决策机(研发) |
|---|---|---|
| 连板子 | **是**(ST-Link / 探针 + 目标板) | 否 |
| 装什么 | Yoma + 目标工程 + 交叉工具链 | Yoma |
| 在界面上选的角色 | **工位** | **决策** |
| 干什么 | 跑调试 agent:改代码、构建、烧录、看日志、跑判据 | 跑母 agent:看结果、决定下一轮做什么、宣布终局 |

两边唯一的通信渠道是**一个 git 仓库**(信箱)。它可以是 GitHub/Gitee 私有仓、公司
GitLab、NAS 上的裸仓,甚至局域网共享盘上 `git init --bare` 出来的目录 —— 唯一要求是
**两台机器都能读写**。

---

## 1. 拿安装包

Windows 安装包由仓库的 GitHub Actions 出:**Actions → desktop-win → Run workflow**
(`engines` 选 `prebuilt`,`channel` 选 `prod`),跑完在该次运行的 Artifacts 里下载
NSIS 安装包。

装的时候 SmartScreen 会拦一下("Windows 已保护你的电脑")——**点「更多信息 → 仍要运行」**。
包目前没有代码签名证书,这是已知且被文档承认的状态,不是出了问题。

**引擎(probe-rs 等)已经打在包里**,工位机不需要另外装它们。

---

## 2. 工位机的额外前置(决策机不需要)

1. **探针驱动**:插上 ST-Link,设备管理器里能看到即可(Windows 通常自带)。
2. **目标工程**:`git clone` 到本地,必须是 git 仓库(调试台永远开分支提交,不动主干)。
3. **交叉工具链在 PATH 里**:`arm-none-eabi-gcc`、`cmake`、`ninja` 之类 —— 打开
   PowerShell 敲 `cmake --version` 能出版本就行。
4. **known-good 固件**:一份"已知能跑"的 ELF 放进工程里(例如 `.bench/known-good/`)。
   任务失败或超预算时调试台会自动把它烧回去,板子不会停在半烧状态。

---

## 3. 项目模板(每个工程配一次,提交进版本库)

模板告诉调试台**这个工程怎么构建、怎么验、板子是什么**。放在
`<工程>/.bench/mailbox.template.json`。

> **这三样必须提交进版本库**(工位机是从 git 克隆工程的,少了就跑不起来):
> `.bench/mailbox.template.json`、`.bench/checks/*`、以及 `bench.knownGoodElf`
> 指向的那份固件。调试台自己写的 `.bench/.gitignore` 只挡运行产物(轮次输入输出、
> 决策日志),这三样是放行的。

参考 final_foc 的那份:

```json
{
  "id": "foc",
  "title": "final_foc(B-G431B-ESC1)",
  "repo": { "ref": "develop" },
  "bench": {
    "chip": "STM32G431CB",
    "probe": "0483:374b:066DFF575154657287134352",
    "elf": "build/Debug/final_foc.elf",
    "knownGoodElf": ".bench/known-good/final_foc.elf"
  },
  "task": "## 工位与安全约束(每个任务都适用)\n1. 绝不能让电机转动……",
  "success": {
    "build": "cmake --build build/Debug",
    "checks": [
      { "type": "bash", "command": "python .bench/checks/firmware_alive.py", "timeoutS": 60 }
    ]
  },
  "policy": "unattended",
  "allowCommands": ["firmware_alive.py"],
  "protectedPaths": ["Algo/**", "*.ld", "startup_stm32g431xx.s"],
  "maxDiffLines": 120,
  "model": { "providerID": "deepseek", "modelID": "deepseek-v4-pro" },
  "mailbox": { "mother": { "model": { "providerID": "deepseek", "modelID": "deepseek-v4-flash" } } }
}
```

四个字段决定了这套东西可不可信,值得逐个看一眼:

- **`success.checks` 是判据 —— 由调试台亲自跑,agent 说"修好了"不算数。**
  判据必须客观可执行(退出码、日志出现/不出现)。它永远来自模板,**不由任务描述生成**。
- **`task` 是项目级前置约束**(安全红线、目录禁区、已知现象),每个任务自动带上,
  与当次的描述拼在一起。"电机绝不能转"这种事写在这里,不靠人每次记得重复。
- **`protectedPaths` / `maxDiffLines`**:碰了受保护路径或改动过大,权限策略直接拦。
- **`policy: "unattended"`**:无人值守。需要人工裁决的动作一律拒绝,并把"这条路
  被拦了"写进下一轮提示词 —— agent 会换条路,不会卡在那等人。

### Windows 上写模板的三个坑

- 判据命令用 **`python`** 而不是 `python3`(Windows 上通常没有 `python3`)。
- **判据不过 shell**(argv 直接执行),所以别写 `&&`、管道、重定向 —— 要多步就写成
  一个脚本文件再调它。好处是没有 sh 也能跑。
- `npm`/`bun` 这类是 `.cmd` 包装器,直接执行会 ENOENT,要写成 `cmd /c npm run build`。
  调试台遇到这种情况会在报错里直接告诉你该怎么改。

## 4. 配一次(两台机器各做一遍)

打开 Yoma → 左侧「**调试台**」→ **配置**页:

1. **信箱远端**:填 git 地址(两台填**同一个**),例如
   `git@github.com:you/your-mailbox.git`;
2. **本机角色**:工位机选「工位」,决策机选「决策」;
3. 点**保存**,再点**连通自检**。

自检做的就是 `git ls-remote`。**凭据走系统 git**(SSH key 或 Windows 凭据管理器),
Yoma 不保存也不代管密码。所以自检失败的话,先在 PowerShell 里直接跑一次
`git ls-remote <地址>` —— 那里的报错就是真报错。

**模型凭据**:与 Zed / 命令行共用一份,在 `%USERPROFILE%\.my-pi\auth.json`:

```json
{ "deepseek": { "type": "api_key", "key": "sk-…" } }
```

`"type"` 字段不能少 —— 少了会被静默忽略,表现是"我明明配了 key 却说没配"。

## 5. 第一次先跑「本机演练」(强烈建议)

**任务**页 → **本机演练**。

它用一个脚本化的假模型在本机跑一遍完整闭环:不要 key、不碰硬件、不花钱,几十秒出
终局。跑通说明这台机器上的守护进程、子进程、判据执行、事件通道全都是好的 —— 之后
真任务出问题,你就知道问题不在这一层。

---

## 6. 跑一个真任务

**决策机或工位机任意一台**(通常是研发)→ **任务**页:

1. **项目模板**:填模板文件的完整路径;
2. **要修什么**:用大白话描述 —— 现象、怎么复现、什么样算修好;
3. **预算档**:快速(4 轮 / 30 万 tokens / 45 分钟)、标准(8 轮 / 100 万 / 2 小时)、
   彻底(12 轮 / 250 万 / 6 小时);
4. 点**入箱并开跑**。

然后**工位机**打开 Yoma → 调试台 → 任务页 → **启动守护**(如果它还没在跑)。

之后闭环自转:工位机领指令 → 跑一轮 agent → 判据独立复验 → 结果回填信箱;
决策机读结果 → 裁决 → 下发下一轮或宣布终局。**判据全绿、预算耗尽、环境错误由代码
守卫直接终局,模型无权宣布成功。**

**进度**页看轮次时间线(指令来源、agent 摘要、判据逐条结果、裁决与裁决者),
点「打开会话观战」能直接跳进那一轮的完整会话回放。**终报**页在终局后给结论与报告。

## 7. 会遇到的情况

| 现象 | 含义 / 怎么办 |
|---|---|
| 状态条显示"信箱暂时不可达,已在退避重试" | 网络或远端抽风。**不是任务失败**,跑完没推出去的成果会在恢复后原样送达,不重跑不重花钱。 |
| "另一个 Yoma 实例正在跑这个信箱" | 单实例锁:同一个信箱同一个角色只能有一个守护。关掉另一个,或等它结束。 |
| 任务活跃时,交互会话里的烧录/gdb 按钮被拒 | **有意的**。探针同一时间只能被一个进程用,调试台任务在跑时交互会话不能动硬件。任务终局后自动解除。 |
| 想中途停 | 任务页**停止**。守护和它正在跑的 agent 轮会被一起带走(Windows 上杀整棵进程树)。 |
| 关掉 Yoma / 自动更新重启 | 守护也会被一起停掉 —— 不会留下还在动板子的孤儿进程。 |
| 任务失败或挂起 | 工位机自动把 known-good 固件烧回去,板子回到已知状态。 |

## 8. 灰度:exe 和命令行可以混搭

信箱的文件协议一字没改。所以"一台用 exe、另一台用命令行"完全成立 —— 命令行形态见
`docs/信箱闭环-协议与双机部署.md`。先让一端用 exe 跑起来,另一端慢慢迁,是推荐的
上线路径。
