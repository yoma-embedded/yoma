# 调试台:两台 Windows 电脑,从下载到跑起来

> 面向**研发**(研发端)和**测试**(工位端)两个人。目标是:各自装一个 Yoma,
> 配一次,之后每个调试任务都在界面上完成。
>
> 配套:协议与 CLI 形态见 `docs/信箱闭环-协议与双机部署.md`;产品设计与施工记录见
> `docs/施工指南-信箱调试台桌面端.md`。

---

## 0. 先明确两台机器的分工

| | 工位机(测试) | 研发机(研发) |
|---|---|---|
| 连板子 | **是**(ST-Link / 探针 + 目标板) | 否 |
| 装什么 | Yoma + 目标工程的克隆 + 判据脚本要的运行时(通常是 Python) | Yoma + 目标工程 + **交叉工具链** |
| 在界面上选的角色 | **工位** | **决策** |
| 干什么 | 上板、复现、观察、如实报告;判据由调试台亲跑 | **改代码、构建**、把产物当附件发出去、决定下一轮、宣布终局 |

**分工的依据是手上有什么**:改代码要工具链和完整检出,那在研发机;上板要探针,
那在工位机。所以**交叉工具链装在研发机**,工位机不需要 `arm-none-eabi-gcc` / `cmake`
—— 它不构建,固件是当附件穿过信箱来的。

工位端**不改源码**:`edit`/`write` 会被权限策略直接拒掉。它发现要改什么,写进报告,
下一轮研发端把新产物附过来。反过来研发端**碰不到硬件**(`flash`/`gdb`/`log` 被拒)——
板子根本不在那台机器上。

两边唯一的通信渠道是**一个 git 仓库**(信箱)。它可以是 GitHub/Gitee 私有仓、公司
GitLab、NAS 上的裸仓,甚至局域网共享盘上 `git init --bare` 出来的目录 —— 唯一要求是
**两台机器都能读写**。

---

## 1. 拿安装包

Windows 安装包由仓库的 GitHub Actions 出:**Actions → desktop-win → Run workflow**
(`engines` 选 `prebuilt`,`channel` 选 `prod`),跑完在该次运行的 Artifacts 里下载
NSIS 安装包。

装的时候 SmartScreen 会拦一下("Windows 已保护你的电脑")——**点「更多信息 → 仍要运行」**。
包目前没有代码签名证书,这是已知且被文档承认的状态,不是出了问题。

**引擎(probe-rs 等)已经打在包里**,工位机不需要另外装它们。

---

## 2. 两台机器各自的前置

**工位机**(测试):

1. **探针驱动**:插上 ST-Link,设备管理器里能看到即可(Windows 通常自带)。
2. **目标工程**:`git clone` 到本地。它是**被测环境**,工作树必须干净 —— 判据在这棵树上
   跑,树被人动过判据就不再说明"已提交的那份代码行不行"(开轮前会检查,脏了直接拒)。
3. **判据脚本的运行时**:判据通常是 Python,装一个 Python 即可(3.x)。
   `python` 还是 `py -3` 不用管 —— 见第 3 节。
4. **known-good 固件**:一份"已知能跑"的 ELF 提交进工程(例如 `.bench/known-good/`)。
   任务失败或超预算时调试台会自动把它烧回去,板子不会停在半烧状态。
5. **不需要**交叉工具链:它不构建。

**研发机**(研发):

1. **目标工程**:`git clone` 到本地。调试台会在它上面开 `agent/<任务id>` 分支提交改动,
   终局通过时推这条分支 —— 所以工作树也要干净。
2. **交叉工具链在 PATH 里**:`arm-none-eabi-gcc`、`cmake`、`ninja` 之类 —— 打开
   PowerShell 敲 `cmake --version` 能出版本就行。它要真的能把固件编出来。
3. **不需要**探针和板子。

## 3. 项目模板(每个工程配一次,提交进版本库)

模板告诉调试台**这个工程怎么构建、怎么验、板子是什么**。放在
`<工程>/.bench/mailbox.template.json`。

> **这三样必须提交进版本库**(工位机是从 git 克隆工程的,少了就跑不起来):
> `.bench/mailbox.template.json`、`.bench/checks/*`、以及 `bench.knownGoodElf`
> 指向的那份固件。调试台自己写的 `.bench/.gitignore` 只挡运行产物(轮次输入输出、
> 决策日志),这三样是放行的。

参考 final_foc 的那份:

```json
{
  "id": "foc",
  "title": "final_foc(B-G431B-ESC1)",
  "repo": { "name": "final_foc", "ref": "develop" },
  "bench": {
    "chip": "STM32G431CB",
    "probe": "0483:374b:066DFF575154657287134352",
    "elf": ".bench/incoming/final_foc.elf",
    "knownGoodElf": ".bench/known-good/final_foc.elf"
  },
  "task": "## 工位与安全约束(每个任务都适用)\n1. 绝不能让电机转动……\n5. 构建命令(研发端用):cmake --build build/Debug",
  "success": {
    "checks": [
      { "type": "script", "path": ".bench/checks/flashed_build.py", "timeoutS": 180 },
      { "type": "script", "path": ".bench/checks/firmware_alive.py", "timeoutS": 60 }
    ]
  },
  "policy": "unattended",
  "allowCommands": ["cmake", "ninja", "firmware_alive.py"],
  "protectedPaths": ["Algo/**", "*.ld", "startup_stm32g431xx.s"],
  "maxDiffLines": 120,
  "model": { "providerID": "deepseek", "modelID": "deepseek-v4-pro" },
  "mailbox": { "mother": { "model": { "providerID": "deepseek", "modelID": "deepseek-v4-flash" } } }
}
```

**这份文件里不许出现绝对路径** —— 它要被推进信箱、在另一台机器上读。工程目录是本机
事实,两台机器各自在配置页填(见第 4 节)。

三处容易写错的地方:

- **`bench.elf` 指 `.bench/incoming/…` 而不是 `build/…`**:工位机不构建,固件是研发端
  当附件发过来的,调试台把它放在工程的 `.bench/incoming/<原文件名>`。
- **没有 `success.build`**:构建归研发端(它才有新代码和工具链)。在工位机上跑构建
  只会编出一份**旧**代码,判据于是在错误的固件上通过 —— 那是假通过。
  构建命令写进 `task` 里告诉研发端就行。
- **判据用 `script` 而不是 `bash`**:见下一小节。

四个字段决定了这套东西可不可信,值得逐个看一眼:

- **`success.checks` 是判据 —— 由调试台亲自跑,agent 说"修好了"不算数。**
  判据必须客观可执行(退出码、日志出现/不出现)。它永远来自模板,**不由任务描述生成**。
- **`task` 是项目级前置约束**(安全红线、目录禁区、已知现象),每个任务自动带上,
  与当次的描述拼在一起。"电机绝不能转"这种事写在这里,不靠人每次记得重复。
- **`protectedPaths` / `maxDiffLines`**:碰了受保护路径或改动过大,权限策略直接拦。
- **`policy: "unattended"`**:无人值守。需要人工裁决的动作一律拒绝,并把"这条路
  被拦了"写进下一轮提示词 —— agent 会换条路,不会卡在那等人。

### 判据要写成 `script`,别写死解释器

```json
{ "type": "script", "path": ".bench/checks/firmware_alive.py", "args": [], "timeoutS": 60 }
```

**解释器由跑判据的那台机器当场解析**:macOS 上是 `python3`,Windows 上优先 `py -3`
再退到 `python`;`.sh` 找 bash,`.js` 找 node,`.ps1` 找 powershell。写死
`{"type":"bash","command":"python3 …"}` 就是把出题人那台机器钉进了判据 —— 换台机器
一律"命令起不来",而那个报错长得和"板子没插"一模一样。

**脚本里也别写死绝对路径。** 调试台会给判据进程注入这些环境变量,照着读:

| 变量 | 含义 |
|---|---|
| `YOMA_PROBE_RS` | probe-rs 可执行文件的完整路径(Windows 上已带 `.exe`) |
| `YOMA_ENGINES_DIR` | 引擎目录(别的引擎二进制在 `<它>/bin/`) |
| `YOMA_WORKSPACE` | 工程根的绝对路径(判据的 cwd 也是它) |
| `YOMA_CHIP` / `YOMA_PROBE` | 模板里声明的芯片名与探针选择器 |
| `YOMA_ELF` / `YOMA_KNOWN_GOOD_ELF` | 相对工程根的固件路径 |

```python
ELF = os.environ.get("YOMA_ELF") or ".bench/incoming/firmware.elf"
PROBE_RS = os.environ.get("YOMA_PROBE_RS") or shutil.which("probe-rs") or "probe-rs"
```

另外两条老规矩不变:

- **判据不过 shell**(argv 直接执行),所以别写 `&&`、管道、重定向 —— 要多步就写成
  一个脚本文件再调它。好处是没有 sh 也能跑。
- `npm`/`bun` 这类是 `.cmd` 包装器,直接执行会 ENOENT,要写成 `cmd /c npm run build`。
  调试台遇到这种情况会在报错里直接告诉你该怎么改。

### 一定要有一条"烧录新鲜度"判据

上板这件事交给工位端 agent 自己判断怎么做,于是多出一种失败:**它忘了烧、或者烧失败
了却接着测**。判据于是跑在旧固件上,万一旧固件恰好能过,你会拿到一个**假通过**,而且
从证据里完全看不出来。

挡它的办法是加一条比对判据(final_foc 的 `.bench/checks/flashed_build.py` 就是它):

```python
argv = [PROBE_RS, "verify", "--chip", CHIP, ELF]      # 逐字节比对 flash 与 ELF
```

比"读一个魔数常量"强 —— 魔数只证明"某个带这个符号的固件在跑",不证明是**哪一版**。

**但要认输出文本,不能只看退出码**:`probe-rs verify` 内容不匹配时照样 `exit 0`
(实测输出 `Verification failed: contents do not match`)。只看退出码的话,这条闸门
永远不会响,比没有更糟。

## 4. 配一次(两台机器各做一遍)

打开 Yoma → 左侧「**调试台**」→ **配置**页:

1. **信箱远端**:填 git 地址(两台填**同一个**),例如
   `git@github.com:you/your-mailbox.git`;
2. **本机角色**:工位机选「工位」,研发机选「决策」;
3. **工程目录(本机)**:这台机器上目标工程的检出路径,例如
   `D:\work\final_foc`。**两台机器都要填,而且填各自的** —— 任务书要跨机器传,
   绝对路径在对方那儿没有意义,所以它不在任务书里,由每台机器自己说;
4. 点**保存**,再点**连通自检**。

自检做的就是 `git ls-remote`。**凭据走系统 git**(SSH key 或 Windows 凭据管理器),
Yoma 不保存也不代管密码。所以自检失败的话,先在 PowerShell 里直接跑一次
`git ls-remote <地址>` —— 那里的报错就是真报错。

**模型凭据**:与 Zed / 命令行共用一份,在 `%USERPROFILE%\.my-pi\auth.json`:

```json
{ "deepseek": { "type": "api_key", "key": "sk-…" } }
```

`"type"` 字段不能少 —— 少了会被静默忽略,表现是"我明明配了 key 却说没配"。

## 5. 第一次先跑「本机演练」(强烈建议)

**任务**页 → **本机演练**。

它用一个脚本化的假模型在本机跑一遍完整闭环:不要 key、不碰硬件、不花钱,几十秒出
终局。跑通说明这台机器上的守护进程、子进程、判据执行、事件通道全都是好的 —— 之后
真任务出问题,你就知道问题不在这一层。

## 6. 跑一个真任务

**研发机**(它有工程和工具链,出题也在它这边)→ **任务**页:

1. **项目模板**:填模板文件的完整路径;
2. **要修什么**:用大白话描述 —— 现象、怎么复现、什么样算修好;
3. **预算档**:快速(4 轮 / 30 万 tokens / 45 分钟)、标准(8 轮 / 100 万 / 2 小时)、
   彻底(12 轮 / 250 万 / 6 小时);
4. 点**入箱并开跑**。

然后**两台机器**分别打开 Yoma → 调试台 → 任务页 → **启动守护**(如果还没在跑)。

之后闭环自转:

1. **研发机**看到信箱里只有任务书(状态"等研发端下发第一轮"),它读任务、
   必要时先改代码、跑构建,把产物写进这一轮的附件,再用大白话写指令
   ——"新固件在附件里,烧进去,然后发 X 看 Y";
2. **工位机**领到指令和附件。附件已经由调试台放在工程的 `.bench/incoming/` 下,
   **怎么上板由那边的 agent 自己定**(用 `flash` 工具烧、跑工程里的 OTA 脚本、
   或者别的路子)。它复现、观察、如实报告;
3. **判据由工位机的调试台独立跑**,不经模型;结果与证据回填信箱;
4. **研发机**读结果 → 继续改 → 下一轮,或宣布终局。

**判据全绿、预算耗尽、环境错误由代码守卫直接终局,模型无权宣布成功。**
代码改动都提交在研发机的 `agent/<任务id>` 分支上;通过时由**研发机**推交付分支,
失败时由**工位机**把 known-good 固件烧回去 —— 谁手上有什么,谁干什么。

> 换成 OTA、或者产物由远端 CI 构建?**协议不用改**。变的只是研发端指令里那句话,
> 和工位端 agent 手上的脚本 —— 附件通道 + 一句人话就是全部机制。

**进度**页看轮次时间线(指令来源、agent 摘要、判据逐条结果、裁决与裁决者),
点「打开会话观战」能直接跳进那一轮的完整会话回放。**终报**页在终局后给结论与报告。

## 7. 会遇到的情况

| 现象 | 含义 / 怎么办 |
|---|---|
| 状态条显示"信箱暂时不可达,已在退避重试" | 网络或远端抽风。**不是任务失败**,跑完没推出去的成果会在恢复后原样送达,不重跑不重花钱。 |
| "另一个 Yoma 实例正在跑这个信箱" | 单实例锁:同一个信箱同一个角色只能有一个守护。关掉另一个,或等它结束。 |
| 任务活跃时,交互会话里的烧录/gdb 按钮被拒 | **有意的**。探针同一时间只能被一个进程用,调试台任务在跑时交互会话不能动硬件。任务终局后自动解除。 |
| 想中途停 | 任务页**停止**。守护和它正在跑的 agent 轮会被一起带走(Windows 上杀整棵进程树)。 |
| 关掉 Yoma / 自动更新重启 | 守护也会被一起停掉 —— 不会留下还在动板子的孤儿进程。 |
| 任务失败或挂起 | 工位机自动把 known-good 固件烧回去,板子回到已知状态。 |
| 报"这台机器上还没配工程目录" | 配置页的「工程目录(本机)」没填。任务书里没有路径是**有意的**,两台机器各配各的。 |
| 报"工作树不干净" | 工位机的工程被改动过。判据要在已提交的代码上跑才有意义 —— `git checkout .` 或提交掉。 |
| 进度里出现"⚠ 工位端改了工作树" | 工位端不该改源码。这一轮的判据是在被改过的树上跑的,证据要打折看。 |

## 8. 灰度:exe 和命令行可以混搭

信箱的文件协议一字没改。所以"一台用 exe、另一台用命令行"完全成立 —— 命令行形态见
`docs/信箱闭环-协议与双机部署.md`。先让一端用 exe 跑起来,另一端慢慢迁,是推荐的
上线路径。
