# 架构审查：本地资源与运行状态

日期：2026-09-16。范围：STM32 重构之外的工具链、手册库、进程生命周期、引擎交付和会话状态。

本审查沿着一条用户路径核对：**配置的来源 → 解析出的资源 → 真正执行的对象 → 界面宣称的能力 → 安装环境验证**。
审查以源码和隔离临时探针为依据；另外修复了一处已复现的 PATH 别名问题（见第 3 节）。没有重启桌面端、连接硬件、修改用户账本或发出外部请求。
STM32 本地数据库/固件的重构由同一轮工作另行处理，不在这里重复列问题。

## 后续实施范围（2026-09-16）

按用户最新要求，第 1 项手册/RAG 暂缓：后续采用上传服务器解析的方向，本轮撤下本地解析与索引的新增实现。第 2、3 项及 STM32 可用性继续修复；第 4 项 Mac/CPU 发布契约暂不改动，第 5 项仍是待专项实测的审查记录。以下各节的“证据”保留发现问题时的调用路径，不代表修改后的实现。

- **手册库（延期）**：用户明确本机解析不适合预期使用方式，后续应上传服务器处理；本轮不改手册导入、索引或查询协议。
- **执行环境**：每次工具调用获取所属会话的环境快照，GDB、日志、PowerShell 和各原生工具显式消费同一份环境。设置、安装及重新探测统一刷新已开会话；已启动进程保留启动时的快照，不修改宿主的全局 PATH。
- **能力状态**：目录配置、路径记录、入口不完整、执行/版本未验证与已就绪分别表达；编译工具链必需入口和 GDB 候选入口分别声明。用户明确指定的位置失效时返回该位置的状态，不悄悄改选全局安装。
- **STM32 可用性**：会话根据本机 CubeMX 数据库的只读探测决定是否提供 `stm32config`。没有数据库时不提供该工具，不要求用户为了使用 Yoma 安装 CubeMX；普通网表解析和其他工具仍可用，配置变化在后续用户轮次重新检查。

### 修复验收

- 两个真实会话运行同名、不同路径的假工具，核对实际子进程收到的 PATH 和项目 exports；GDB、日志与流式命令分别验证环境传递。设置更新后，执行快照及模型的工具链提示同步变化。
- 受控时序回归覆盖“停止资源探测后立即发新消息”和“旧探测晚于新设置完成”：旧轮取消不会误伤新轮，旧刷新结果不会覆盖新环境。
- 空目录、错误入口、部分编译工具链、替代 GDB 入口、未识别版本和显式失效配置分别验证；版本探测与执行使用一致的基础环境和声明变量。
- 使用真实安装的 CubeMX 及原生转换器验证可用性；显式失效路径返回不可用，不回退到另一份安装。探测阶段不生成缓存。
- 强制执行 11 个包与根目录类型检查；桌面生产构建、真实 MessagePort IPC、preload/contextBridge 往返、30 项页面检查及引擎冒烟均通过。分发冒烟确认安装资源没有 CubeMX 数据库、器件包或 STM32 固件。
- 最终整套复验：69 个测试文件通过，1311 项通过、90 项跳过（kernel、kernel-domain、desktop，4 个 worker）。先前与构建并行的一次运行中，已有确认流程用例发生等待超时；该用例、完整宿主文件和最终整套复验均已通过，未通过放宽断言掩盖失败。

验证使用隔离配置、假模型和假设备进程，没有重启用户正在使用的 Yoma，也没有操作硬件。Mac 发布和手册/RAG 不在本轮验收范围。

## 结论与顺序

发现了三处已确认的产品边界不一致，以及两处需要在双平台交付前修正的运行/交付边界。
它们需要分别建立明确契约，不适合再做一个统管所有资源的大模块。

| 顺序 | 范围 | 判断 | 建议边界 |
| --- | --- | --- | --- |
| 1 | 手册库与 datasheet | 本地导入成功后，agent 的检索路径完全看不到它 | 明确知识来源与检索能力，统一导入和查询的资源身份 |
| 2 | 工具链与执行器 | 项目选定的环境没有到达 GDB 和日志命令；手填配置不更新已开会话 | 会话级执行环境，由每个执行器显式消费 |
| 3 | 工具链状态 | 保存路径被当成“已就绪”，缺少已定位/可执行/版本匹配的区别 | 接受配置与验证能力分开 |
| 4 | 原生引擎交付 | 校验了操作系统格式，未校验 CPU 架构；非便携脚本仍可放行 | 目标平台和 CPU 对应完整发布能力清单 |
| 5 | 退出与取消 | 父进程等待预算短于工具释放预算，退出完成不能证明资源释放完成 | 宿主统一持有资源释放期限及终态 |

会话重试、乐观消息确认以及日志/GDB 内部状态已有明确的不变式和专项测试，本次没有证据支持把这些部分整体推倒重写。

## 1. 手册库写本地，agent 只读远端（P1，已确认）

### 证据

- `packages/desktop/src/main/manuals.ts:129` 从本地 shared/overlay manifest 列出文档；`:202` 将 overlay 文档直接显示为完整。
- 同文件 `:523` 用 `rag_yoma ingest --tier overlay --out <本地索引> --artifacts <本地产物>` 导入；`:531` 起本地 Python。
- `packages/app/src/pages/manuals.tsx:447` 说明芯片家族用于检索过滤；`:474` 说明提取图表“可被检索并支持看图”。
- 但 `packages/kernel/src/host/tools/datasheet/session.ts:4` 明确声明“完全在线、零本地状态”；实际查询由 `client.ts:250` 发往远端 `/api/search`，章节和图片由 `client.ts:235`、`:236` 从远端获取。
- 该工具没有读取本地 overlay、共享索引或下载产物的路径。服务器地址解析已统一，但知识内容的来源仍是两套系统。

### 用户后果

用户导入自己的手册，界面显示入库成功，并说明内容能被检索；agent 随后查询的却仍是服务器上的公共资料。本地下载也不构成离线查询能力。
现有界面承诺文档仅存本地，与用户最新指定的后续服务器解析方向不同，未来实现时需一起调整说明。

### 修正方向

本项按用户要求延期。后续采用上传服务器解析/索引，由同一查询入口读取导入结果，并统一文档来源身份、处理状态和查询能力。
导入完成应表示正文确实已经可查，不能用“文件上传成功”代替“agent 可查询”。本轮不实现上传或部署。

### 验收

后续用带唯一短语的文档验证“上传 → 解析 → 索引 → agent 检索 → 章节/图片读取”，并验证处理中、失败和查询就绪的状态一致性。现有远端客户端单测不覆盖此链路。

## 2. 工具链解析与实际执行环境分开（P1，已确认）

### 证据

- `packages/kernel/src/host/session-manager.ts:908` 将项目工具链 PATH/exports 放进 `entry.shellEnv`，`:916` 交给 `NodeExecutionEnv`；进程全局 PATH 只加入机器级目录。
- `packages/kernel/src/host/tools/gdb/session.ts:404`、`:406` 调 `resolveGdbPath` 和 `serverBinary` 时没有传会话环境。两者默认读 `process.env`（`gdb/target.ts:402`，`gdb/servers.ts:84`）。
- `gdb/mi-session.ts:151` 和 `gdb/servers.ts:227` 自行 spawn，没有会话环境参数。
- 日志命令也相同：`log/session.ts:226` 构造采集器，`log/capture.ts:196` 自行 spawn，未传项目环境。
- `host/index.ts:176`、`:192` 的手填路径 RPC 只记账；`:208` 只有自动安装调用 `sessions.refreshMachineEnv()`。

### 隔离验证

临时探针通过真实 `resolveToolchain` 和 `shellEnvFor` 构造含项目 `YOMA_GDB={bin}` 的环境：`resolveGdbPath(..., sessionEnv)` 返回项目选定路径；同样调用若使用没有该配置的进程环境则报找不到 GDB。
探针只验证选址边界，用 Node 可执行文件作为占位路径，没有启动 GDB 或连接硬件。

### 用户后果

设置页/项目清单认为某版本可用，bash 也可用，内置 GDB 或日志工具却找不到，或者选择全局另一版本。
用户在已开会话里手填正确位置，页面更新了，而下一条执行仍使用旧环境；自动安装与手填路径的生效语义不同。

### 修正方向

形成会话级的执行环境快照，包含解析出的工具、PATH、exports 和配置版本；bash、PowerShell、GDB server/GDB、日志命令都显式消费它。
机器级配置变化统一发布更新，下一次工具调用使用新快照；已运行的硬件进程继续持有旧快照直到被关闭。
不能通过把项目专用 PATH 写进全局进程环境来修复，否则不同项目会互相影响。

### 验收

两个同时存在的项目选择不同路径、同名不同版本工具；分别经 bash、GDB 和日志命令观察实际启动路径与环境。
再验证手填路径、自动安装、重新探测之后，已开会话的下一次调用都按同一规则更新，现有进程不被中途改环境。

## 3. 记录路径不等于工具已就绪（P2，已确认）

### 证据

- `domain/toolchain/actions.ts:113`、`:114`：给了目录但找不到声明的可执行文件时，仍原样记录目录。这符合“允许用户先保存路径”的既有产品决定。
- `domain/toolchain/resolve.ts:146` 只要求记录路径存在；`:270` 在未声明版本范围时把没有版本信息也视为满足；`:297` 返回 `status: "ok"`。
- `packages/app/src/i18n/zh.ts:407` 将 `ok` 呈现为“已就绪”。
- `ToolSpec.bin` 同时表示 Arm 编译工具的“多个文件都需要”和 GDB 的“有一个替代即可”；`resolve.ts:165` 只要找到任何一个名称就算命中。

### 隔离验证

清空临时 Node 子进程的 PATH，将一个没有任何文件的目录保存为 `arm-gcc`，再读取 STM32 平台解析结果，实际得到：

```json
{"id":"arm-gcc","status":"ok","bin":{"empty-toolchain":"<临时空目录>"},"source":"ledger"}
```

测试只写 `out/architecture-audit/` 下的隔离账本。

### 修正方向

保留宽松的路径保存，不把它改成会卡住用户的强制安装验证。将“已记录位置”“已解析可执行入口”“版本满足”“本项操作可运行”分开表达。
为工具定义明确的入口要求（全部必需/候选替代），不要用“官方包通常一起安装”代替契约。
对 GDB/J-Link 等不支持标准 `--version` 的工具，使用适当的非破坏性能力验证或明确的未验证状态。

### 验收

空目录、错误可执行文件、缺少 objcopy 的部分工具链、GDB 替代入口、无标准版本输出和多版本并存；保存成功不能自动产生“已就绪”。

### 同一区域发现的 Windows 实现缺陷

审查时，`domain/toolchain/locations.ts:72` 的 `withPath` 只删除一个大小写不敏感命中的键。
若输入同时有 `PATH`、`Path`，重写后仍有两个键，`findEnvKey` 可先返回旧 `Path`。
本机隔离探针观察到真实 Node 子进程环境有这两个键；向空目录执行 `recordToolchainPath` 时错误地解析并记录了机器全局的 Arm 工具路径。
纯函数重现：`withPath({PATH:"old-a",Path:"old-b"}, ["chosen"])` 的有效查找值仍是 `old-b`。
此处已修改为删除全部大小写别名后写入唯一 PATH。新增两个回归场景，验证空的手选目录不会误命中全局工具、同名工具优先采用手选目录、输入环境不被修改。测试先在修复前失败；修复后 locations / resolve / ledger 共 100 项测试通过。
PATH 别名的实现修复与上述能力状态设计分别验证；能力状态已纳入后续实施范围。

## 4. 双平台交付尚缺 CPU 与便携性契约（P1，Mac 发布前必须处理）

### 证据

- `packages/desktop/scripts/stage-engines.ts:102` 有目标 CPU，用于下载资产名。
- 但 `localSatisfiesTarget` 的本地选择逻辑只检查魔数格式和存在至少一个本机格式文件，未检查 CPU。
- `verifyManifest` 没有校验 manifest 的平台/CPU；后续逐文件校验也只看 PE/Mach-O/ELF。
- 同文件 `nonPortable` 分支对 POSIX shebang 指向开发机的脚本仅发警告，并继续打包。
- `packages/desktop/package.json:20` 的 Mac 打包会直接走这条暂存链；`electron-builder.config.ts:141` 允许 DMG/ZIP，但没有在此为每个 CPU 独立绑定引擎资源。

### 用户后果

Apple Silicon 和 Intel 都是 Mach-O，现有验证无法证明目标 Mac 能运行全部引擎；某个开发机上的引擎还可能依赖本机虚拟环境。
这不是要求立即支持所有架构，而是每一个声称支持的目标都必须交付与之匹配的完整能力。

### 修正方向与验收

将引擎集合、版本、目标 OS/CPU、必需资源和入口协议组成发布清单；正式分发不接受开发脚本或不匹配 CPU。
在独立目标 runner 上验证安装后的实际功能，脱离源码目录、构建工具和开发机虚拟环境。
逻辑分析仪的解码器/FPGA 资源属于随安装包分发的资源，与用户本地 CubeMX 数据是不同生命周期，不应混进同一种缓存策略。

## 5. 退出预算与资源释放预算不一致（需专项实测）

### 已确认的代码事实

- `packages/desktop/src/main/kernel.ts:82` 发 stop 后仅等 3 秒，随即 `child.kill()` 并完成 stop。
- `packages/kernel/src/host/session-manager.ts:1444` 按顺序 dispose 各个工具，`:1468` 按顺序关各会话。
- `gdb/mi-session.ts:489` 的单个 GDB 关闭过程就可能等待 3 秒命令响应、5 秒自然退出以及后续强杀宽限；`gdb/servers.ts:343` 另外等待 server 退出。
- 主进程的私有文档解析在 `manuals.ts:569`、`:615` 仅对直接子进程 `.kill()`，不走内核已有的进程树关闭机制，也没有等待释放完成。

### 判断范围

这些预算不能互相保证，正常退出有可能抢在领域层清理完成之前终止内核。
本次没有起硬件进程，也没有验证 Windows utilityProcess 强制退出之后是否残留后代，因此**不把“必然留孤儿”写成已复现结论**。

### 修正方向与验收

由宿主统一管理退出阶段、截止时间和未释放的进程树，领域工具上报释放结果；先停止所有资源接收新任务，再并行释放，超时后由仍活着的父进程确认整棵树已结束。
使用假 GDB/日志/解析器进程，刻意延迟退出并派生子进程；在真实打包桌面宿主里测试关闭窗口、正常退出、升级退出和取消，验证所有 PID 与文件句柄都消失。

## 本次没有要求重构的部分

- 数据手册服务器地址已有统一解析实现；问题是查询与导入的数据来源没有统一，不是再写一份配置解析器。
- 会话重试状态来自内核事件，busy 不中断，前端只呈现；最新轮次归属已有独立修复。继续维护 live/replay 和忙碌状态不变量即可，本审查没有发现必须整体替换投影器的证据。
- 日志采集以流关闭作为结束依据，GDB 有明确目标状态、关闭检查和所有权；应补环境传递与宿主释放边界，不应重新实现它们的内部协议。
- 信箱的状态从原子提交后的文件推导，角色与项目路径分离，守护有退出杀树链；目前没有证据支持重新设计协议。不同宿主共享硬件的互斥策略是既有产品决策，不以本次审查为由擅自改权限体系。
