## 摘要

1. **yoma 的技能今天只有一条路:"系统提示词里的一张目录 + 模型自己用 `read` 去读 SKILL.md"**。内核开会话时扫三个目录(`~/.agents/skills`、`~/.yoma/skills`、`<cwd>/.agents/skills`),把名字、描述、绝对路径拼进 `<available_skills>`;唯一的"显式调用"是子 agent 定义里的 `skills:` 首轮预加载。**没有 Skill 工具、没有 `/技能名`、没有技能 RPC、没有任何技能界面、没有内置技能。**
2. **发动机其实已经把显式调用做了一半**:`lane.skill()`、`accept({kind:"skill"})`、`formatSkillInvocation`、`loadSourcedSkills`、`disable-model-invocation` 都现成,yoma 也把 `resources.skills` 喂进去了,但全仓零调用。改造**不用动发动机一个字**,全在 kernel / app / desktop / bench 侧。
3. **最该先修的是四个 bug**:① 技能诊断走 `kernel.error`,界面上**只响错误音、一个字都不显示**,每开一个会话(含每个子 agent、bench 每一轮)重复一遍;② SessionManager 调 `discoverSkills` **没传 `homeDir`**,测试读的是开发机真实的 `~/.agents/skills`;③ 信箱把技能诊断标成"**轮内 provider 错误(模型侧故障)**"送给研发端模型;④ 同名覆盖静默。另有:本机 `~/.agents/skills` 里 Claude Code 插件带来的技能(依赖 `$ARGUMENTS`、`${CLAUDE_PLUGIN_ROOT}`)被原样塞进 yoma 提示词、在 yoma 里跑不通;带 BOM、或 description 里有未加引号的半角 `: ` 的 SKILL.md 会被丢弃(分件验证过,见 Q7);仓库里被 gitignore 的 `routine-driven-development` 引用已移出主线的 `examples` 工具。
4. **主流做法已经收敛**:格式照 agentskills.io 开放规范;`.agents/skills` 是跨客户端约定(Claude Code 是例外,只扫 `.claude/skills`);项目级覆盖用户级且冲突要告警;列表有预算;**用户显式调用(`/名字` 或 `$名字`)是标配**;模型调用分"读文件派"(pi、Codex)与"专用工具派"(CC `Skill`、opencode `skill`、Gemini `activate_skill`)。pi 自己的文档承认读文件派"模型不总会去读"。
5. **推荐方案**(照 CC 的骨架、按 yoma 约束挑着抄):
   - 发现:保留三个目录、加祖先遍历(到 git 根,不在仓库里到 home)、加内置目录(最低优先级)、项目级 `.claude/skills` 兼容;冲突可见;诊断收进 `skill.list`,不再发 `kernel.error`;对 BOM 与"未加引号的冒号"宽松解析。
   - 注入:列表继续放系统提示词(会话内快照,fork / btw 前缀逐字不变),改用 yoma 自己的格式化函数:加预算、路径统一正斜杠。
   - 模型调用:新增一个 kernel 侧 `skill` 工具(静态描述、参数是名字 + 可选 args),`read` 保留为兜底。
   - 用户调用:`/技能名 参数`,**由内核在 `session.prompt` 里解析**(bench / 信箱白拿),前端只做补全与徽标;新增只读 RPC `skill.list`。
   - 管理:设置里加"技能"页(列表、来源、诊断、开 / 仅用户 / 关、打开目录);开关写 `~/.yoma/settings.json`。
   - 内置技能:走 extraResources + 新注入参数 `builtinSkillsDir`(信箱守护走环境变量),不进 asar、不往 `~/.yoma/skills` 拷。
   - 不照搬:`allowed-tools` 授权、正文 `` !`cmd` `` shell 注入、`model` / `effort` / `hooks` 覆盖、`paths` 条件激活。
6. **分期**:P0 修 bug + 用户调用闭环(约 4 人日,审校认为偏紧,见 §7);P1 `skill` 工具 + 预算 + 技能页 + 目录对齐 + 压缩保护(约 7 人日);P2 内置技能 + `context: fork` + 重载 + MCP 技能(约 10 人日,不含写技能内容)。§9 列了 11 个需要拍板的决定(其中 D9 请 ben 定)。

## 1. 背景:技能是什么、和别的东西怎么分工

### 1.1 Agent Skills 开放规范

Agent Skills 由 Anthropic 发起、后作为开放标准发布在 agentskills.io([规范](https://agentskills.io/specification),2026-09-25 访问;页面没有版本号)。规范**只定义技能目录里有什么**,不管放在哪、怎么列给模型、怎么激活、怎么授权 —— 这些全是宿主(yoma)的策略。

- **一个技能 = 一个目录**,至少有 `SKILL.md`;推荐的可选子目录:`scripts/`(可执行代码)、`references/`(按需读的文档)、`assets/`(模板、数据)。
- **frontmatter 只有 6 个字段**:

  | 字段 | 必填 | 约束 |
  |---|---|---|
  | `name` | 是 | 1–64 字符;只许 `a-z0-9-`;不以 `-` 开头 / 结尾;不含 `--`;**必须与父目录名一致** |
  | `description` | 是 | 1–1024 字符;写清"做什么 + 什么时候用" |
  | `license` | 否 | 许可证名或随附文件名 |
  | `compatibility` | 否 | 1–500 字符;环境要求 |
  | `metadata` | 否 | string→string 映射,客户端自定义字段放这里 |
  | `allowed-tools` | 否 | **实验性**;空格分隔的"预批准工具",各实现支持程度不一 |

- **渐进加载三层**:① 元数据(每个技能约 50–100 token,开会话就给模型);② 指令(SKILL.md 正文,建议 < 5000 token、< 500 行,激活时整份读入);③ 资源(scripts / references / assets,正文提到时才读)。
- 规范的[客户端实现指南](https://agentskills.io/client-implementation/adding-skills-support)对 yoma 最有用,要点:扫 `<项目>/.<客户端>/skills` + `<项目>/.agents/skills` + 用户级同名两处,可兼容 `.claude/skills`、可沿祖先到 git 根;**项目级覆盖用户级,冲突要告警**;项目级技能来自可能不可信的仓库,建议按"项目是否受信任"门控;**宽松解析**(未加引号的冒号要兜底修复,名字与目录不一致只警告);被禁用或 `disable-model-invocation` 的技能**从列表里直接隐藏**;专用激活工具的 `name` 参数最好约束在有效名字内;用户显式激活用 `/name` 或 `$name`;激活内容用结构化标签包起来,以便**压缩时豁免**、重复激活时去重。

Claude Code 在规范之上加了一大堆独有字段(`when_to_use`、`argument-hint`、`arguments`、`user-invocable`、`context: fork`、`agent`、`model`、`effort`、`hooks`、`paths`、`shell`、`disallowed-tools`……),官方文档明说分发到 claude.ai / Skills API 时只能用规范那 6 个字段([CC 技能文档](https://code.claude.com/docs/en/skills),"Using skill frontmatter outside Claude Code" 一节,2026-09-25 访问;原话 "Restricting frontmatter to the spec's six fields avoids the unexpected-key error")。

### 1.2 技能与系统提示词 / 上下文文件 / 子 agent / MCP 的分工

| 东西 | 进上下文的方式 | 适合放什么 | yoma 里在哪 |
|---|---|---|---|
| 系统提示词正文 | 每轮全文 | 产品身份、通用行为守则、工具守则 | `packages/kernel/src/host/system-prompt.ts` |
| 上下文文件(AGENTS.md / CLAUDE.md) | 每轮全文(`<project_context>`) | **这个项目**的约定:目录结构、构建命令、禁区 | `packages/kernel/src/host/resources.ts:51-84` |
| 技能 | 平时只有名字 + 描述,用到才读正文 | **某一类任务**的流程知识:"HardFault 怎么查""烧录失败怎么排",可带脚本与参考资料 | 本文主题 |
| 子 agent | 另开一个会话,只把结果带回来 | 需要隔离上下文、并行、或换工具集的任务 | `host/domain/agents/`、`host/tools/agent/` |
| MCP | 工具定义常驻(或延迟加载),调用走外部进程 / 服务 | **连接**外部系统:数据库、网页、云服务、别家的调试器 | yoma 还没有,见 [./02-MCP调研与yoma接入设计.md](./02-MCP调研与yoma接入设计.md) |

一句话:Anthropic 的定位是"**MCP 负责连接,技能负责教模型怎么用**"("MCP connects Claude to data; Skills teach Claude what to do with that data",claude.com/blog/skills-explained)。两者已经在协议层会师:MCP 官方扩展 `io.modelcontextprotocol/skills`(SEP-2640,已 Final)让 MCP 服务器也能分发技能([overview](https://modelcontextprotocol.io/extensions/skills/overview),2026-09-25 访问,原话"SDK and host support is still being implemented")。详细对比与 yoma 的 MCP 设计交给 02 号文档;本文只在 §6.10 讲技能这一侧要预留什么。

## 2. Yoma 现状(develop `fe811c7`)

### 2.1 端到端链路

```
openEntry(开会话 / 子会话 / LRU 淘汰后重开)
  ├─ discoverSkills(三个目录)  ──► 诊断:每条一个 kernel.error ──► app:错误音
  ├─ buildSystemPrompt(... skills)  ──► 有 read 工具才追加 <available_skills>
  ├─ AgentHarness.create({ resources: { skills } })  ──► lane.skill() 能用,但没人调
  └─ entry.skills = 快照
模型:看到目录 → 自己用 read 读 SKILL.md(读不读全凭模型)
子 agent:firstMessages 按 profile.skills 把技能正文拼成首轮 user 消息
```

逐步证据:

**① 发现**(`packages/kernel/src/host/resources.ts:86-112`)

- 三个目录按序加载,**后加载的覆盖先加载的**:`~/.agents/skills` → `<configDir>/skills`(缺省 `~/.yoma/skills`)→ `<cwd>/.agents/skills`(`resources.ts:95-101`)。去重就是 `Map.set`,**静默覆盖、不出诊断**(`:109-111`)。
- 不沿祖先目录找,注释给的理由是 Zed 时代的"Zed 会话的 cwd 就是项目根"(`:92-93`)—— Zed / ACP 路径已于 2026-09-09 删除(`a5292c8`)。对照:同仓的 agent 定义沿祖先找 `.yoma/agents`、止于 home(`host/domain/agents/load.ts:169-200`);上下文文件沿祖先一直走到根(`resources.ts:51-84`)。
- 调用点 `packages/kernel/src/host/session-manager.ts:1101-1108`,与 `loadContextFiles` 并发;**不传 `homeDir`**(`discoverSkills` 支持它,`resources.ts:104-107`)。快照式:每次 `openEntry` 读一次,会话内不变,改了技能要重开会话(注释 `:1104`)。
- 发动机 `loadSkills`(`packages/agent/src/harness/skills.ts:51-78`,与 pi 上游同文件逐字相同)的行为:目录里有 `SKILL.md` 就当技能根、不再往下递归;跳过 `.` 开头的项与 `node_modules`;读 `.gitignore` / `.ignore` / `.fdignore`;根目录下带 frontmatter 的 `.md` 也算技能;`name` 缺省取父目录名;名字校验(与目录名一致、≤64、`[a-z0-9-]`,`skills.ts:310-320`)**全部只是警告,技能照样加载**;缺 description → 诊断并丢弃;`Skill` 类型只保留 `name / description / content / filePath / disableModelInvocation`(`packages/agent/src/harness/types.ts:49-60`),**其他 frontmatter 字段全丢**,`parseFrontmatter` 也不导出。诊断只有一种级别(`type: "warning"`)和 5 个 code(`file_info_failed / list_failed / read_failed / parse_failed / invalid_metadata`,`skills.ts:12-29`);"缺 description 被丢弃"与"名字不合规但照样加载"**共用 `invalid_metadata`**,只能靠 message 或"该路径有没有产出技能"来区分(F6 分级要用到)。Windows junction 被当作 symlink,能正常加载,`filePath` 是链接路径。

**② 诊断**(`session-manager.ts:1109-1117`)

每条诊断 `emit` 一个 `{ type: "kernel.error", sessionID, message: "技能 <code> <path>:<message>" }`。app 侧(`packages/app/src/context/notification.tsx:309-338`、`:343-356`):

1. `settings.sounds.errorsEnabled` 缺省 `true` → **播放错误音** `nope-03`(`packages/app/src/context/settings.tsx:99-104`);
2. 往通知 store 里 `append` 一条 `type: "error"`;
3. 系统通知缺省**关**(`settings.tsx:95-98`),开了正文也是会话标题,不是错误文字;
4. store 里的 `unseenHasError` **没有任何组件读**(全仓 grep 只在 `notification.tsx` 内部出现)。

所以一个格式不对的技能在界面上的真实后果:**每次开会话连响 N 声错误音,屏幕上什么都没有**。仓库 `CLAUDE.md` 与 `session-manager.ts`、`host/session-title.ts` 里"kernel.error 会弹系统通知、把会话标红"的描述与现状不符。

**③ 注入系统提示词**(`packages/kernel/src/host/system-prompt.ts:181-184`)

- **只在 `tools.includes("read")` 且技能非空时**追加 `\n\n` + 发动机的 `formatSkillsForSystemPrompt(skills)`(`packages/agent/src/harness/system-prompt.ts:3-25`):三句英文说明 + `<available_skills>`,每项 `<name>/<description>/<location>`,过滤掉 `disableModelInvocation`。全被过滤时发动机返回 `""`,yoma 仍会追加一个孤零零的 `\n\n`。
- 位置:正文 → `appendSystemPrompt` → `<project_context>`(含 `<project-memory>`、`<toolchain>`)→ **技能块** → `Current working directory:`(主会话,`:196`)或 `<env>`(子 agent)。
- 会话内字节稳定(`discovered.skills` 被闭包定住),不破坏前缀缓存。fork(/btw 转后台)用主会话那份系统提示词原字符串(`session-manager.ts:1119-1122` 注释),/btw 用主会话"最后一次真发出去"的那份(`:2408-2420`)。
- `location` 是原样的绝对路径:Windows 上是反斜杠 + 用户名(本机实测 `C:\Users\<用户>\.agents\skills\understand\SKILL.md`),而同一提示词里 cwd 被规整成正斜杠 —— 分隔符不统一。
- 没有体积预算。本机实测 9 个技能 ≈ 3.1 KB(约 800 token),每个请求都带。

**④ 模型调用**:只能靠模型自己 `read`。发动机提供的显式调用 `AgentLane.skill(name, additionalInstructions, ctx)`(`packages/agent/src/harness/agent-harness.ts:552`,实现 `runtime/lane.ts:1147-1152`)与 `OperationRequest` 的 `{ kind: "skill" }`(`agent-harness.ts:114`;`lane.ts:529-541` 按名字查 `resources.skills`、找不到回 `UnknownSkill`、找到就造一条普通 user 消息 `formatSkillInvocation(skill, args)`)—— yoma 全仓零调用。`session-manager.ts:1262-1263` 的注释写着"lane.skill() 从这里查技能",`LANE_ERROR_TEXT.UnknownSkill = "没有这个技能"`(`:293`)是走不到的预留代码。注意 `lane.skill` 走的是 accept + drive:**不收图片、忙时返回 `LaneBusy`、不能排进收件箱**。

**⑤ 子 agent 预加载**(`session-manager.ts:2665-2688` 的 `firstMessages`):对 `profile.skills` 里每个名字,在子会话自己发现的 `entry.skills` 里找,找到就 `userMessage(formatSkillInvocation(skill))` 放在任务书之前;找不到发 `kernel.error`。`skills:` 字段解析在 `host/domain/agents/load.ts:132-134`。内建三个 agent 都没用它。fork 的首轮是继承的种子,不走预加载。子会话页上这些预加载消息会以整段 `<skill …>` 原文显示成用户气泡 —— 投影器的 `userText` 只特殊处理了 fork 守则(`packages/kernel/src/host/projector.ts:60-62`)。**[推断,未在界面实看]**

### 2.3 协议与前端

- 浏览器安全面(`packages/kernel/src/{protocol,types,client,index}.ts`)**没有任何技能相关的类型、RPC、事件**。可参照的同类是 `agent.list`(`protocol.ts:178`,现读现算、按目录;但 app 里目前没人调它)。

- 斜杠命令:只有前端内置的 `/new` `/undo` `/compact` `/btw` `/open` `/model`(`packages/app/src/pages/session/use-session-commands.tsx:184-231`、`use-composer-commands.tsx:38`);候选只从 `command.options` 里取(`components/prompt-input.tsx:623`);`slash-popover.tsx:8` 的注释明说"内核没有自定义命令,也没有 MCP prompt / skill"。
- 提交拦截:`components/prompt-input/submit.ts:302-308` 在一切发送逻辑之前用 `parseBtw` 截走 `/btw` —— 这是现成样板。
- 设置页 `components/settings-v2/dialog-settings-v2.tsx`:`general` / `providers` / `models` / `toolchain` 四页,没有技能页。

### 4.2 值得借鉴 / 不该照搬

**值得借鉴**

1. **用户显式调用**(所有家都有):照 CC / opencode / Copilot 用 `/名字 参数`,用户有肌肉记忆。
2. **专用工具激活**(CC、opencode、Gemini、Cline):结构化包装便于压缩豁免、去重、统计、拒绝"仅用户"技能;规范指南列了 5 条好处。
3. **冲突可见**(pi 的 `collision` 诊断带赢家 / 输家路径;规范指南)。
4. **列表预算**(CC 1%、Codex 2%)——国产模型窗口普遍 64k–128k,比 CC 更要紧。
5. **压缩后重附**(CC 5k / 25k)与**重复激活去重**(CC 文档 "Skill Content Lifecycle")。
6. **三态开关**(CC `skillOverrides`、Codex `[[skills.config]]`)。
7. **内置技能**(Codex 按指纹写盘、CC 首次调用解压):yoma 的领域知识正适合做成技能。
8. **宽松解析**(Codex 对"值里带冒号"修复一次再解析,`codex:codex-rs/skills/src/parser.rs:44-60,98-180`:把值整体包成单引号字符串后重试;规范指南建议"加引号或改块标量")。
9. **`opencode` 的工具结果形态**:`<skill_content>` + 正文 + Base directory + 文件取样,简单、对前缀缓存友好。
10. **Codex 的"怎么用技能"说明**(`codex:codex-rs/ext/skills/src/catalog_prompt.rs:24-40`):点名或明显匹配就必须用、读完整、相对路径相对 SKILL.md、优先跑 `scripts/`、宣布用了哪个 —— 可以浓缩进 yoma 的列表说明。

**不该照搬**

1. **`allowed-tools` 当临时授权**:yoma 自 2026-08-10 起没有权限系统,照搬没意义,还可能被误读成"技能能跳过烧录确认"。解析、展示,**不产生任何授权效果**;确认门永远生效。MCP 技能扩展也要求这类授权逐技能显式同意。
2. **正文 `` !`cmd` `` shell 注入**:加载即执行、先于模型看到;CC 自己后来陆续补了 `disableSkillShellExecution`、同步技能禁用、auto 模式改规则;Windows 上没 Git Bash 就失败;在接着硬件的机器上等于绕开确认门执行命令。
3. **`model` / `effort` / `hooks` 按技能改运行时**:yoma 用户各配各的国产模型与凭据,技能作者写死的模型名多半不可用;yoma 也没有 hooks 系统。
4. **CC 的生态重装备**:`.claude/commands` 合流、插件市场、账号同步、技能检索(`EXPERIMENTAL_SKILL_SEARCH`)—— 与 yoma 当前规模不匹配。
5. **`paths` 条件激活 + 读文件时动态发现嵌套技能**:每读一个文件都可能改变技能列表,打断缓存、行为难预期;嵌入式工程大多是单一项目根,祖先遍历够用。
6. **CC 的"列表放 system-reminder、增量公布"**:它的前提是 Skill 工具 + 热重载;yoma 目前快照式、没有热重载,放系统提示词更简单且同样缓存稳定(见 §5 原则 3)。等做热重载(P2)再考虑增量公布。

## 5. 改造目标与原则

**目标**:让技能在 yoma 里"**能看见、能点名、能管、模型会用、不出怪声**",并为内置嵌入式技能和 MCP 技能留好位置。

**原则**(每条后面是理由):

1. **发动机一个字不改**。`packages/{agent,ai,chord,telemetry}` 哈希锁定;需要的东西(`loadSkills`、`loadSourcedSkills`、`formatSkillInvocation`、`Skill` 类型、`before_compaction`、会话值 `value()`)都是公开接口。发动机不支持的(多余 frontmatter 字段、BOM、冒号修复、预算、来源)全在 kernel 侧包装。
2. **浏览器安全边界不破**。新类型进 `packages/kernel/src/types.ts` / `protocol.ts`(只许纯类型与 typebox);技能工具的契约 `host/tools/skill/contract.ts` 只 import typebox;读文件、解析 YAML 全在 `host/`。`host/boundary.test.ts` 的门规照旧。

### 6.10 与 MCP 的接口预留(P2,细节见 [./02-MCP调研与yoma接入设计.md](./02-MCP调研与yoma接入设计.md))

- `SkillInfo.source` 留 `"mcp"`;MCP 技能的身份是"服务器 + URI",名字不保证唯一(扩展原文:"Names are labels and are not guaranteed to be unique. Hosts **MUST** preserve both server identity and URI"),同名时以 `服务器:名字` 限定,**不许静默覆盖**本地技能("Prevent skills with the same name from silently replacing one another" 也是 MUST)。
- 协议形状(2026-09-25 核 overview 页):服务器在 `server/discover` 里声明 `io.modelcontextprotocol/skills` 扩展(示例基于协议修订 `2026-07-28` 及以后),客户端用 **`skills/list` / `skills/get`** 拿条目(frontmatter + 带 SHA-256 与字节数的完整文件清单),文件内容走 `resources/read`,可选 `resources/directory/read`。
- `skill` 工具按名字解析时能落到 MCP 来源:正文经 `resources/read` 取、按清单校验字节数与 SHA-256、再逐字段比对 frontmatter,内容一律当不可信输入;宿主不预取文件("including on connection, listing, or approval",扩展的 MUST)。
- **与"没有权限系统"的冲突由 02 号文档拍板**(02 §5.9 已给推荐:只实现下面第二种子集,剩下的同意复用 MCP server 的配置批准,项目级批准绑定清单 digest):扩展有几条 MUST 级的同意要求 —— 激活嵌套技能前要"fresh user consent"、跨服务器读要"per-call approval"、`allowed-tools` 这类授权与宿主侧执行代码要逐技能同意、持久化的同意要绑定整份清单的 digest。yoma 要么为 MCP 技能单开一道确认(类似确认门),要么只实现不触发这些条款的子集(不做嵌套技能、不跨服务器、`allowed-tools` 不授权)。
- `/` 候选的 `source` 同时承载 MCP prompts(`"mcp"`),与技能共用一套补全与徽标。
- 技能声明依赖某个 MCP 服务器(Codex `agents/openai.yaml` 的 `dependencies.tools`)—— 等 MCP 落地后再议。

## 8. 风险与未决问题

1. **上游升级**:`loadSkills`、`formatSkillInvocation`、`Skill` 类型是发动机的公开接口,上游改了措辞或字段,yoma 的包装与投影器反解析会跟着变。缓解:U3 的反解析与 F3 的包装各有用例;`npm run upstream:check` 升级时先跑这些。
2. **内核解析 `/名字` 的误伤**:用户真想发一条以 `/某技能名` 开头的普通消息时会被展开。概率低(技能名是 `a-z0-9-` 且必须命中);CC 也是这么做的。没有转义语法,若有反馈再加(例如开头多一个空格)。
3. **弱模型乱调 `skill`**:多一个工具定义(约 150–250 token),模型可能频繁调无关技能。缓解:列表说明写清"匹配才调";去重;技能页 token 估算让用户知道成本。需要 DeepSeek / Kimi 真机观察。
4. **提示注入与供应链**:项目技能不设信任门控(D8),打开陌生仓库时它的技能描述会进系统提示词,正文在被调用时进上下文。这与"无权限系统"的产品决定一致,但要写进用户文档;确认门兜底硬件动作。MCP 技能按 SEP-2640 当不可信输入。
5. **压缩保护方案未实测**:排队 custom 消息的做法依赖收件箱在空闲时入队、下一轮带上(v0.4 已核实 steer 的这一语义),但 custom 消息对各 provider 的投影、与 fork 种子的交互还没验证。
6. **预算用的 `contextWindow`** 来自模型目录,国产模型目录项可能缺或不准;缺时回落 8000 字符。
7. **Windows 路径**:junction、长路径、带空格的安装路径(`C:/Program Files/Yoma/resources/skills`)进提示词;内置技能的 `scripts/` 必须在没有 bash 的 Windows 上能跑(或只用 PowerShell / node)。
8. **信箱两端技能不对称**:本方案只做"告知",不做分发;真要分发得改信箱协议。
9. **CC 生态在快速变化**:本文引用的 CC 行为基于 2.1.88 源码 + 2026-09-25 的官方文档;字段与默认值(如 fork 默认后台)还会变,"照 CC 做"的条目落地前再核一次。
10. **祖先遍历与 CC 的已知差异**:cwd 在工程内嵌的 submodule / vendored 仓库里时,CC 会把边界放宽到外层工程根,yoma 本期只停在最近的 git 根(F1),外层工程的 `.agents/skills` 看不到。
11. **未决**:agent 定义的祖先规则要不要与技能统一(F1);agent 定义诊断同样逐条 `kernel.error`,要不要一起改(A2);`/名字` 一行叠多个技能(CC 2.1.199)要不要做;技能页要不要显示"本会话实际用到了哪些技能"(CC `/skill-doctor` 的思路)。
