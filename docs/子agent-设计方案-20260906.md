# 子 agent 设计方案(草案 v0.1,2026-09-06)

worktree:`D:\MyCode\yoma\yoma-pi-subagent`(分支 `subagent`,自 develop d1e7825 开出)。
阅读范围:`packages/agent`(循环 / harness / 会话树 / 存储)、`packages/kernel/src/host`(会话管理 / 投影器 / 协议)、
`packages/coding-agent`(工具定义 / 系统提示词 / 资源发现 / ACP 适配器)、`packages/app` 的相关残留。

## 0. 一句话结论

- **现状:内核没有"agent 身份"这个概念。** opencode 里一个 agent = 一份 prompt + 一组权限/工具 + 一个模型(+ mode);
  yoma 里这四样要么写死、要么按会话临时选、要么已被删除。每个会话的"身份"就是宿主装配 harness 时传进去的那一组参数,
  而且所有会话拿到的是同一组(只有 model / thinking / cwd 三个变量)。
- **方案:子 agent 是应用层的组合,内核(`packages/agent`)几乎不改。** 三个新东西:
  `AgentProfile`(身份的数据形状 + 注册表)、`task` 工具(委派,spawn 由宿主注入)、
  `SessionManager.spawnSubagent()`(开一个带 parent 元数据的子会话、装配、跑到底、把结论当工具结果还回去)。
  子会话复用现有的一切:harness / 投影器 / 事件流 / 自动重试 / 自动压缩 / JSONL 落盘。

## 1. 现状:agent 身份在内核里是怎么定义的

对照 opencode 的四要素:

| opencode 的 agent 要素 | yoma-pi 现状 | 落点 |
|---|---|---|
| prompt(persona) | **一份字面量**:`You are Yoma, a coding and embedded-development agent.`;提示词 = f(工具集, 项目上下文文件, 技能, cwd) | `packages/coding-agent/src/core/system-prompt.ts:111`;`buildSystemPrompt` `:50`;`collectToolPromptData` `:33-47` |
| 工具/权限组 | 工具是**固定拼接**:编码 6 件(read/bash/edit/write/toolchain/examples)+ 嵌入式 8 件(netlist/datasheet/stm32config/flash/log/gdb/la/scope)= 14;按名挑选的装配面 2026-08 删了;**权限系统 2026-08-10 整体删除** | `packages/coding-agent/src/core/tools/index.ts:259-291`;桌面端 `packages/kernel/src/host/session-manager.ts:81-97, 530-542` |
| 模型 | **按会话现场选**(`session.setModel` → 会话树里一条 `model_change` 条目),默认 = `resolveModel()` 的顺序:`YOMA_PROVIDER/MODEL` 环境变量 → `~/.yoma/settings.json` → 第一个配了 key 的 provider;**不存在按 agent 绑模型** | `packages/coding-agent/src/acp/models.ts:143, 157-181`;`session-manager.ts:356-377` |
| mode(primary/subagent) | 没有。最接近"模式"的是 thinking 档位;ACP 的 modes 被挪用来表示思考档位 | `packages/kernel/src/thinking.ts`;`packages/coding-agent/src/acp/agent.ts:311-322` |

五个关键事实:

1. **harness 层没有"agent"**。`AgentHarnessOptions`(`packages/agent/src/harness/types.ts:533-569`)只有
   `systemPrompt`(字符串或回调)/ `model` / `thinkingLevel` / `tools` + `activeToolNames` / `resources`(技能、模板)。
   身份 = 宿主把这几样凑成什么。两个宿主各凑一遍:桌面端 `session-manager.ts:466-581`(`ensureOpen`),
   Zed 的 ACP 适配器 `coding-agent/src/acp/agent.ts:403-472`(`setupSession`),形状一模一样。
2. **会话树里有"身份变更"的条目,但没有"身份"本身。** `model_change` / `thinking_level_change` / `active_tools_change`
   都是追加式条目(`harness/types.ts:186-200`),`buildContext()` 扫全路径推导当前值(`session/session.ts:44-62`)。
   其中 `active_tools_change` 只有内核自己写,宿主从未用过 —— 这是"按 agent 缩工具集"的现成机制。
3. **两个已定义、零调用的钩子**:`BuildSystemPromptOptions.customPrompt` / `appendSystemPrompt`
   (`system-prompt.ts:13-30`),以及 `JsonlSessionRepo.fork()` 与会话头里的 `parentSession` / `metadata`
   (`harness/types.ts:328-332`;`jsonl-storage.ts:14-22`)。父子会话的链接位在存储层**已经存在**。
4. **会话是平的。** 视图 `Session`(`packages/kernel/src/types.ts:24-44`)没有 `parentID`;`types.ts:9-15` 的删除清单明写
   "subtask 没有子代理 / agent 只有一个系统提示词,没有 persona";app 侧 `server-session.ts:8`、
   `session-composer-region-controller.ts:19` 都注释了"没有子会话"。i18n 还剩两条尸体
   `session.child.promptDisabled` / `session.child.backToParent`(`app/src/i18n/en.ts:127-128`),storybook 有 `task` 卡片夹具。
5. **唯一的"多 agent"是信箱闭环的 mother/runner**,那是跨机器、经 git 仓库、各自一整个内核宿主,
   角色差异 = 首轮用户提示词 + 宿主选项,不是注册表。

所以对"opencode 里 agent = prompt + 权限组 + 模型"这个理解:对,而且 yoma 现在恰好三样都没绑 —— 这正是设计要补的东西。

## 2. 目标与非目标

目标(v1):

- 一个**具名的 agent 身份**(profile):prompt 片段 + 工具子集 + 可选的模型/思考档位 + mode。内建几份,用户可用 md 文件加。
- 主 agent 能用一个 **`task` 工具**把自包含的子任务委派给某个子 agent,子 agent 在**独立会话、独立上下文**里跑到底,
  只把结论(最后一条 assistant 文本)带回主会话的工具结果里。
- 子会话在桌面端**可见、可回放、可停止**:侧边栏嵌套在父会话下,父会话里的 task 卡片能跳到它。
- 关掉再开(进程重启后)父子关系与子会话的身份都能从 JSONL 恢复。

非目标(v1 不做,留 P4):

- 子 agent 再开子 agent(深度 > 1)。
- 多个子 agent 并行。
- Zed(ACP)侧的委派。
- 在父会话的 task 卡片里实时流子 agent 的输出(现在 `tool_execution_update` 根本不投影,见 §7)。
- 主 agent 的"切换 persona"UI(协议先留 `agent` 字段,UI 后补)。

## 3. 设计

### 3.1 AgentProfile:身份的数据形状

新文件 `packages/coding-agent/src/core/agents.ts`(与 `resources.ts` 同层:这是产品决策,不是内核机制)。

```ts
export interface AgentProfile {
  name: string;                 // 稳定 id:小写字母/数字/连字符,同技能命名规则
  description: string;          // 给主 agent 看的一句话:什么任务该交给它(进 task 工具的说明)
  mode: "primary" | "subagent" | "all";
  prompt?: string;              // 角色段,默认 **追加** 到 Yoma 正文之后(appendSystemPrompt)
  replacePrompt?: boolean;      // true 时改走 customPrompt,整段替换(专家用,默认 false)
  tools?: { include?: string[]; exclude?: string[] };   // 按名筛工具;缺省 = 全部
  model?: { provider: string; id: string };             // 缺省 = 继承父会话当前模型 / 宿主默认
  thinkingLevel?: ThinkingLevel;                        // 缺省 = 继承
  maxTurns?: number;            // 子 agent 轮数上限,0 = 不限;primary 忽略
  filePath?: string;            // 来自磁盘时的位置,诊断用
  builtin?: boolean;
}
```

来源与优先级(后者按 name 覆盖前者,和技能一样):

1. 内建注册表 `BUILTIN_AGENTS`(代码里);
2. 全局 `<configDir>/agents/*.md`(默认 `~/.yoma/agents/`,与凭据/技能同一个目录);
3. 项目 `<cwd>/.yoma/agents/*.md`(`.yoma/` 是 yoma 在用户项目里唯一的落脚点;它的 `.gitignore` 是黑名单式,
   `agents/` 不在黑名单里就会随项目提交 —— 实施时核对 `ensureYomaDir` 的黑名单常量)。

文件格式照技能:frontmatter + 正文即 prompt。frontmatter 字段:`name`(缺省取文件名)、`description`(必填,缺了不加载)、
`mode`、`tools`(数组;`-name` 表示排除)、`model`(`provider/id`)、`thinking`、`max-turns`、`replace-prompt`。
解析复用 `packages/agent/src/harness/skills.ts` 里的 `parseFrontmatter`(现在是模块私有,导出即可)。
校验同技能的"宽松警告"式:引用了不存在的工具名 → diagnostics,不拒载。

内建三份(v1):

| name | mode | 工具 | 用途 |
|---|---|---|---|
| `yoma` | primary | 全部 + `task` | 今天的默认 persona,行为逐字节不变 |
| `explore` | subagent | read / bash / examples / toolchain | 只读侦察:工程结构、符号、构建方式;回一份带路径的报告 |
| `datasheet` | subagent | datasheet / read / examples | 查手册取证:回带页码/章节引用的事实,不进父会话的上下文 |

**v1 不给子 agent 任何会动板子的工具**(flash/log/gdb/la/scope/stm32config/netlist 之外的 flash 类),理由见 §4 决策 2。
`general`(全部工具减 task)作为可选第四份,由决策 2 定。

### 3.2 身份如何施加:一个共享的装配函数

把 `session-manager.ts:466-581` 的 `ensureOpen` 中"从 (cwd, 工具链, 模型) 装出 harness"那一段抽成
`assembleHarness(entry, profile, inherit?)`,主会话与子会话都走它。profile 施加在四个点:

1. **工具集**:`selectTools(allDefinitions, profile.tools)` 按名过滤;然后按 mode 决定要不要加 `task`
   (primary/all 加,subagent 不加 —— 这就是深度 1 的实现,零额外状态)。
2. **系统提示词**:`buildSystemPrompt({ appendSystemPrompt: profile.prompt, customPrompt: replace ? prompt : undefined,
   ...collectToolPromptData(selected), cwd, contextFiles, skills })`。`collectToolPromptData` 从工具定义反推工具清单与守则,
   所以工具子集一变,提示词自动跟着变,不需要另写一份。
3. **模型 / 档位**:`profile.model` 存在且 `models.getModel()` 找得到就用它;找不到(该 provider 没配 key)
   → 退回继承值并发一条 `kernel.error`,**不让委派失败**。继承值 = 父会话 harness 当前的 `getModel()` / `getThinkingLevel()`。
4. **会话头元数据**:子会话 `repo.create({ cwd, parentSessionPath, metadata: { agent, parent: { sessionID, toolCallID } } })`。
   `ensureOpen` 重开任何会话时先看 `meta.metadata.agent`,按它挑 profile 再装配 —— 重启后子会话的身份不丢。
   主会话不写 `agent`(等价于 `yoma`),老会话文件全部兼容。

### 3.3 `task` 工具:委派

新文件 `packages/coding-agent/src/core/tools/task.ts`,形状是普通 `ToolDefinition`(`core/tools/types.ts:14-34`),
与其他工具唯一的差别是**它不知道怎么开子会话**,那件事由宿主注入:

```ts
export interface SubagentRequest { agent: string; description: string; prompt: string; parentToolCallID: string }
export interface SubagentResult {
  sessionID: string; status: "completed" | "aborted" | "error";
  text: string;                       // 子 agent 最后一条 assistant 的文本(非 synthetic)
  turns: number; usage: { input: number; output: number; cost: number }; durationMs: number;
  error?: string;
}
export type SpawnSubagent = (req: SubagentRequest, signal?: AbortSignal,
                             onUpdate?: (partial: TaskToolDetails) => void) => Promise<SubagentResult>;

createTaskToolDefinition(profiles: AgentProfile[], spawn: SpawnSubagent): ToolDefinition
```

- `parameters`:`agent`(枚举 = mode ∈ {subagent, all} 的 profile 名)、`description`(≤ 60 字,做子会话标题与卡片标题)、
  `prompt`(完整任务书)。
- `description` 动态生成:列出每个可用子 agent 的 name + description,模型据此选人 —— 与 opencode 的 Task 工具同款。
- `promptSnippet` / `promptGuidelines`(进系统提示词):何时委派(上下文重、结论轻的子任务:大范围翻代码、查手册取证),
  何时不委派(需要父会话上下文的事、用户要盯着看的硬件操作);**子 agent 看不到你的对话,任务书必须自包含**;
  拿回的是二手结论,涉及寄存器/时序的断言要在父会话里按证据规则复核。
- `executionMode: "sequential"`:循环里只要一批工具调用中有一个 sequential 就整批串行(`agent-loop.ts:406-409`),
  于是模型一次发两个 `task` 也不会并行开两个子 agent(决策 1)。
- `execute`:调 `spawn`;`signal` 直接透传(父会话被停 → 子会话被停);结果映射:
  completed → `content` = text + 一行"完整过程见子会话 <id>",`details` = 全部字段;aborted / error → `isError: true`。

### 3.4 宿主:`SessionManager.spawnSubagent()`

流程:

1. 从注册表解析 profile(内建 + 父会话 cwd 下发现的文件,与 `ensureOpen` 时同一份快照);不是 subagent/all → 直接返回错误结果。
2. 建子会话(§3.2 第 4 点),`Entry` 新增 `parentID` / `agent` 两个字段;标题 = description(`appendSessionName`);
   发 `session.created`(视图带 `parentID`、`agent`),侧边栏由此嵌套。
3. `assembleHarness(childEntry, profile, inherit = parentEntry)`;投影器、`harness.subscribe → project()` 与主会话完全一样,
   子会话的事件用**子会话自己的 sessionID** 流向前端,**协议不加任何新事件类型**。
4. 跑:把 `prompt()` 的"发起一轮 + 自动重试 + 溢出压缩"那段(`session-manager.ts:764-878`)重构成
   `runTurn(entry, text): Promise<AssistantMessage>`,RPC 的 `prompt()` 不 await 它,`spawnSubagent` await 它。
   子会话因此白得轮级重试、溢出压缩、"重试期间压住 idle"这些既有策略。
5. 中止链:父会话 stop → `abort(parentID)` → 父 harness 的 loop signal → task 工具的 `signal` → `abort(childID)`;
   子 `prompt()` resolve(中断是数据),工具返回 `aborted`。直接在 UI 上停子会话也成立:工具拿到 aborted,父会话继续。
6. 轮数上限:在子 harness 的 `subscribe` 里数 `turn_end`;到 `maxTurns` 时 `harness.steer("轮数已到上限,立即给出结论")`,
   到 `maxTurns + 3` 硬 `abort`。这是安全网不是裁决(与调试台"代码不裁决"的原则不冲突:用户随时能停)。
7. 结果:最后一条 assistant 的 text parts(排除 synthetic,与 bench `result.text` 同一条规则);
   usage = 子会话本轮全部 assistant 消息的 usage 求和;`turns` = `turn_end` 计数。
8. 完成后子 Entry 保留为 idle(可回放),交给现有的 LRU 淘汰(`MAX_LIVE_SESSIONS = 8`,`session-manager.ts:72`)。

父子链接**不需要**在父会话树里加 `custom` 条目:父会话的 transcript 本来就记着 `task` 的调用与结果(`toolResult` 消息的
`details.sessionID`),重开父会话时投影器照常把它投成卡片,UI 从 `details` 拿子会话 id 即可。

其他宿主行为:

- `session.prompt` 打到子会话 → 拒绝,错误 `data._tag = "SubagentSessionError"`(复活 i18n 的 `session.child.promptDisabled`);
  v2 可加"提升为顶层会话"。
- `session.delete(parentID)` 级联删子会话(按 `list()` 里的 `parentID` 找)。
- `session.list(directory)` 本来就会把子会话列出来(同一个 `--<cwd>--` 目录),所以视图**必须**带 `parentID`,前端据此嵌套/折叠。

### 3.6 `packages/agent` 的改动

几乎为零,这是方案的主要优点:

- `harness/skills.ts`:导出 `parseFrontmatter`(agent 文件复用)。
- 其余全部是既有机制:一个 harness 一个会话、`JsonlSessionCreateOptions.parentSessionPath/metadata`、

### 3.7 另外两个宿主

- **bench / 信箱**:走 `createKernelHost()`,只要在 `SessionManager` 里注册了 `task`,mother 端自动有委派能力
  (研发端翻代码、查手册正是 explore/datasheet 的用武之地);runner 端没有项目检出,explore 基本无用但无害。
  一轮一个子进程的不变式不受影响(子 agent 在同一个子进程里跑完)。
- **ACP(Zed)**:`setupSession()` 是 `ensureOpen` 的孪生,同样可以注入 spawn;但 Zed 没有"子会话"的展示位,
  v1 不注入(spawn 缺席 → 不注册 `task` 工具,提示词里也就没有它),留 P4。

## 4. 需要拍板的决策

1. **并行**:v1 串行(`executionMode: "sequential"`)。备选:只读 profile 允许并行 —— 收益是省时间,代价是 bash 工具
   在两个子 agent 里同时跑与探针无关但会抢 CPU/文件,先不做。
2. **子 agent 能不能碰硬件**:建议 v1 不能。父 agent 是"板子状态叙事"的唯一持有者,persona 的证据规则要求
   运行时行为要有 log/gdb 证据,子 agent 回来的是二手摘要;而且 probe 租约 / gdb 会话表 / log 采集是模块级全局,
   子 agent 用完不释放就是父会话撞 `0xe00002c5`。要做 `general` 的话,建议排除 flash/gdb/log/la/scope。
3. **轮数上限**:默认 40、可按 profile 改、0 不限;还是完全不设(与调试台"代码不裁决"一致)?建议设,理由是子 agent
   不在用户眼皮底下,而且父会话被它阻塞着。
4. **子会话能否直接对话**:建议 v1 不能(opencode 同款),避免"子会话被追问后,父会话工具结果与子会话内容不一致"。
5. **费用归属**:子会话的 token/费用只在 task 卡片与子会话自己里显示,不并入父会话的会话级汇总;要并入需要前端改汇总逻辑,后议。
6. **agent 文件的项目位置**:`<cwd>/.yoma/agents/`(与 `.yoma/toolchain.json`、`bench/mailbox.template.json` 同类的"要提交的项目配置")
   还是 `<cwd>/.agents/agents/`(挨着项目技能)?建议前者。

## 7. 风险与坑(实施前再读一遍)

- **模块级全局**(probe 租约 / gdb 表 / log 采集,`coding-agent/src/core/tools/engines.ts`):子 agent 与父 agent 在同一进程,
  串行 + 不给子 agent 硬件工具是 v1 的护身符;放开任何一条之前先想清楚释放路径。
- **循环默认并行工具**(`agent-loop.ts:398-413`):task 必须 `sequential`,否则两个 `task` 调用会并发开两个子会话。
- **`tool_execution_update` 不投影**(`session-manager.ts:656-657` 只处理 `tool_execution_start`):父卡片上看不到子 agent 的进度,
  v1 靠子会话自己的流;不要试图从 task 工具的 `onUpdate` 往父卡片塞进度,先修投影。
- **`TOOL_NAMES` 闸门**(`kernel/src/host/tool-names.test.ts`)会因 `task` 变红,这是预期,顺手补 types/details-check/session-ui 渲染表。
- **`smoke` 数 14 个工具**:改成 15 并同步 CLAUDE.md。
- **LRU 淘汰**(`evictIdle`):子会话跑完是 idle,可能被淘汰,只丢内存态不丢磁盘,重开走 `ensureOpen` 按元数据装配 —— 所以元数据里的 `agent` 是硬需求。
- **contextBridge 剥 Error**:`SubagentSessionError` 必须走 `data._tag`,与 `SessionNotFoundError` 同款,否则前端崩到错误页。
- **faux provider 共享队列**:测试里父子 steps 的顺序要按执行序排。
- **内核没有 HMR**:改完 host 要重启 `bun dev:desktop`。
- **`.yoma/.gitignore` 黑名单**:确认 `agents/` 不在里面,否则用户写的项目 agent 文件提交不进去。
