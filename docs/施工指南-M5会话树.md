# M5 施工指南：会话树（session 层）

> 你问"agent-harness.md 看不懂，从哪里入手"。答案：**不从它入手。**
> agent-harness.md 是 M7 的图纸，而 M7 站在 M5（会话树）和 M6（执行环境）两块地基上。你现在读不懂它，不是水平问题，是它描述的四类状态里有一类（session）在你的世界里还不存在。**先把 M5 建出来，再回头读它，会突然变得可读。**
> 行号均指 pi-minimal。日期：2026-07-22。

---

## 0. 全景：M5 在造什么

一句话：**把"消息数组"升级成"只追加的树"**。每个条目带 `{id(UUIDv7), parentId, timestamp}`，当前对话 = 从 leaf 走到 root 的那条路径。换模型、压缩、打标签、甚至移动光标本身，都是追加的树条目。

```
依赖关系(从下往上建):

uuidv7 (54行)                     ← Step 1,零依赖
   ▲
types: 条目联合 + SessionStorage   ← Step 0,纯类型
   ▲
InMemorySessionStorage (133行)    ← Step 2,树逻辑在内存里做对
   ▲
messages.ts 类型部分 (~100行)      ← Step 3 前置,4 个自定义角色
Session + buildContext (338行)    ← Step 3,投影层(M5 的智力核心)
   ▲
迷你 FileSystem (~80行)            ← Step 4 前置(M6 的首付)
JsonlSessionStorage (314行)       ← Step 4,同一接口的磁盘实现
   ▲
repos (280行)                     ← Step 5,可推迟
```

整层是**纯数据结构**：零 LLM、零 Agent 依赖、测试连 faux 都不用。这是所有里程碑里最"安全"的一个——每一步都有确定性测试立刻告诉你对不对。

## Step 1：uuidv7（一小时，今天就能拿下第一个绿测试）

`harness/session/uuid.ts`，54 行，零依赖。要点：

- RFC 9562 布局：前 6 字节 = 毫秒时间戳，byte6 高 4 位 = 版本 `0x7`，byte8 高 2 位 = variant `0b10`。
- **单调性处理**（这是它存在的意义，时间序 ID 让树条目天然可排序）：模块级 `lastTimestamp` + `sequence` 计数器——同一毫秒内的连续调用递增 sequence；sequence 溢出则把 `lastTimestamp` 假装推进 1ms。
- 随机源优先 `globalThis.crypto.getRandomValues`，降级 Math.random（浏览器/Node 双兼容）。

**验收：移植 `test/harness/session-uuid.test.ts`（1 个测试：布局 + 单调序）。**

## Step 2：InMemorySessionStorage（一个下午）

`harness/session/memory-storage.ts`，133 行。**树的全部逻辑在这里第一次成形**，而且没有磁盘干扰：

- `appendEntry(shape)`：分配 `id = uuidv7()`、`parentId = 当前 leaf`、`timestamp`，追加进数组，**leaf 前进到新条目**。
- `getPathToRoot(fromId)`：沿 `parentId` 一路向上走——这就是"当前对话"的定义。
- `setLeafId(targetId)`：**不是改内存变量，而是追加一条 `leaf` 条目**。为什么？JSONL 重放时才能恢复光标位置（jsonl-storage.ts:247-265 同款语义，内存版先把接口做对）。
- `findEntriesByType` / label 查找缓存（"latest label wins"）。
- 构造函数接受初始条目（测试 "copies initial entries" 会检查防御性拷贝）。

**验收：移植 `storage.test.ts` 的 `InMemorySessionStorage` describe（6 个测试，:10-101）。**

## Step 3：Session 门面 + buildContext 投影（两三天，M5 的智力核心）

前置：先把 `harness/messages.ts` 的**类型/工厂部分**写了（~100 行）：4 个自定义角色接口（`BashExecutionMessage`/`CustomMessage`/`BranchSummaryMessage`/`CompactionSummaryMessage`，messages.ts:19-52）、`declare module` 声明合并注册（:54-61）、`create*Message` 工厂（:81-110）。`convertToLlm` 投影函数（:120-164）可以先不写——那是接 loop 时的事。

然后 `harness/session/session.ts`，338 行。两块：

**① Session 类（:137-338）**：`SessionStorage` 之上的门面——`appendMessage` / `appendModelChange` / `appendThinkingLevelChange` / `appendCompaction` / `appendLabel` / `moveTo(newLeafId, summary?)`（移动光标 + 可选追加 branch_summary 条目，注意摘要条目**挂在新 leaf 下**，:318-337）。

**② 投影管线（:22-135，导出的纯函数）**——这是整个 M5 最值得反复琢磨的 40 行：

```
buildContext() = getBranch()(leaf→root 路径) 然后两遍独立的扫描:
  遍1 deriveSessionContextState(:37-55): 扫完整路径 → {model, thinkingLevel, activeToolNames}
      (在"完整"路径上扫——被压缩掉区域里的 model_change 依然生效!)
  遍2 buildContextEntries(:82-91): defaultContextEntryTransform(:57-80) → 应用最后一个
      compaction 条目: firstKeptEntryId 之前的条目从投影里消失,换成摘要
      再 sessionEntryToContextMessages(:93-123): 条目→消息
      (compaction→CompactionSummaryMessage, custom→默认丢弃除非注册了 projector,
       model_change 等配置条目→[])
```

记住咒语：**压缩改的是投影，不是历史。**

**验收：移植 `session.test.ts`（15 个测试，含分支/压缩投影/自定义条目/label），先跑 memory 后端。** 注意它的参数化写法：`describe(name, ...)` 包在一个接收 storage 工厂的辅助函数里——移植时先只传 InMemory 工厂，Step 4 后加 Jsonl 工厂，同一套测试双后端跑。

## Step 4：迷你 FileSystem + JsonlSessionStorage（两三天）

**关键发现（这条帮你省掉半个里程碑）**：JSONL 存储 + repo 只用到 `FileSystem` 的 **10 个方法**——`readTextFile / readTextLines / writeFile / appendFile / absolutePath / joinPath / createDir / exists / listDir / remove`——**完全不需要 Shell**。所以不用先做完整 M6（nodejs.ts 有 569 行），写一个 ~80 行的 `MiniNodeFs`（node:fs/promises 包一层、返回 `Result<T, FileError>`、errno → FileError code 映射参考 nodejs.ts:81-100）就够 M5 用。

然后 `harness/session/jsonl-storage.ts`，314 行：

- **文件格式**：第一行 header（version 3 + metadata，:8-16），之后一行一个 JSON 条目。只有两种写操作：创建时写 header，之后永远 `appendFile`。
- `static create(fs, path, metadata)` / `static open(fs, path)`（:205-210）：open 逐行重放，用 `leafIdAfterEntry`（:127-129）边读边推演 leaf 位置——`leaf` 条目让光标在重放中恢复，这就是 Step 2 里"光标必须是条目"的回报。
- 坏数据处理：header 缺失/畸形、条目行畸形 → 抛 `SessionError`（测试逐一覆盖）。

**验收：`storage.test.ts` 剩余 12 个测试（:103-330）+ 给 session.test.ts 加上 Jsonl 工厂参数（15 测试 ×2 后端）。全绿即 M5 毕业。**

## M5 之后的路

- **M6 只剩尾巴**：Step 4 已把 FileSystem 写了。剩下 Shell/exec、truncate.ts、shell-output.ts——等 M7/M9 真用到再补（skills 层只用 `canonicalPath/fileInfo/listDir/readTextFile` 4 个方法）。nodejs.ts 里的平台脏活（进程树 kill、Windows 引号解析）**建议直接抄**，那不是学习内容。
- **M7 之前，重读 agent-harness.md 的正确姿势**：它全文都在回答一个问题——四类状态（harness 配置 / turn 快照 / session / 挂起写入）怎么严格分离。带着"我已经有 session 了"再读，先读 `Operation phases` 和 save point 两节，然后记住：**harness 没有自己的循环，它只是 runAgentLoop 的一个高级调用者**（它给 loop 喂 `prepareNextTurn` 回调来刷快照，喂 `convertToLlm`——就是你 Step 3 缓写的那个函数）。
- **毕业典礼**：M7 完成后，把 `example/04-正例-harness如何解决.ts` 的 import 从 `../../pi-minimal/...` 改回 `@yoma/my-pi`——三个场景全跑通，harness 就是你的了。

## 心法

1. **每一步先移植测试再写实现也完全可行**（TDD 式）——这些测试全是纯数据断言，是极好的规格说明书。
2. 卡住时对照参考实现，但照你之前的成功路径来：**自己写完一版，再拿参考当"我漏了什么"清单**——你的 agent-loop 就是这么拿下的。
3. M5 全程不碰 LLM。如果你发现自己在想"这里要不要调模型"，说明走偏了——摘要生成是 M8（compaction）的事。
