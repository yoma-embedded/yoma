## 1. 目标与度量

一个数:**干净的 Windows 机器上,从装完 Yoma 到第一次烧录成功,用户要手动做几步、花几分钟。**

| | 现在 | 目标 |
|---|---|---|
| 已装 Keil / CubeIDE 的机器 | 配 key → 自己找到设置页 → 选平台 → 看 11 行 → 手装探针软件 → 自己摸索怎么让 agent 构建 Keil 工程 | 配 key → 插板子 → 选工程文件夹 → 一键补齐(≤ 5 分钟,国内网络) |
| 什么都没装的机器 | 同上,且 GitHub 下载大概率失败 | 同上,Arm 工具链走国内镜像;openocd / ninja 离线秒装 |

验收方法:**Windows Sandbox**(Win11 Pro 自带,每次都是干净系统)跑无硬件那一半:装包 → 引导 → 工具链装成功;
带硬件那一半用真机 + 全新 `YOMA_CONFIG_DIR`。每个 P 完成后各跑一遍,记步数与分钟数。

## 2. 总体思路

```
首跑引导(P4)
  ├─ ① 模型 key            已有(dialog-select-provider)
  ├─ ② 插上板子 → 认设备    P2  devices.scan:探针 / 串口 / DSLogic + 驱动状态
  ├─ ③ 选工程 → 认工程      P3  project.detect:Keil / CubeIDE / CMake / IDF / west … + 芯片型号
  ├─ ④ 这个工程缺什么 → 补齐 P1  国内镜像 + 代理 + 离线种子,保证"点了就成"
  └─ ⑤ 落到会话             已有(drafts.create 预填提示词)
```

顺序 P0 → P1 → P2 → P3 → P4。P1 最先:它最小,而且现在国内用户第一次点"安装"就可能失败,后面做得再好也白搭。
P4 的骨架可以在 P1 之后就搭,②③ 两步等 RPC 好了再插进去。

## 3. 工作分解

### P0 小修(0.5 天)

| 项 | 动作 |

### P1 点了就能装上(3–4 天)

**1a. 国内镜像。** `catalog.ts` 每个 artifact 填 `mirrors`,用**带版本的全路径**(`<基址>/<包id>/<版本>/<文件名>`)——
不用现成的"基址 + 文件名"那条:`ninja-win.zip` 文件名里没有版本,平铺会撞。sha256 校验已经让镜像不需要被信任。
新增 `scripts/sync-toolchain-mirror.ts`:读 catalog → 逐个下载 → 核 sha256 → 传对象存储;升 catalog 版本时跑一次。
GPL 包(OpenOCD、MinGit、Arm 工具链)镜像的是厂商**原包不改**,包内自带许可文本;`NOTICE` 写明来源与源码地址。

**1b. 顺序按地区。** `downloadCandidates`(`install.ts:426-434`)加 `preferMirrors`:时区 `Asia/Shanghai` 等或
`YOMA_TOOLCHAIN_PREFER_MIRROR=1` → 镜像在前;否则官方在前、镜像兜底。海外用户不该被国内镜像拖慢。

**1c. 慢也要换源。** `downloadTo`(`install.ts:458-505`)加停滞检测:连续 20 s 低于 50 KB/s **且后面还有候选** → 中止换下一个。
最后一个候选不设限(慢总比没有强)。失败汇总里标明 "too slow" 与真失败的区别。

**1d. 认系统代理。** `KernelHostOptions` 加 `fetch?: typeof fetch` → `host/index.ts:213-222` 的 `toolchain.install` 与
`session-manager.ts:765-773` 的工具选项 → `InstallToolchainOptions.fetchImpl`(口子已在)。`desktop/src/main/kernel-entry.ts`
`import { net } from "electron"`,传 `net.fetch`。bench / 信箱不传,行为不变。`model-catalog.ts`、`datasheet/client.ts` 顺带接同一个口;
**模型流量(pi-ai)先不动** —— SSE 走 Chromium 栈要单独验,不混进这一刀。闸门:`e2e:ipc` 加一条"注入的 fetch 真被调到"。

**1e. 离线种子(随包 + 用户自带)。** `InstallToolchainOptions` 加 `seedDirs`:联网之前先在种子目录找
`<包id>/<版本>/<文件名>`,找到就当"下载"用 —— **后面的 sha256、解压、标记、记账一行不改**。两个种子目录:
- 随包:`resources/toolchain-seed/`,只放 openocd(3.2 MB)+ ninja(0.3 MB)的原包。打包期 `scripts/stage-toolchain-seed.ts`
  按 catalog 下载并核 sha256,electron-builder `extraResources` 带上;main 把路径经 host 选项传给内核(同 `enginesDir`,显式传、不向上找)。
- 用户:`<configDir>/toolchain-seed/` 恒扫。内网 / 断网的公司把压缩包拷进去即可;设置页加「从文件夹导入离线包」(就是往这里拷)。

> 为什么不把 openocd 直接丢进 `engines/bin`(09-17 对话里的初版建议,作废):它不是单个 exe(要 `../openocd/scripts` 与 DLL),
> `distribution.ts` 的 `PUBLIC_DATA` 白名单会把脚本目录丢掉;而且设置页核账看不见 `engines/bin`(§0 第 7 条),照旧报 MISSING。
> 走种子就是走现成的 managed 档:布局原样、设置页变绿、PATH 自动有,零新机制。
>
> 种子**不自动装**:managed 档排在 PATH / well-known 之前,自动装会遮住用户 CubeIDE 里那份 ST 定制 OpenOCD(支持的新芯片比 xPack 0.12 多)。
> 只在工具 MISSING 时由"一键补齐"触发 —— 区别只是这次不用联网、两秒装完。

**1f. 顺手修 §0 第 7 条。** `host/toolchain.ts` 的设置页 RPC 改用与会话同一个 base env(`withMachineOnPath` + `withEnginesOnPath`),
把"同一个工具两处结论不同"这个洞补上。

验收:拔网线 + 全新 configDir,`toolchain install id=openocd` 3 秒内成功、设置页显示 ok;接国内网络不挂代理,Arm 工具链装完 ≤ 5 分钟;
挂系统代理(Clash)不设环境变量,下载走代理。

### P2 设备体检(3–4 天)

**形态。** `host/domain/devices/{usb-ids,enumerate,diagnose,index}.ts`,只读枚举、不打开任何设备(同 `log ports` 的立场)。
- Windows:一段 PowerShell 5.1 脚本查 `Win32_PnPEntity`(`PNPDeviceID LIKE 'USB\VID_%'`),取 `Name / PNPDeviceID / Service / ConfigManagerErrorCode`,
  脚本**自己编 UTF-8 字节写 stdout**(友好名是本地化的)。`serial.ts:203-232,268-274` 的 `serialPowershellExe / Argv` 这套搬到 `host/domain/` 下共用
  (domain 不能反向 import tools)。
- macOS:`ioreg -p IOUSB -l`;Linux:`/sys/bus/usb/devices/*/{idVendor,idProduct,product}` + 对 `/dev/bus/usb/…` 的可写检查(udev 规则没装的判据)。
- `usb-ids.ts` 是数据表:VID/PID → 种类(探针 / USB 转串口 / 仪器)+ 名字 + 这类设备该配什么驱动。初表:ST-Link(0483:3744/3748/374B/374E/374F/3752/3753/3754…)、
  J-Link(1366:*)、CMSIS-DAP(按接口名含 "CMSIS-DAP",VID 不定)、WCH-Link(1A86:8010/8012)、ESP USB-JTAG(303A:1001)、
  CH340/CH343(1A86:7523/55D3)、CP210x(10C4:EA60)、FTDI(0403:*)、DSLogic(2A0E:*)。**以实机与 usb.ids 为准,别凭记忆定稿。**
- `diagnose.ts` 是纯函数:设备列表 → 人话结论。要覆盖的几条:

| 现象 | 结论(给用户 / 给模型) |
|---|---|
| 探针在,`ConfigManagerErrorCode` = 28 / 10 | "看到 ST-Link 了,但驱动没装好" + 官方驱动下载页。**这条现在的报错和"没插板子"一模一样** |
| J-Link 在,`Service` 是 SEGGER 驱动 | 走 JLinkGDBServer 路线;别让 OpenOCD 直连(要 WinUSB,和 SEGGER 驱动互斥 —— 正是当年删 probe-rs 的原因) |
| 探针在、驱动好 | 给出推荐后端(ST-Link → openocd;J-Link → jlink)与对应工具装没装 |
| 只有 USB 转串口 | "这是串口不是调试探针":ESP32 可以走 esptool,STM32 只能串口下载 |
| 什么都没有 | 换线 / 换口 / 线是不是只供电;Linux 上提示 udev |
| CMSIS-DAP v2 | 免驱,直接可用(文档里顺势推荐这类探针) |

(ST 官方驱动是否 WinUSB 系、各 PID 对应型号,**待实机核实**后再写死。)

**出口两个。** RPC `devices.scan`(`protocol.ts` 的 `KernelMethods` + `host/index.ts` handlers + `client.ts`,`satisfies` 会逼你三处写全)给引导与设置页;
第 17 个工具 `devices`(只读:无确认门、无队列、无 dispose,样板同 datasheet)给 agent —— `TOOL_NAMES` 末尾加名、`contracts.ts` 与 `tools/index.ts` 同序追加,
其余闸门(tool-names / boundary / 三处 `diffToolNames`)自动跟。同时改掉两句话:`flash/contract.ts:58` 的 "no built-in probe enumeration"、
`engines.ts:292-299` 的 `probeFailedHint`,都指向新工具。

**测试。** `diagnose` 的表格用例吃**真机录的输出**当夹具(开发机上有 DSLogic 与探针,先录再写;别对着编出来的形状写测试 —— datasheet 那次的教训)。
平台分支靠注入 `platform`,不靠"跑测试的机器是什么系统"。

### P3 认领现有工程(4–5 天)

**形态。** `host/domain/project-kind/{detect,keil,cubeide,ioc,recipes}.ts`。`detect(cwd)` 扫三层目录(跳过 .git / node_modules / build 类目录),按标记文件判:

| 标记 | 类型 | 构建口径(给模型的) | 需要的工具 id |
|---|---|---|---|
| `*.uvprojx` / `*.uvmpw` | Keil MDK | `UV4.exe -b <工程> -t <目标> -j0 -o <绝对路径日志>`;**UV4 是 GUI 程序,stdout 是空的,结果只在日志文件里**;退出码 0 干净 / 1 有警告 / ≥2 失败。产物 `<OutputDirectory>/<OutputName>.axf`,gdb 直接能读 | keil(+ 调试要 arm-gdb) |
| `.cproject` + `.project` | STM32CubeIDE | 有 `Debug/makefile` → CubeIDE 自带的 make + gcc 进 PATH 后 `make -C Debug all`;否则 headless build | arm-gcc(复用 CubeIDE 自带) |
| `CMakeLists.txt`(+ `CMakePresets.json`) | CMake | 现有路线 | arm-gcc、cmake、ninja |
| `sdkconfig` / `idf_component_register` | ESP-IDF | `idf.py build` | idf、python |
| `west.yml` / `prj.conf` | Zephyr / NCS | `west build` | west、zephyr-sdk |
| `platformio.ini` | PlatformIO | `pio run` | (pio,目录外) |
| `*.ewp` | IAR | `IarBuild.exe <ewp> -build <配置>` | (iar,目录外) |

- `keil.ts` 解析 `.uvprojx`(XML):目标名列表、`<Device>`、输出目录与文件名、AC5 / AC6。`ioc.ts` 读 `Mcu.UserName`。
  **芯片型号是白捡的**:datasheet 的家族解析、stm32config、OpenOCD 的 target cfg 都能直接用,不必再问用户"你用的什么芯片"。
- UV4 的位置从 armclang / armcc 的探测结果推(`…\ARM\ARMCLANG\bin` → `…\UV4\UV4.exe`)+ `existsSync`,**绝不 spawn `UV4 --version`**(会真的弹起 IDE,`families.ts:137` 的老规矩)。
- `UV4 -f`(下载到板子)碰探针:`flash/contract.ts` 的 `PROBE_SUBCOMMANDS` 加 `uv4` + `-f`,否则它绕过烧录确认门。
- 进提示词的通道是现成的:`session-manager.ts:807-809`,按 `<toolchain>` 的样子追加一个 `{ path: "<project-build>", content }` 的 context file;
  探测放在 `openEntry` 里与 `loadContextFiles` / `discoverSkills` 并行(`:741-744`),不进工具链解析那段关键路径。没认出来就一个字不加。
- RPC `project.detect {directory}` 给引导用:返回类型、芯片、目标、需要的工具 id。引导拿这组 id 走现成的"虚拟清单"那条路
  (`familyManifestText` 的做法)核账 —— 于是 Keil 工程的用户看到的是"编译 ✅ 用你装的 Keil",而不是 arm-gcc / cmake / ninja 三行黄字。

**测试。** 夹具用真工程文件的切片(BK64 的工程、BK80 的 west 工程、一个真 `.uvprojx`、一个真 `.ioc`)。Keil 那条要在装了 Keil 的开发机上真跑一次
`UV4 -b`,核对"日志在文件里、退出码语义、.axf 能被 arm-none-eabi-gdb 读符号"三件事,再写进守则。

## 4. 不做的

- **Docker / WSL / devcontainer**:Windows 上 USB 透传比装工具链还痛。
- **把 Arm 工具链打进安装包**:296 MB,比整个安装包还大;镜像 + 按需装已经够。
- **静默装驱动**:要管理员权限与签名,出错是蓝屏级的;先检测、先引导。
- **自动装种子包**:会遮住用户自己那份 OpenOCD(见 1e)。
