# Yoma 创业执行记录

建立日期：2026-09-09。状态：资源盘点与首次销售实验。

本轮目标：以 30 天为一次实验周期，验证一个独立客户的付费试点及可验收交付；没有必须在该日期收款的硬期限。长期目标是找到可以重复交付、人工成本持续下降的嵌入式 agent 业务。

## 当前决策

- 第一轮验证工程师与 agent 共同交付的板卡复测启动包，优先使用已有工具，工作以晚间异步交付为前提。广义 agent 可以是桌面产品、工具编排、客户自有 agent 的硬件接口、托管工位或技术服务，形式由购买与使用证据决定。
- 初步客户：使用 STM32 等现有能力覆盖平台、已有可运行项目且重复发版或交付的小型方案公司或设备研发团队。芯片/模组技术支持团队作为第二条访谈线。
- 第一笔付费购买的是明确交付物。后续通过复测、版本维护和工位服务验证复购。
- 新研发以具体销售或交付阻碍为输入；每个需求记录对应客户、影响与最小解决办法。
- 扩展 RTOS、芯片与仪器覆盖，要有具体任务支持。当前不启动新 RTOS 开发。

## 首个实验

产品草稿见 [板卡复测启动包](pilot.md)。候选线索见 [首批线索与联系文案](leads.md)。

假设：有重复发版或交付任务的商业团队，愿意为把人工复测转成可重复运行的流程付费，且接受晚间异步协作。这个需求尚未经过客户访谈验证。

验证步骤：

1. 确认资源与一个真实案例，安排 Ben 操作、现同事验收的短演示，核对能节省的具体步骤。
2. 接触首批 5 个目标对象，争取 3 次实际交流。
3. 至少拿到 2 份具体任务描述，核对平台、板卡、复现条件、交期、预算和采购人。
4. 对合适任务发出具体报价，争取一个付费试点。
5. 验收后询问下一次同类需求，并向另一家客户复用同一交付流程。

这些数字是执行目标。未响应不算需求被否定，口头称赞不算购买意愿，正式报价也不算收入。

## 判断与调整

| 观察到的情况 | 下一步 |
| --- | --- |
| 接触不到负责具体任务的人 | 改联系路径与引荐方式，暂不改产品 |
| 多次对话均无近期具体问题 | 调整客户画像或触发场景 |
| 有问题，但不能提供工程/板卡/合适模型数据路径 | 研究客户现场运行、最小复现工程或其他可接受交付方式 |
| 愿意给任务，但不接受启动包费用 | 查清是复测频率不足、成果不够有用、信任不足、采购障碍还是预算不足；记录原话后改报价 |
| 买家反复要求沿用自己的 agent/IDE | 优先验证工具接口或集成服务的销售，不强求使用 Yoma 桌面端 |
| 成交后大量时间耗在环境接入 | 收缩支持范围，完善可复用接入流程，再扩客 |
| 只有一次性急活、没有重复需求 | 保留现金流，另找同类问题的高频拥有者；不把救火收入当订阅验证 |
| 三次相近付费交付可复用且人工投入下降 | 再设计持续服务或产品订阅 |

## 经营记录

本轮正式销售记录起点：已联系 0；已交流 0；有效任务 0；已报价 0；已收款 0。历史触达另记：至少一位现同事试用并给出首用负面反馈；前公司工程师收到链接后未回应，人数未明确。尚无已确认付费客户证据。

每次交流追加：

```text
日期 / 线索编号：
对方角色 / 是否能决定采购：
最近发生的具体问题：
原处理方式 / 实际人时：
交期 / 不解决的影响：
平台 / 板卡 / 源码与工具可获得性：
对外部模型和远程接入的接受方式：
客户认为有价值的交付物：
报价 / 对方原话 / 异议：
```

每个试点记账：收入、售前人时、环境接入人时、开发/诊断人时、复核人时、后续支持人时、模型与外部支出、可复用资产、下一次需求。创始人时间按内部时薪计入经济成本，同时单列实际现金支出。

## 本轮 Ben 的任务

现在：资源与现实关系问题已回答；等待真实案例信息。可展示案例如果在本机，只需提供路径和背景。实际板卡/仪器清单、方便对外交流的时间和收款条件在有候选任务时补齐。

下一项真人任务：联系已经试用的现同事，约一次 15—20 分钟的具体任务交流，争取选出一个有权展示、能在一晚内验证的小任务。Ben 操作工具，同事判断结果是否有用；先不要求同事安装或迁移。首次邀请文案见 leads.md。

本次需要返回：原来怎样完成这项工作、最费时间的一步、用现有 agent 是否已解决、愿意验收什么结果、下次何时还会做同类工作。拿到任务后 Agent 负责设计对照与演示，Ben 只执行必要的现实操作。

若同事不方便，选择一位前同事做同样的具体邀请，记录回应。冷线索暂作后备，不在尚无清楚演示时扩大联系数量。

暂不要求购置设备或重新制作大型演示。已有案例不足时，由 Agent 拟定最小实测步骤，再请 Ben 完成必要的物理操作。

## 决策更新

2026-09-09：获知 Ben 在职、主要晚间投入且追求可复制收入后，将首个产品假设由故障诊断调整为板卡复测启动包。原因是后者更容易排期、明确交付物并复用流程。急单救火与要求白天持续响应的服务暂不进入首轮。

2026-09-09：获知首用摩擦与现有 Claude Code 使用习惯后，将下一步调整为具体任务价值验证。复测启动包仍为候选，不视为已证实需求；提供工具接口仍为候选，不先投入开发。先记录接入时间、主动操作时间、失败与重配次数、结果能否被同事独立理解和复核，再确定最小产品改动。
