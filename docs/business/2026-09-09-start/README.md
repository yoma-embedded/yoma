# Yoma 创业执行记录

建立日期：2026-09-09。状态：现有案例取证与需求验证，报价暂缓。

本轮目标：以 30 天为一次实验周期，验证一个独立客户的付费试点及可验收交付；没有必须在该日期收款的硬期限。长期目标是找到可以重复交付、人工成本持续下降的嵌入式 agent 业务。

## 当前决策

- 当前先核实两个已有案例，优先核实“网表 + 手册发现硬件问题并给出软件规避”。板卡复测启动包降为备用假设，报价暂缓。工作仍以晚间异步交付为前提。
- 广义 agent 可以是桌面产品、工具编排、客户自有 agent 的硬件接口、托管工位或技术服务，形式由购买与使用证据决定。
- 案例一对应研发/FAE 的软硬件联合排障候选需求；案例二对应 M5Stack 玩家创作候选需求。两者都缺少独立用户的重复使用与付费证据，目前不承诺同时开发两条产品线。
- 第一笔付费购买的是明确交付物。后续通过复测、版本维护和工位服务验证复购。
- 新研发以具体销售或交付阻碍为输入；每个需求记录对应客户、影响与最小解决办法。
- 扩展 RTOS、芯片与仪器覆盖，要有具体任务支持。当前不启动新 RTOS 开发。

## 首个实验

先核实 [已有案例与下一步验证](cases.md)。[板卡复测启动包](pilot.md)作为暂缓的内部草稿；[候选线索](leads.md)作为后备。

当前待验证：案例一是否有可复核的正确结论与实际收益，其他工程师是否会主动带来同类任务。复测服务及玩家产品保留为候选，不视为已经成立的需求。

验证步骤：

1. 获取案例一原始材料，核实问题、手册依据、规避修改及上板前后结果。
2. 整理一页可复核案例；原始记录不足时先标明不足，不用宣传材料补空白。
3. 请原同事确认价值与当前替代办法，并争取一个由对方选择的同类真实任务。
4. 根据重复使用、介入成本和采购人反馈，选择值得报价的交付范围。
5. 收到付费并验收后，再检验另一家客户能否复用同一流程。

这些数字是执行目标。未响应不算需求被否定，口头称赞不算购买意愿，正式报价也不算收入。

## 判断与调整

| 观察到的情况 | 下一步 |
| --- | --- |
| 接触不到负责具体任务的人 | 改联系路径与引荐方式，暂不改产品 |
| 多次对话均无近期具体问题 | 调整客户画像或触发场景 |
| 有问题，但不能提供工程/板卡/合适模型数据路径 | 研究客户现场运行、最小复现工程或其他可接受交付方式 |
| 愿意给任务，但不接受启动包费用 | 查清是复测频率不足、成果不够有用、信任不足、采购障碍还是预算不足；记录原话后改报价 |
| 买家反复要求沿用自己的 agent/IDE | 优先验证工具接口或集成服务的销售，不强求使用 Yoma 桌面端 |
| 成交后大量时间耗在环境接入 | 收缩支持范围，完善可复用接入流程，再扩客 |
| 只有一次性急活、没有重复需求 | 保留现金流，另找同类问题的高频拥有者；不把救火收入当订阅验证 |
| 三次相近付费交付可复用且人工投入下降 | 再设计持续服务或产品订阅 |

本轮正式销售记录起点：已联系 0；已交流 0；有效任务 0；已报价 0；已收款 0。历史触达另记：至少一位现同事试用并给出首用负面反馈；前公司工程师收到链接后未回应，人数未明确。尚无已确认付费客户证据。

## 本轮 Ben 的任务

现在：已收到两个案例的简述，等待案例一具体问题、软件规避方式、是否上板验证及原始材料位置。实际板卡/仪器清单、方便对外交流的时间和收款条件在有候选任务时补齐。

下一项真人任务：先把已有案例一的事实或材料路径交给 Agent；Agent 整理后，再联系原同事核对事实和实际价值，争取一个由对方选择的同类问题。Ben 操作工具，同事判断结果是否有用；先不要求同事安装或迁移。

本次需要返回：原来怎样完成这项工作、最费时间的一步、用现有 agent 是否已解决、愿意验收什么结果、下次何时还会做同类工作。拿到任务后 Agent 负责设计对照与演示，Ben 只执行必要的现实操作。

若同事不方便，选择一位前同事做同样的具体邀请，记录回应。冷线索暂作后备，不在尚无清楚演示时扩大联系数量。

暂不要求购置设备或重新制作大型演示。已有案例不足时，由 Agent 拟定最小实测步骤，再请 Ben 完成必要的物理操作。
