## 0. 全景:在造什么

一句话:**让研发和测试各自下载 Yoma Desktop,配置一次(信箱远端 + 本机角色 + 项目模板),
之后每个任务只需要在界面上描述需求 → 开跑 → 观战 → 拿终报**。

```
测试的电脑(工位)                          研发的电脑(决策)
┌────────────────────────┐                ┌────────────────────────┐
│ Yoma Desktop (exe)     │                │ Yoma Desktop (exe)     │
│  main ──spawn──> 信箱  │   私有 git 仓   │  main ──spawn──> 信箱  │
│  runner 守护(打包产物) │◄──(信箱)──────►│  mother 守护(打包产物) │
│   └─> turn-entry 子进程 │                │   (全自动母 agent)     │
│        └─> 板子/探针    │                │                        │
│  交互内核进程(观战/回放)│                │  交互内核进程(观战/回放)│
└────────────────────────┘                └────────────────────────┘
```

两半的分工不变(引擎干活,桌面端呈现):守护进程就是今天 CLI 里那两个 `runMailboxRunner` /
`runMailboxMother`,桌面端负责**打包它、托管它、把它的事件流画出来**。

**产品红利(已存在,不用施工)**:exe 里已打包 engines(probe-rs 等)→ 测试机零额外安装;
两侧会话本来就落在桌面端 sessionsRoot → 观战与回放是现成的(真跑当天已验证)。

**兼容承诺**:信箱文件协议一字不改 —— exe 端与 CLI 端可以混搭配对(一台跑桌面端、
一台跑 CLI 完全成立),这也是灰度上线的路径。

## 1. 硬约束(施工前必读,每条都有证据)

1. **exe 里没有 bun,bench 现在是 bun 直跑源码。** 两个具体障碍:
   - `Bun.file/Bun.write`:打包面共 **29 处、11 个文件**(2026-08-07 grep,不含测试),
     全部要换成 `node:fs/promises`。机械活,但必须先做 —— 这是其余一切的地基。
   - 子进程入口:`runTurnInChildProcess` 用 `process.execPath` 起 `turn-entry.ts`
     (`bench/src/runner.ts`)。打包后 execPath 是 Electron 本体,必须改为
     **`ELECTRON_RUN_AS_NODE=1` + esbuild 打包出的 JS 入口**(与 `out/main/kernel.js`
     同一条管线;内核 inline 的全部理由 —— raw TS 的 strip-only 报错、TS 参数属性 ——
     对 bench 同样成立,见根 CLAUDE.md"内核接缝")。
   - 入口从环境探测:开发态(bun)与打包态(RUN_AS_NODE)用同一个分支点,
     `process.versions.bun` 判定即可。cli.ts / sim.ts / testkit 不进打包面,可继续用 Bun API
     (`askHuman` 的 `for await (const line of console)` 是 CLI-only,不用动)。
2. **探针跨进程不互斥,必须产品层解决。** my-pi 的探针租约是**模块级全局 = 进程内**的
   (根 CLAUDE.md"只 fork 一个内核进程"的整个理由)。桌面端引入 mailbox 守护后,工位机上
   同时存在两类会碰探针的进程:交互内核进程(用户自己开会话调试)与 bench 的 turn 子进程。
   真跑当天已实测撞过:判据脚本里的 probe-rs 撞上 agent 自己的 gdb 会话,报
   `exclusive access (0xe00002c5)`。**方案(强制,不是 UI 提示)**:调试台任务活跃时,
   main 通知交互内核进程,host 侧注入一层 policy 把 `flash/gdb/log(rtt)` 判 deny,
   理由写明"探针被调试台任务占用";任务终局后撤除。UI 同步置灰 + 黄条。
3. **contextBridge 会把 Error 剥成一句话**(根 CLAUDE.md"会咬人的地方",e2e:renderer 钉着)。
   mailbox 的事件与失败**只用普通对象**过桥,沿用 `{ message, data }` 形状,不包 Error。
4. **一个信箱一个任务、每角色单实例**是协议前提(引擎已有 pid 锁,`mailbox/daemon.ts`)。
   桌面端 main 托管时仍要防"用户开两个窗口/两次点开跑":main 层再挂一道任务级状态机,
   锁冲突的报错要转成人话("另一个 Yoma 实例正在跑这个信箱")。
5. **Windows 的进程终止没有优雅信号**:`child.kill("SIGTERM")` 在 win32 是硬杀,
   turn-entry 的"信号转杀孙进程"链路(`bench/src/runner.ts` 的 activeTurnChildren)在
   Windows 上不会被走到 —— main 停任务时必须**自己遍历杀进程树**(`taskkill /T` 语义),
   这是 P4 的验收项之一,别指望引擎自理。
6. **信箱远端凭据走系统 git**(ssh-agent / credential manager),桌面端不存也不代管
   git 凭据;配置页只做"连通性自检"(`git ls-remote`,报错原样给人看)。实测教训:
   公司代理会间歇性掐死 GitHub(fake-IP 198.18.x),引擎已有退避与"先推欠账"兜底,
   UI 要把 blocked 状态如实显示成"信箱暂时不可达,已在退避重试",不要报成任务失败。

## 2. 架构决策(含被否掉的方案)

| 决策 | 选择 | 否掉的与理由 |
|---|---|---|
| 守护进程宿主 | **main 进程 spawn**(utilityProcess.fork,带 `ELECTRON_RUN_AS_NODE` 起孙进程) | 塞进交互内核进程:违反"内核进程只干交互"的职责,且 bench 一轮一子进程的模型和内核的单进程铁律没有交集,硬融会把探针清理语义搅浑 |
| renderer 通道 | **独立命名空间 `window.api.mailbox`**(preload 桥,main 中转事件) | 并入 kernel MessagePort 帧协议:内核进程根本不在这条数据通路上,借道等于让两个无关生命周期互相绑架 |
| 事件流 | 守护 stdout 上加 **`@@event {json}` 行**(与 `@@escalate` 同款小而蠢的协议),main 逐行解析转发 | 另开 socket/文件轮询:多一种运输层,重放/调试都不如"进程输出即事件"直白 |
| 浏览器侧类型 | **结构化复制进 `packages/kernel/src`(视图模型)+ bench 侧编译期防漂移断言**(bench 已依赖 kernel,方向合法;断言必须是约束式 `Expect<T extends true>`,教训见 details-check.ts) | 浏览器直接 import bench 类型:bench 是纯 Node 包,违反 kernel 浏览器安全入口的边界 |
| 任务的判据来源 | **项目模板**(`<项目>/.bench/mailbox.template.json`:芯片/探针/构建/判据/known-good,配一次)+ 界面表单;任务级只填自然语言描述与预算档 | 让模型从描述生成判据:违反"判据不归模型管"的根基;"AI 起草、人确认"列为后续增强 |
| 单机形态 | sim 引擎复用,产品里叫**"本机演练"**(新手第一次跑的默认引导) | —— |

## 2026-08-08 · 分工对调与机器无关

P1–P3 落地并实板跑通之后,用户提了两件事,它们把这套东西的形态改了一次。

### 一、分工对调:代码归研发端,工位端只上板

> "测试其实是没有必要改代码的 比如说母agent下发测试指令 是有一些具体需要测试的任务
> 测试那边的agent负责测试 返回结果 需要改代码应该是母agent改 改完之后给测试那边
> 比如说重新烧录还是怎么样的 然后继续完成测试任务"

理由是**手上有什么**:改代码要工具链和完整检出,那在研发机;上板要探针,那在工位机。
旧分工逼着工位端既改代码又验证自己,等于让考生自己出题。

角色字符串仍是 `mother`/`runner`(改名会波及锁文件、事件、UI、view-check 一大片,
收益是零),含义换了:

| | 研发端(mother) | 工位端(runner) |
|---|---|---|
| 工作区 | 项目仓,`role:"dev"` | 项目仓,`role:"bench"` |
| 能做 | 改代码、构建、附产物、写指令、开分支提交、终局推交付分支 | 上板、复现、观察、报告 |
| 被拒 | `flash`/`gdb`/`log`(板子不在这台机器上) | `edit`/`write`/`stm32config generate` |
| git | 开 `agent/<id>` 分支,每轮提交 | 不开分支不提交;工作树必须干净 |

角色是**拒绝层**,压在三档策略之上,只拒不升级 —— 这两条不是"有人点头就能干"的
权限问题,是"这台机器上根本不该发生"。

**协议里不预设"怎么把新固件弄上板"**:每轮一个 `rounds/NNN/artifacts/` 目录,加上
指令里的一句人话,就是全部机制。研发端在决定 JSON 里写 `"artifacts": ["build/x.elf"]`,
拷贝/存在性/大小上限由**代码**做(`attachArtifacts`)——agent 因此不需要信箱目录的
写权限,而"附件是不是真的在"有机器保证。工位端收到后由调试台落到 `.bench/incoming/<原名>`,
路径写进提示词,**怎么用由那边的 agent 自己判断**(probe 烧录 / OTA / 别的)。
换机制时改的只是指令那句话,协议一个字不动。

**第一轮不再由 init 写死"只复现取证"**:开局做什么本来就是判断(先复现?先加日志?
先烧 known-good 排除环境?),固化在代码里等于在最需要判断的地方绕开了 agent。
新状态 `kickoff` = job.json 在而零轮次,等研发端出手。

**代价与解法**:上板交给 agent 判断,就有"忘了烧却接着测"的可能,判据于是跑在旧固件
上 —— 万一旧固件恰好能过就是**假通过**,证据里看不出来。挡它的不是协议,是一条
**烧录新鲜度判据**:`probe-rs verify` 逐字节比对 flash 与交付的 ELF。
两个实测事实:它比读魔数常量强(魔数只证明"某个带这个符号的固件在跑",不证明是
哪一版);而且它**内容不匹配时照样 exit 0**,判据必须认输出文本,只看退出码的话
这条闸门永远不会响。

### 二、机器无关:一份任务书,两台机器

> "你写死的话 我日后要在很多不同电脑上跑 那不是乱套了"

原来 `job.json` 里有两样本机事实,跨机器一律作废:

1. **`repo.directory`** —— 出题机的绝对路径。改成可选,`serializeMailboxJob` 主动摘掉;
   工程目录由本机提供(`resolveWorkspace(job, localDir)`:桌面端配置页的「工程目录」、
   CLI 的 `--project`、守护配置的 `projectDir`)。新增 `repo.name` 供人对号入座。
   没配就起不了常驻角色,报错是人话而不是某个 git 命令在 `undefined` 目录里失败。
2. **判据里的解释器与绝对路径** —— `python3` 在 Windows 上不存在,
   `/Users/ben/…/probe-rs` 换台机器更不存在。新增判据类型
   `{ "type": "script", "path": …, "args": [] }`:argv[0] 由**跑判据的机器**当场解析
   (macOS python3/python;Windows 优先 `py -3`;`.sh`→bash、`.js`→node、`.ps1`→powershell),
   仍然 argv 直 spawn 不过 shell。另外给判据进程注入环境契约
   `YOMA_PROBE_RS` / `YOMA_ENGINES_DIR` / `YOMA_WORKSPACE` / `YOMA_CHIP` / `YOMA_PROBE` /
   `YOMA_ELF` / `YOMA_KNOWN_GOOD_ELF`,脚本照着读就跨机器可用。

顺带:`success.build` 从模板里删掉。构建归研发端,在工位机上跑构建只会编出一份**旧**
代码,判据于是在错误的固件上通过。`bench.elf` 相应指 `.bench/incoming/…`。

### 三、没有动的不变式

判据仍由**工位端调试台亲跑**,模型说"修好了"不算数;裁决仍分两层(守卫先裁判据/预算/
环境,模型只裁"判据没过且预算还有");工位端仍是一轮一个子进程(探针租约等模块级
全局靠进程边界清理);状态仍由文件存在性推断,不落状态文件;`pullReset` 仍是
`fetch + reset --hard + clean -fd`。

### 四、路上逮到的三个坑

- **`.my-pi/.gitignore` 不忽略自身**,于是它是一个"未跟踪又不被忽略"的条目,工作树
  永远不干净 —— 而 `prepareBranch` 的第一道检查正是它。这是 `.bench` 那条教训的
  第三次上演,修法一样(忽略清单里带上自己,旧版逐字相同才升级)。
- **`git status --porcelain` 不能按固定列切**(教训现记在 `runGitReal` 头上;当时那个
  `dirtyTrackedFiles` 已随工位端项目检出一起删除):`runGitReal` 对整段 stdout 做过 trim,第一行
  的前导空格没了,`slice(3)` 把文件名咬掉一个字符(`main.c` → `ain.c`)。
- **终局收尾必须在"刚写下 verdict"那一步做完**:守护循环见到 `done` 就返回退出,
  留到下一轮等于永远不做 —— 交付分支永远推不出去(测试逮住的)。

### 五、验收

- `bun typecheck --force` 7/7;
- 单测:bench 202 / kernel 76 / desktop 408 / app 425 / session-ui 54 / ui 4,全绿;
- `smoke`、`e2e:ipc`、`e2e:mailbox`(17 项)、`e2e:renderer` 全过;
- **`smoke:mailbox` 全过** —— 它是对**打包产物**跑的完整本机演练,走的已经是新分工的
  四步舞:工位端 idle 等指令 → 研发端 kickoff 下发第 1 轮 → 工位端跑 → 研发端改代码
  并下发第 2 轮 → 工位端跑 → 守卫终局 passed → 工位端收尾;
- 用户项目 final_foc 的两条判据(`flashed_build.py` / `firmware_alive.py`)在**实板**上
  按新的环境契约跑通,并验证了 `flashed_build` 对"换成别的 ELF"确实判失败。

## 2026-08-10 · 大幅简化:删掉整个"不信任 agent"的机制层

> **本节之前的内容是施工记录,原样保留**;下面这些是它描述的东西里**已经不存在**的
> 部分。冲突时以本节和源码为准。

上面每一期都在往"机器兜住模型"的方向加东西:判据由调试台亲跑、权限门拦硬件动作、
角色边界拒工具、失败自动回刷 known-good、探针互斥锁。这一次一口气把它们全删了。

理由是这些机制**每一样都在假设 agent 会骗人或会失手,然后用一层代码去堵**,而堵的代价
是:判据要单独维护一套脚本与环境契约(还要跨 macOS/Windows 解释器);权限规则要用户
配白名单,配窄了 agent 原地打转、配宽了等于没有;工位机为了跑判据必须克隆工程、装
Python、保持工作树干净 —— 一台只该插着板子的机器背上了半套开发环境。删掉之后,约束
agent 能做什么靠的是**它手上有什么**:工位端没有项目检出,不把脚本送过去它就跑不了。

### 删了什么

| 删掉的 | 原来在哪 |
|---|---|
| 判据层:`grader.ts` / `interpreter.ts` / `.bench/checks/` 约定 / 判据的环境契约(`YOMA_PROBE_RS`、`YOMA_CHIP`、`YOMA_ELF`、`PYTHONIOENCODING`…) | 本文 §2「任务的判据来源」、§3 P3「进度页」、2026-08-08 一节的「二、机器无关」 |
| job spec 的 `success.checks` / `success.build` / `success.repeat` | 同上 |
| 权限层:内核权限门(`kernel/src/host/permission.ts`)、bench 三档策略(`unattended`/`supervised`/`readonly`)、角色边界(dev 拒硬件 / bench 拒改码)、`allowCommands` / `protectedPaths` / `maxDiffLines`、桌面端的权限弹窗 | §1 硬约束 2、§3 P2-3、2026-08-08 的分工表「被拒」行 |
| 探针互斥锁(`mailbox.setActive`、权限门的任务级覆盖槽、`hardwareLockPolicy`) | §1 硬约束 2、§3 P2、§6 P2 施工记录 |
| known-good 回刷:`bench.knownGoodElf` 与工位端的终局收尾 | §2「任务的判据来源」、2026-08-08 一节 |
| CLI 的 `yoma-bench run` 与 `yoma-bench grade` | ——(它们的循环终止条件本来就是判据) |

### 换成了什么

- **裁决**:`DecisionKind` = `continue` / `done` / `fail`(原来是 `continue`/`success`/
  `fail`/`park`,而且解析器**拒绝** `success` —— 判据全绿才由守卫宣布成功)。
  现在模型可以说 `done` 了,它就是 `verdict.outcome = "passed"`。
  `outcome` 只剩 `passed` / `failed`,`parked` 没有了。
- **代码不裁决任何东西**。同日稍晚又把预算一并删掉了:没有轮数 / token / 墙钟上限,
  闭环跑到研发端说 `done` 或 `fail` 为止。`by:"policy"` 只剩一种情况 —— 决定 JSON
  连着两次读不出来,那不是裁决而是"没法把它的话变成动作"。提前收工靠进度页的停止按钮。
  唯一保留时间上限的是单机模拟(`mailbox sim`,60 分钟看门狗):演练台要在 CI 里收敛。
- **"通过"的可信度改由话术承担**:研发端的角色提示词要求它把**自证**写进指令 ——
  让工位端报出的数字本身说明问题(版本指纹、计数器增量、原文照抄的日志),而不是问
  "好了吗"。烧录新鲜度原来靠 `probe-rs verify` 判据挡,现在靠指令里的构建指纹自证。
- **job spec 瘦身**:删 `success` / `policy` / `allowCommands` / `protectedPaths` /
  `maxDiffLines` / `bench.knownGoodElf` / `bench.elf`;**整个 `budget` 段与
  `mailbox.mother.maxTokensPerAnalysis` 也删了**。任务页的"预算档"选择器随之消失。
- **CLI 只剩两条主命令**:`yoma-bench check <job.json>` 与
  `yoma-bench mailbox <init|runner|mother|status|sim>`。`--yes` / `--ask` / `--force` /
  `--dry-run` 删了(它们都是权限交互的旋钮),新增 `--work-root`;`--project` 只有
  `mother` 和 `sim` 用得上。

### 工位端不再有项目检出

这是删除判据带来的最大形态变化,也是唯一影响部署的一条。

工位端的工作目录现在是一个**一次性目录**,住在信箱克隆的**兄弟位置**
(`<克隆的上级>/work/<任务id>/work`,`--work-root` 可改),内容全部来自附件。
**不能落在克隆里面** —— `pullReset` 的 `clean -fd` 会把附件每轮删一次。
附件落在这个目录的**根**(不再是 `.bench/incoming/`),`result.incoming` 里是纯文件名。

于是工位机不需要 clone 目标工程、不需要 arm-none-eabi 工具链、不需要 Python 运行时,
也没有"工作树必须干净"这条纪律。配置页的「工程目录」只有研发端要填。

### 2026-08-08 那张分工表里,哪几行不再成立

| 行 | 现状 |
|---|---|
| 工作区:两边都是"项目仓 + `role`" | 研发端仍是项目仓;**工位端是一次性工作目录,没有 `role` 这个概念了** |
| 被拒:dev 拒 `flash`/`gdb`/`log`,bench 拒 `edit`/`write` | **整行作废**。没有拒绝层了 —— 研发端调 `flash` 只会得到"探针没找到"(板子确实不在那台机器上),工位端能不能改代码取决于那儿有没有代码(没有) |
| git:工位端"不开分支不提交;工作树必须干净" | 工位端**根本没有 git**。干净性检查只剩研发端一侧(`prepareBranch`) |
| 能做 | 仍然成立 |

同一节的「三、没有动的不变式」里,**"判据仍由工位端调试台亲跑"和"裁决仍分两层"
两条已经作废**;其余(一轮一个子进程、状态由文件存在性推断、`pullReset` 是
`fetch + reset --hard + clean -fd`)不变。

§5 里"预算三档的具体数值"这条决策也随之作废 —— 没有预算了。

§5「明确不做」里的"从自然语言生成判据"也随之失去意义 —— 没有判据了。

### 还剩什么防线

诚实地说:少了。

- **附件是唯一通道**,而且拷贝、存在性、大小上限由代码做(`attachArtifacts`),
  agent 声明、机器执行 —— 这条没变,它是"工位端拿到的东西是真的"的全部保证。
- **一轮一个子进程**仍在(探针租约、gdb 会话表、log 采集器都是模块级全局,进程边界
  是免费且可靠的清理)。
- **裁决者不能伪造**:守卫裁的记 `by:"policy"`,模型裁的记 `by:"mother"`。
- 但**没有权限系统了**:同机的交互会话与调试台任务可以同时抢探针(实测会撞
  `0xe00002c5`),而且没有任何东西拦得住 agent 调用任意工具。这是产品决定,不是遗漏。
- **判据层原本还兜着一件事:子进程的输出编码**(`PYTHONIOENCODING=utf-8` +
  `PYTHONUTF8=1`,见 `docs/交接-20260809-Windows待办.md` 那次真跑)。现在工位端 agent
  是自己经 bash/my-pi 跑脚本的,那条路上没有我们注入的环境 —— 坑还在,防线没了。
  真撞上就在任务书里让脚本自己 `sys.stdout.reconfigure(encoding="utf-8")`。

### 验收状态

`bun --cwd packages/desktop smoke:mailbox`(对打包产物跑完整本机演练)与单机
`mailbox sim` 都过了。**双机真跑一次仍然是必须的**:研发端能不能把上下文写够、工位端
在只有附件的目录里能不能干活,只有真跑才知道 —— 这一版把"验证"整个交给了话术,而话术
