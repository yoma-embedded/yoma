# 信箱闭环:母 agent 管什么、双机(Windows)怎么用

> 配套代码:`packages/bench/src/mailbox/`。本文回答两件事:母 agent 与调试 agent 之间
> **到底传什么**;在两台陌生的 Windows 电脑上**从零怎么跑起来**。示例全部取自
> 2026-08-07 对 final_foc(STM32G431)的首次真跑。

## 一、母 agent 如何"管"调试 agent —— 传的是什么

先说清一个边界:**母 agent 从不直接和调试 agent 对话**。两边是两个独立的 yoma 内核
会话(各自的模型上下文留在各自机器上,不过网);过信箱的只有下面这些**结构化文件**,
全部可 `git log` 审计:

```
mother → runner   rounds/NNN/instruction.json   本轮指令(纯文本 prompt)
runner → mother   rounds/NNN/result.json        轮结果(见下)
                  rounds/NNN/patch.diff         相对任务基线的完整代码补丁
裁决记录          rounds/NNN/decision.json      谁(mother/守卫)决定了什么,花了多少
终局              verdict.json + report.md      结论与终报
收尾              finalize.json                 回刷/交付是否真的做了
```

### mother 发出的:一段指令文本

`instruction.json` 里有效载荷就一个 `prompt` 字段。真跑第 2 轮她写的是(原文节选):

> 立即实现指纹变量。在 Core/Src/main.c 的 CubeMX 用户区内添加
> `__attribute__((used)) uint32_t g_bench_magic = 0xB00C0DE5UL;`。要求:(1) 必须带
> 初始化值,不能落进 .bss;(2) used 防止 --gc-sections 丢弃;(3) 放在 Core/,
> Algo/ 一行不许动;(4) 只加这一个 uint32_t(RAM 91%)。改完后按顺序自证:
> (a) 构建退出码 0;(b) nm 确认符号在 .data;(c) 烧录并 reset;(d) gdb 读内存
> 确认值 == 0xB00C0DE5,贴出实际值。全程不发送任何 CLI 命令……

注意她**不复述日志原文** —— 因为 runner 组装轮提示词时会确定性地附上:

1. 母 agent 指令(上面那段);
2. **上一轮判据的原始证据**(runner 自己跑出的,不信任何转述);
3. 上一轮被权限策略拦下的动作清单(让 agent 别原地重试)。

所以调试 agent 收到的 = 指挥意图 + 机器事实,两者来源分离,谁也篡改不了谁。

### runner 回填的:一份可采信的轮结果

`result.json` 的字段(真跑第 2 轮的实际内容):

| 字段 | 内容 | 真跑示例 |
|---|---|---|
| `turn` | agent 自述正文、工具统计、中断原因、provider 错误 | `{"edit":3,"bash":22,"read":4,"flash":2,"gdb":9}` |
| `grade` | **判据结果与证据,工位机独立执行**,模型说了不算 | `firmware_alive: pass, bench_magic: pass` |
| `denied` | 被策略拒绝的动作(带规则名) | 5 条,如 bash 直跑 probe-rs → `bash.not-allowed` |
| `git` | 基线/头提交、diffStat、改动文件清单 | `M Core/Src/main.c` |
| `spentTokens` | 工位侧累计花费(预算强制的输入) | 124,579 |

mother 的分析提示词由这份结果 + `patch.diff` 组装;她还能用 read 工具翻信箱里的任何
轮次文件。她的产出被解析器强约束:结尾必须是一个 JSON 围栏,`decision` 只认
`continue / fail / park` —— **`success` 会被解析器当场拒绝**,判据全绿时由确定性守卫
(代码)终局,模型无权宣布成功。每次裁决(包括守卫做的)都落 `decision.json`,
`by` 字段如实记录裁决者与花费:

```json
{ "round": 1, "by": "mother", "decision": "continue",
  "analysis": "构建通过、固件存活且停在 IDLE…bench_magic 差在 ELF 里还没有该符号",
  "usage": { "tokens": { "input": 12568, "output": 454, … } } }
```

### 管理的"手感"从哪来

- **预算**:轮数 / token(两侧合计)/ 墙钟三个上限全由代码守卫强制,mother 每轮
  只被告知余量,不做算术;
- **纪律**:一轮一个假设、先复现再修、判据不归模型管 —— 写死在提示词模板里;
- **审计**:信箱的 git 历史就是完整决策链;工位机本地另有
  `.bench/mailbox/<jobId>/decisions.jsonl` 记录每一次工具放行/拒绝。

## 二、两台陌生 Windows 电脑,从零跑起来

角色:**工位机**(连板子的那台)+ **决策机**(跑母 agent 的那台,不需要硬件)。

### 0. 信箱可以是任何 git 远端 —— 对,随你填

协议只依赖 `git fetch/push`:GitHub/Gitee 私有仓、公司 GitLab、NAS 上的裸仓、
甚至局域网共享盘上 `git init --bare` 出来的目录都行。唯一要求:**两台机器都能
读写它**(SSH key 或 HTTPS 凭据各自配好)。一个信箱同一时间只跑一个任务。

### 1. 两台机器共同的前置

```powershell
# ① 开发者模式 + git 符号链接(README「Windows 用户」一节,一次性)
git config --global core.symlinks true
# ② 装 bun,克隆 yoma-pi 仓(bench 直接跑源码,无需构建)
git clone <你的 yoma-pi 仓> C:\yoma-pi
cd C:\yoma-pi && bun install
# ③ 模型凭据(与 Zed/桌面端同一份)
#    %USERPROFILE%\.my-pi\auth.json → {"deepseek":{"type":"api_key","key":"sk-…"}}
#    (格式必须带 "type" 判别字段,少了会被静默忽略)
# ④ 克隆信箱仓
git clone git@github.com:you/your-mailbox.git C:\mailbox
```

### 2. 工位机独有的前置

- **engines**(probe-rs 等引擎二进制):跑 `bun engines\build.ts`,或按
  `packages/desktop/engines.lock.json` 钉住的 tag 下载 Windows 预编译产物解到
  `engines\`;临时也可用 `YOMA_ENGINES_DIR` 指向现成目录;
- 目标工程检出(必须是 git 仓)+ 它的交叉工具链(arm-none-eabi-gcc、cmake/ninja
  在 PATH)+ ST-Link 等探针驱动;
- 无人值守硬件任务必须准备 `knownGoodElf`(失败自动回刷,job 校验会逼你填)。

### 3. 写任务书(job JSON,放哪都行)

拿 `packages/bench/example/mailbox-job.example.json` 改。Windows 上专门注意:

- `repo.directory` 写**工位机上的**路径,如 `"D:\\work\\motor-fw"`(决策机不读它);
- 判据命令注意 `python` vs `python3`、路径分隔符;白名单匹配自动剥 `.exe`,
  写 `make` 就能配上 `make.exe`;
- 判据不过 shell(argv 直接 spawn),所以**没有 sh 也能跑**,但也别在判据里写
  `&&` 管道 —— 写不进去,这是故意的。

### 4. 开跑(每台一条常驻命令)

```powershell
# 任一台:任务入箱(校验 spec → 写 job.json → 下发第 1 轮复现指令)
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox init D:\jobs\fix-can.json C:\mailbox

# 工位机:常驻执行者(--ask = 权限升级问终端;不加 = 真无人值守,升级一律拒)
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox runner C:\mailbox --interval 30

# 决策机:母 agent
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox mother C:\mailbox --interval 30
```

就这些。之后闭环自转:runner 领指令→跑轮→判据→回填;mother 读结果→裁决→下发
下一轮或终局;判据全绿/预算耗尽由守卫自动终局;终局后工位机自动收尾(通过则按
`deliver.push` 推交付分支,失败/挂起则回刷 known-good)然后两边进程自己退出。

观察进度,随时随地:

```powershell
bun …\cli.ts mailbox status C:\mailbox     # 命令行看轮次与状态
# 或直接开信箱仓的网页看提交流;或在装了 Yoma Desktop 的机器上回放会话
# (会话在跑它的那台机器上:%APPDATA%\Yoma\sessions)
```

### 5. 断了怎么办(都排练过)

- **断网/远端抽风**:两边退避重试;跑完没推出去的成果由"先推欠账再对齐"保住,
  恢复后原样送达,不重跑不重花钱;
- **进程被杀/机器重启**:重新执行第 4 步同一条命令即续跑(单实例锁防止重复起,
  持有者已死会自动接管);
- **换一台工位机续跑**:先把目标仓连同 `agent/<jobId>` 分支同步过去 —— 不带历史
  的话 runner 会拒绝开轮并把原因回填(防止前几轮修复静默蒸发);
- **单机模拟**(上手第一步建议先跑这个):`mailbox sim <job.json>`,零网络零凭据,
  本地裸仓当远端,`--remote` 一换就是双机形态。
