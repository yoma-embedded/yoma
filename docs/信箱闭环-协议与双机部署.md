# 信箱闭环:协议是什么、两台机器怎么跑起来

> 配套代码:`packages/bench/src/mailbox/`。本文回答两件事:两个 agent 之间**到底传什么**;
> 在两台机器上**从零怎么跑起来**(命令行形态;装了 Yoma Desktop 的走界面,见
> `docs/调试台-Windows双机上手.md`,两种形态可以混搭)。

## 零、先说清分工

角色字符串是 `mother` / `runner`,含义是:

- **mother = 研发端**。工程的完整检出和构建环境在这台机器上。它读工位端回填的证据 →
  改代码 → 构建 → 把产物当**附件**塞进本轮 → 用大白话写下一轮指令。它在项目仓上开
  `agent/<任务id>` 分支、每轮提交,终局通过时推交付分支。**板子不在这儿**。
- **runner = 工位端**。板子在这儿,而且**只有板子**。它领指令与附件 → 自己决定怎么上板
  → 复现、观察 → 把看到的现象如实回填。

依据是**手上有什么**:改代码要工具链和完整检出,那在研发机;上板要探针,那在工位机。

**工位端没有项目检出**(2026-08-10 起)。它的工作目录是一个一次性目录,里面只有研发端
附过来的文件。于是工位机不需要克隆目标工程、不需要交叉工具链、也没有"工作树必须干净"
这条纪律。代价是研发端写指令时要把上下文补全(见第一节末尾)。

## 一、传的是什么

**两个 agent 从不直接对话**。它们是两个独立的 yoma 内核会话,各自的模型上下文留在各自
机器上、不过网;过信箱的只有下面这些文件,全部可 `git log` 审计:

```
<信箱根>/
  job.json                     总任务书(两台机器读同一份)
  rounds/001/instruction.json  研发端 → 工位端:本轮指令(自然语言)
  rounds/001/artifacts/*       研发端 → 工位端:本轮附件(新固件、脚本、参考数据)
  rounds/001/patch.diff        研发端本轮的代码改动(相对任务基线,累计;审计与终报用)
  rounds/001/result.json       工位端 → 研发端:轮结果(**最后写** —— 它的存在 = 本轮完成)
  rounds/001/decision.json     本轮裁决(研发端 agent)
  verdict.json                 终局(出现即整个任务结束)
  report.md                    终报(与 verdict 同一次提交写入)
```

**一轮的输入是一整包**:指令 + 附件 + 补丁同住 `rounds/NNN/`,同一次提交推出去。

### instruction.json:一段人话 + 一份附件清单

有效载荷是 `prompt` 一个字段(纯文本),外加 `artifacts`(本轮附件的文件名与字节数)。
工位端组装轮提示词时会确定性地在它前面加两段:角色说明(只在会话第一轮)和**附件落点
清单**——那是调试台拷完文件之后自己列的,不靠模型复述。

指令长什么样,由研发端的角色提示词管着两条硬纪律(`mailbox/prompts.ts`):

1. **上下文由研发端补全。** 工位端读不到源码,所以"这个地址是什么变量""这一版改了
   什么""该盯哪个符号"必须写进指令。写之前先想一句:一个只看得见这段话和这几个附件
   的人,能不能照着做出来?
2. **不规定它用什么工具上板。** 烧录 / 跑附件里的脚本 / OTA,哪条路子对是工位端的判断。

### result.json:工位端看到了什么

| 字段 | 内容 |
|---|---|
| `turn.text` | agent 的自述正文(只收 assistant 的非 synthetic text part) |
| `turn.toolCounts` / `toolErrors` | 工具调用统计与报错,如 `{"flash":2,"gdb":9,"bash":22}` |
| `turn.usage` / `stopReason` / `errors` | 本轮花费、中断原因、provider 级故障 |
| `incoming` | 本轮附件落到工作目录里的**纯文件名**,由调试台落盘、不经模型 |
| `spentTokens` | 工位侧**跨轮累计**花费(只进终报,没有任何门限依赖它) |
| `error` | 轮级失败(子进程没产出结果)。有它时 `turn` 缺失 |

### decision.json / verdict.json:谁裁决了什么

研发端的产出是自由文本 + 结尾一个 ```json 围栏,只有围栏被机器读取:

```json
{ "decision": "continue", "analysis": "两三句对证据的解读",
  "instruction": "下一轮给工位端的完整指令", "artifacts": ["build/Debug/firmware.elf"] }
```

`decision` 只认 `continue` / `done` / `fail`。`continue` 必须带 `instruction`,
`done` / `fail` 必须带 `reason`。解析失败在同一会话里重试一次,再失败就终局 ——
守护循环里没有"这次不算",每次重试都是真实的模型花费。

**裁决分两层,层序即权力边界**:

- **代码不裁决任何东西**,包括什么时候停 —— 没有轮数/token/墙钟上限。闭环跑到研发端
  自己说 `done` 或 `fail` 为止;要提前收工就按停止(桌面端)或杀掉守护进程。
  `decision.by` 记 `"policy"` 只有一种情况:决定 JSON 连着两次读不出来,没法把它的话
  变成动作。
- **别的全归模型**,包括"这个任务算不算做完了"。研发端说 `done` 就是 `verdict.outcome
  = "passed"`,`by` 记 `"mother"`。

**没有独立判据机制。** "通过"就是研发端读完工位端自述之后的判断。所以研发端的提示词
要求它把**自证**写进指令 —— 让工位端报出的数字本身能说明问题(版本指纹、计数器增量、
原文照抄的日志),而不是让它回答"好了吗"。这一条是这套东西可不可信的全部依赖,写坏
指令的代价就是拿到一个说不清楚的 passed。

`verdict.outcome` 只有 `passed` / `failed` 两种。终报 `report.md` 与 verdict 同一次提交
写入,内容是决策链(每轮谁指挥、跑出什么、谁裁决的)+ 两侧最后的自述 + 会话回放指引。

### 附件是工位端拿到任何东西的唯一通道

新固件、诊断脚本、参考数据,全走这条路。agent 只在决定里**声明** `artifacts: [...]`,
拷贝、存在性检查、边界检查、大小上限由代码做(`store.ts` 的 `attachArtifacts`):

- 路径必须相对工程根,不能落在工程目录之外,同一轮里不能重名(信箱里会互相覆盖);
- 声明了但文件不存在是一个**能被逮住的错误**,不是一个空目录;
- 单轮合计默认上限 32MB —— 信箱是个 git 仓,塞进去的大文件永远瘦不回来。

**要给工位端 agent 加一件工具,就是往 `artifacts` 里多列一个文件**,不需要改协议。
换成 OTA 或远端 CI 产物时,变的只是指令里那句话和工位端手上的脚本。

### 状态是推断出来的,不落状态文件

没有 state.json。状态 = "最大的那个有 instruction 的轮次处在哪一步":

零轮次 → `kickoff`(等研发端开第一轮);instruction 有而 result 无 → 等工位端;
result 有 → 等研发端;`verdict.json` 出现 → 终局。

配合两条写入顺序纪律(工位端的 result.json **最后写**;研发端的 decision + 下轮
instruction + 附件 + patch **同一次提交**),崩溃在任何一步都只会退回"重跑本步"。

pull 是 `fetch + reset --hard + clean -fd`,工作树永远等于远端已推的真相。两侧的本地
状态(会话指针、基线提交、单实例锁)住在各自带 `.gitignore` 的目录里 —— `clean` 不删
被 ignore 的文件,这是它们的护身符。

## 二、工位端的工作目录

工位端这台机器上有两个目录:

1. **信箱克隆**,默认落在**规范位置**:

   ```
   ~/.my-pi/mailbox/clones/<远端+分支哈希>/<角色>
   ```

   这与桌面端是**同一个位置**(实现只有一份:`bench/src/mailbox/paths.ts`)。命令行
   不给克隆目录时用 `--remote <url>`,它会算出这条路径并按需 clone;想放别处就照旧
   显式传路径,这条逃生舱留着。

   `status` 有**自己的一份克隆**(角色目录是 `status`),不与守护共用 —— 它要
   `pullReset` 才看得到最新状态,而那是 `reset --hard + clean -fd`,共用目录就会把
   守护还没提交的那一轮原地清掉。显式指到守护的克隆上时它会发现锁并让开(不刷新,
   只显示本地已有的状态)。

   > **别随便放别处。** 单实例锁 `.yoma-lock/<role>.pid` 住在克隆目录**里面**,锁的是
   > "这个物理目录"而不是"这个信箱"。桌面端和命令行落在两个目录上时,两把锁互不知情
   > —— 同一个信箱同一个角色被跑起来两个守护,同时推同一个远端、同时抢同一块板子,
   > 而"另一个实例正在跑"那句话永远不会出现。

2. **一次性工作目录**,默认在克隆的**兄弟位置**:`<克隆的上级>/work/<任务id>/work`。
   `--work-root D` 改的是最外那层。

工作目录**绝不能落在信箱克隆里面**:`pullReset` 的 `clean -fd` 会把克隆里所有非跟踪
文件清掉,附件放在里面等于每轮被自己删一次。

本轮附件落在这个工作目录的**根**(不是某个子目录),同名覆盖 —— 那才是"新版本替换
旧版本"的语义。**不清空**:某一轮没带附件不代表旧固件失效,板上跑的还是它。

工位端在这里没有 git、没有源码、没有构建产物,只有历轮附件加上 agent 自己写下的东西。

## 三、两台机器,从零跑起来

### 0. 信箱可以是任何 git 远端 —— 对,随你填

协议只依赖 `git fetch/push`:GitHub/Gitee 私有仓、公司 GitLab、NAS 上的裸仓,甚至局域网
共享盘上 `git init --bare` 出来的目录都行。唯一要求:**两台机器都能读写它**(SSH key 或
HTTPS 凭据各自配好)。**一个信箱同一时间只跑一个任务**,每个角色只能有一个守护实例
(`.yoma-lock/` 里的 pid 锁;持有者已死会自动接管,不需要人工清锁)。

### 1. 两台机器共同的前置

```powershell
# ① Windows:开发者模式 + git 符号链接(README「Windows 用户」一节,一次性)
git config --global core.symlinks true
# ② 装 bun,克隆 yoma-pi 仓(bench 直接跑源码,无需构建)
git clone <你的 yoma-pi 仓> C:\yoma-pi
cd C:\yoma-pi && bun install
# ③ 模型凭据(与 Zed/桌面端同一份)
#    %USERPROFILE%\.my-pi\auth.json → {"deepseek":{"type":"api_key","key":"sk-…"}}
#    (格式必须带 "type" 判别字段,少了会被 pi-ai 静默忽略)
# ④ 信箱仓**不用手动克隆** —— 给 --remote,它会落在规范位置并按需 clone:
#    %USERPROFILE%\.my-pi\mailbox\clones\<远端+分支哈希>\<角色>
#    与桌面端同一个位置(见第二节的警告:落在别处会让单实例锁形同虚设)
```

### 2. 研发机独有的前置

- **目标工程的检出**,而且是 git 仓 —— 调试台要在它上面开 `agent/<任务id>` 分支提交;
- **工作树干净**:开轮时 `prepareBranch` 会检查,脏了直接拒("agent 的改动必须能和你的
  区分开");
- **交叉工具链在 PATH 里**(`arm-none-eabi-gcc`、`cmake`、`ninja` 之类)。它要真的能把
  固件编出来 —— 编不出来的东西研发端不该往下发。

### 3. 工位机独有的前置

- **engines**(probe-rs 等引擎二进制):跑 `bun engines\build.ts`,或按
  `packages/desktop/engines.lock.json` 钉住的 tag 下载对应平台的预编译产物解到
  `engines\`;临时也可用 `YOMA_ENGINES_DIR` 指向现成目录;
- 探针驱动(ST-Link 插上,设备管理器里认得出即可)+ 目标板。

**就这些。**不需要目标工程的检出,不需要交叉工具链,也不用预装 Python 之类的脚本运行时
—— 要跑什么脚本,研发端会当附件送过来(送过来的东西能不能在这台机器上跑起来,是研发端
写指令时该考虑的事)。

### 4. 写任务书

一份 JSON,两台机器读同一份,所以**里面不许有绝对路径**。
可以拿 `packages/bench/example/mailbox-job.example.json` 改。

```json
{
  "id": "m-20260810-01",
  "title": "修复 CAN 掉帧(信箱闭环)",
  "repo": { "name": "motor-fw", "ref": "develop", "branch": "agent/m-20260810-01" },
  "bench": { "board": "nucleo-g474re", "chip": "STM32G474RE", "probe": "0483:374E:0670FF53" },
  "task": "## 工位与安全约束(每个任务都适用)\n1. 绝不能让电机转动……\n\n上电约 30 秒后 CAN 开始掉帧。复现:烧录后 100kbps 满载发送。期望 RX 计数与 TX 一致。\n构建命令(研发端用):cmake --build build/Debug",
  "deliver": { "push": true, "remote": "origin" },
  "model": { "providerID": "deepseek", "modelID": "deepseek-chat" },
  "mailbox": {
    "pollSeconds": 15,
    "maxArtifactBytes": 33554432,
    "mother": {
      "model": { "providerID": "deepseek", "modelID": "deepseek-chat" },
    }
  }
}
```

几处值得停一下的:

- **`repo.directory` 不写。** 工程目录是本机事实,由研发机的 `--project` 提供;
  `serializeMailboxJob` 入箱时也会主动摘掉它。工位机根本不需要这个配置。
- **`task` 是 agent 唯一的任务来源**,两个角色都会读到它。项目级前置约束(安全红线、
  目录禁区、构建命令、已知现象)写在这里 ——"电机绝不能转"这种事不靠人每次记得重复。
- **没有预算字段**。跑几轮、花多少钱由研发端 agent 自己判断,任务书里没有上限可配。
  注意口径:计的是 input+output,而研发端会话跨轮延续,后期轮的 input 里含全部历史 ——
  设得太小会在最接近收尾的那一轮误触发"分析被中断"。
- **`deliver.push`** 不开的话交付分支只留在研发机本地(这是显式开关,不是 bug)。

先校验一遍再入箱:

```powershell
bun C:\yoma-pi\packages\bench\src\cli.ts check D:\jobs\fix-can.json
```

它只做两件事:任务书合法性 + 本机内核能不能装配出 10 个工具。不碰信箱、不碰板子。

### 5. 开跑(每台一条常驻命令)

```powershell
$MB = "git@github.com:you/your-mailbox.git"

# 研发机:任务入箱(校验 spec → 写 job.json → 推送)。克隆不存在会自动建。
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox init D:\jobs\fix-can.json --remote $MB

# 研发机:改代码的那一半(--project 指本机的工程检出)
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox mother --remote $MB --project D:\work\motor-fw --interval 30

# 工位机:板子在这儿(不需要 --project)
bun C:\yoma-pi\packages\bench\src\cli.ts mailbox runner --remote $MB --interval 30
```

不给 `--remote` 就得显式传克隆目录(`… mailbox mother C:\mailbox …`)——两者必须给一个。
**优先用 `--remote`**:它落在与桌面端相同的规范位置,单实例锁才管得住"同一个信箱同一个
角色只能有一个守护"。

入箱之后信箱里只有 `job.json`,状态是 `kickoff` —— **第一轮由研发端出**。它先读任务书,
可能先改代码、先构建,把产物附上再下发。之后闭环自转:工位端领指令与附件 → 上板复现 →
回填;研发端读结果 → 改代码 → 下一轮,或者终局。终局后两边进程各自退出(通过且
`deliver.push` 开着时,研发端在写下 verdict 的同一步推交付分支)。

其它旗标:`--branch B`(信箱分支,缺省 main)、`--once`(只走一步就退,cron 场景)、
`--work-root D`(工位端一次性工作目录的根)。

随时看进度:

```powershell
bun …\cli.ts mailbox status --remote $MB   # 命令行看轮次与状态(守护在跑时也能随时看)
# 或直接开信箱仓的网页看提交流;或在装了 Yoma Desktop 的机器上回放会话
# (会话在跑它的那台机器上:%APPDATA%\Yoma\sessions)
```

### 6. 先跑一次单机模拟

上手第一步建议先跑这个:

```powershell
bun …\cli.ts mailbox sim D:\jobs\fix-can.json --project D:\work\motor-fw --fresh
```

它在一台机器上起**两个真子进程 + 各自的克隆 + 一个本地裸仓当远端**,除了远端 URL 之外
与生产形态一模一样(`--remote <私有仓>` 一换就是双机形态)。模拟根默认在
`<工程>/.my-pi/bench/mailbox-sim/<任务id>`,`--root` 可改。

### 7. 断了怎么办(都排练过)

- **断网 / 远端抽风**:两边指数退避重试;跑完没推出去的成果由"先推欠账再对齐"保住,
  恢复后原样送达,不重跑不重花钱。
- **进程被杀 / 机器重启**:重新执行同一条命令即续跑(单实例锁防重复起,持有者已死会
  自动接管)。工位端的会话指针与研发端的基线提交都在被 ignore 的目录里,`clean -fd`
  不会碰它们。
- **换一台工位机续跑**:直接在新机器上克隆信箱、起 runner 就行 —— 它没有项目检出,
  也就没有"历史带不带得过去"的问题。板上跑的固件是上一轮附件烧进去的,新机器的工作
  目录是空的,下一轮的附件会自己过来;如果这一轮需要旧附件,让研发端重附一次。
- **换一台研发机续跑**:目标工程连同 `agent/<任务id>` 分支要一起同步过去,否则新机器
  会从当前 HEAD 重新拉基线,前几轮的修复就静默蒸发了。
- **探针冲突**:同一台工位机上,交互会话和调试台任务会抢同一个探针(2026-08-10 起
  没有互斥锁了),症状是 `exclusive access (0xe00002c5)`。任务在跑的时候别在同一台机器
  上开会话动硬件。
