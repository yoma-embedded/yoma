## 今晚在代码上改了什么

### 1. 克隆目录带上分支(桌面端 + CLI 两处)

就是上面第 2 步那个坑。`cloneDirFor` 现在把分支拌进 hash,换分支 = 换目录;`ensureClone`
另外加了一道分支核对,不一致就报人话而不是拖到 push 才吐 git 黑话。

### 2. "解释器在 PATH 上但根本跑不了"现在归成环境问题 ← **对你明天最要紧**

昨晚工位端的判据挂在 `python3` 上,exit 9009,报 "Python was not found"。那是微软商店的
**应用执行别名**:一个 0 字节的桩,`stat` 得到、在 PATH 上、看起来完全正常,一跑就让你去商店。

要命的是它被归成了**判据没过**(代码问题),而不是**环境错误**。区别是:

- 判据没过 → 研发端接着下一轮,继续"修"一个根本不存在的代码 bug,烧完 8 轮预算
- 环境错误 → 确定性守卫直接 park,报"这台机器的问题",不烧钱

现在 `resolveScriptArgv` 在 PATH 命中之后**真起一次 `<解释器> --version`**,退出码 0 才算数
(只探解释器,绝不带上脚本 —— 判据的副作用不能在探测阶段发生;结果按解释器缓存)。
报错也分了两种口径:

> py -3 / python / python3 在 PATH 上找得到,但执行 --version 不成功 —— Windows 上这几乎
> 总是"应用执行别名"的桩(跑起来只会让你去微软商店,exit 9009)。装一个真的解释器,
> 或者到 设置 → 应用 → 高级应用设置 → 应用执行别名 里把它关掉。

在 macOS 上用假桩复现了这个场景当回归测试(造三个 exit 9009 的假 python 顶在 PATH 上)。

**顺带挖出一个 bun 的坑**:`spawnSync` 省略 `env` 时**不认运行时改过的 `process.env.PATH`**,
它按进程启动那一刻的环境解析 argv[0](和 `os.homedir()` 同一类)。自检因此会探到另一个
程序、给出对不上的结论。已显式传 `env`。

### 3. 分支配错时,工位端会照着**别的任务**的指令动板子 ← 最凶的一个

这条是排查过程里挖出来的,比第 1 条严重得多。

`pullReset` 在 `origin/<新分支>` 还不存在时**什么都不做** —— 那是首推之前的合法状态。
但如果克隆停在 `main` 而配置要跑 `run-1`,后果就是工作树仍然是 `main` 的内容,扫描器
读到的是**上一个任务**的 `job.json` 和待执行轮。于是工位端会真的:

1. 领走别的任务的指令(实测:提示词里是"把电机跑到 3000rpm")
2. 烧片、跑判据、失败后回刷 known-good —— **硬件动作真的发生了**
3. 跑完一整轮,才在 push 那一下报 `src refspec run-1 does not match any`

对你这台板子来说,"照着另一个任务的指令动手"是能出事的 —— 那个任务的安全前提可能
和当前的不一样。

**你现在没中这一枪**,是运气:信箱 `main` 上那一轮**已经有 result 了**(昨晚工位端跑完
回填的),状态是"等研发端",工位端对这个状态只会闲等。所以哪怕你的 Windows 克隆还停在
`main`,它昨晚到现在也只是在空转。但这不改变结论 —— 那个克隆目录必须删,否则它永远
领不到 `run-1` 上的活。

另外注意:**你 Windows 上装的是修之前的版本**,这道闸门在它上面还没有。这也是为什么
第 2 步(删克隆缓存)是必须做的,而不是"最好做一下"。

现在 `pullReset` / `flushThenPullReset` 最前面加了一道闸门:**克隆当前分支必须等于要跑的
分支**,不等就当场停,报人话。拦在模型调用和硬件动作之前。回归测试直接断言这两条:
`prompts` 为空、`hardware` 为空。

同时把 `runnerStep` / `motherStep` 里那一跳同步包进 try —— 配置级问题应该走 `blocked`
(守护对它有指数退避),而不是裸抛到守护循环外面。

### 4. 冒烟脚本不再留孤儿守护

`mailbox-smoke.ts` 超时时直接 `SIGKILL`,而 sim 守护下面还挂着两个角色子进程和 turn 孙进程
—— SIGKILL 捕获不到,守护来不及转杀,孙进程就漏出去了。你机器上真有一个:从 8-07 18:53
一直空转到今天,烧了 5 分钟 CPU。已改成 SIGTERM + 10 秒宽限 + 补硬杀,并且接管 Ctrl-C
(以前 Ctrl-C 也漏)。那个孤儿我清掉了。

这次是 mother 角色,只是白烧 CPU;同样的漏法出在 runner 角色上,就是一个攥着探针不放的
孤儿 —— 而那个报错长得和"没插板子"一模一样。

### 5. 还顺手修好的

`mailbox-smoke.ts` 里逐 chunk `Buffer.toString()` 解码 —— 就是 CLAUDE.md 里记着的那条。
终局那一行带着整份终报,中文 3 字节/字轻松超过一个 pipe chunk,边界劈开多字节字符会得到
两个 U+FFFD,而 JSON 结构字符全是 ASCII、`JSON.parse` 照样成功,乱码静默进判定。
已换成 `TextDecoder` + `{ stream: true }`。

## 一个设计问题,你来拍板

**墙钟预算从第 1 轮指令下发时刻起算**(`mailbox/mother.ts:428`)。也就是说"挂起等对方上线"的时间**算进预算**。

今晚这就咬了一口:我本来想把第 1 轮先备好、让你早上一开机就有活干,结果发现那样的话 120 分钟墙钟会在你睡觉时走完,工位端刚接手就被判"预算耗尽"终局。所以我没那么做。

两条路:

- **保持现状**,规则简单:墙钟就是"这个任务从开跑到现在"的绝对时间。代价是跨时区/隔夜/等人上线的场景要把墙钟设得很大。
- **改成只算"双方都在线"的时间**,或者干脆按"最后一次有进展"起算。更贴近意图,但要引入"什么算在跑"的判断,规则变复杂。

我倾向第一条 + 在 UI 上把这件事说清楚(预算档旁边加一句"墙钟从第 1 轮下发起算,包含等待对方的时间")。但这是产品决策,你定。
