## 2. 文章框架(只留用到的)

- 术语:task / trial / grader / transcript / outcome / harness / suite。判 outcome 优先于判 transcript。
- 三类 grader:代码判(快、客观、脆)/ 模型判(灵活、要人工校准、给"Unknown"出口)/ 人判(金标、慢)。
- capability eval 起步应低分(爬坡用);regression eval 要 ~100%。满分后"毕业"成回归集。
- pass@k(k 次至少一次)vs pass^k(k 次全过);不可逆动作看 pass^k。
- 路线图:从 20–50 个真实失败起步;任务要"两个专家独立判同一个 pass/fail";**每题带参考解**证明可解且
  grader 没配错;正反用例平衡;每 trial 干净环境(Anthropic 撞过 agent 翻上个 trial 的 git history);
  判产出不判路径但防作弊;**读 transcript**;0% pass@100 多半是题坏了;评分不读 transcript 不信。

## 3. 嵌入式 agent 为什么不能照抄(设计前提)

1. 环境里有硬件:不可并行、有状态(flash 内容跨 trial 残留)、flaky、稀缺 → 按吃多少硬件分层。
2. 产出是"诊断 + 证据 + 修复",不是代码;植入 bug 的题真值唯一。
3. "量没量"是 outcome 级属性:嵌入式头号失败模式是看源码编一个合理解释、没上板量;猜对也不算对。
4. 有不可逆动作(option bytes / RDP L2 / 擦错片):负向用例要求 pass^k≈100%,触发即整 trial fail。

分层方案:

| 层 | 靶机 | 内容 | 仓里已有 |
|---|---|---|---|
| L0 引擎回归 | 无模型 | controller_map 7 份网表 + check 脚本、stm32kernel golden | 全有 |
| L1 纸面题 | 临时目录 | 网表/stm32config/离线取证/负向行为题 | 网表 fixture、golden |
| L2 仿真 | QEMU / Renode | gdb fixture 的 11 个场景变调试题;植入 bug 的 fail-to-pass | `fixture.elf` + README 期望值表;缺可编译的 STM32 工程 |
| L3 真板 | eval rig,夜跑 | 烧录/串口/RTT/真 HardFault;每 trial 烧回 golden + 断电上电,失败记 error | 三工具;缺 rig |
| L4 信箱协作 | `mailbox sim` | mother 指令是否补全上下文;runner 报告带指纹 | sim、parseMotherDecision |

## 4. 已交付(分支 `worktree-evals`)

**`packages/evals`**(`@yoma-desktop/evals`;typecheck 8/8 绿;67 单测绿;oxlint 零新增)

- `README.md` 是契约:task.json schema、grader 表、trial 四态、selftest、CLI、出题纪律。**改 evals 先读它。**
- 执行:复用 bench 的 `runTurnInChildProcess` → 一 trial 一子进程(`turn-entry.ts`),与桌面端/调试台同一条路径;
  会话 JSONL 落 `runs/<stamp>/sessions/`,`--sessions-root` 可指到桌面端目录回放。
- grader 注册表:`answer`(取 `TurnResult.text` 最后一个 ```json 围栏)/ `grounded`(needles 必须出现在某次
  已完成工具的输出里)/ `tool-called`(慎用)/ `tool-forbidden`(安全红线)。
- 四态:`pass` / `fail` / `error`(基础设施:子进程崩、硬超时、provider 失败到最后;**不计入通过率**)/ `skip`(requires 不满足)。
- `selftest`:每题用假模型(`fauxResolveModels`)跑"参考解必须 pass、坏解必须 fail"。
- 报告:pass@1 / pass@k / pass^k,按题、按 tag;指标只记不判(turns、tokens 含 reasoning、cost、elapsed)。
- 仓级小改:`TurnInput` 加 `hardTimeoutMs`/`settleMs`;`kernel-alias.test.ts` 钉住第五份 paths 副本;CLAUDE.md 两张表加行;根 `test` 脚本加 evals。

**15 道网表题**(`packages/evals/tasks/netlist/`,清单见同目录 README):5 份夹具全用到,10 easy + 5 hard,
答案用 `controller_map.exe` / `board_ir.exe` 直跑核实 —— **这正是后来被质疑的点,见 §6**。

**命令**

```
bun --cwd packages/evals test
bun packages/evals/src/cli.ts list
bun packages/evals/src/cli.ts selftest --engines-dir <主检出>/engines
bun packages/evals/src/cli.ts run --k 3 --model deepseek/deepseek-v4-flash --thinking max --engines-dir <主检出>/engines
bun packages/evals/src/cli.ts report <runDir>
```

注意:worktree 的 `engines/bin` 是空的(构建产物不入库),`--engines-dir` 要指到跑过 `bun engines/build.ts`
的检出;跑真模型需要 `~/.yoma/auth.json` 里有 deepseek 凭据。`runs/` 被 gitignore,**结果与会话不随仓库走**。

## 5. 首跑结果与读 transcript 的发现

| 配置(deepseek-v4-flash,k=3,45 trial) | pass@1 | fail | error | 平均 turns | 平均 reasoning tokens | 花费 |
|---|---|---|---|---|---|---|
| thinking max(调试台默认) | 100% | 0 | 0 | 4.7 | ~1100 | ~$0.15 |
| thinking off(桌面端不注入时的实际默认) | 97.8% | 1 | 0 | 4.0 | 0 | ~$0.13 |

- selftest 30/30 绿。
- 读了 3 条 transcript:hard 题 `nrf52840-p031-fanout` 过程真实(试 part 报错 → 裸模式见低置信度 → 覆盖主控 U1 →
  grep 原始网表交叉验证);`qspi-ss-dnf` 在工具 10k 截断后退回原始 XML 逐网查,正确。
- 唯一 fail:`sumobot-servo-timer` off 档 —— agent 没调 netlist 工具,`read` 原始网表找到 PB0/PB1 后**凭记忆**答
  "F103 上这是 TIM3 CH3/CH4"。答对、零证据,`grounded` 判 fail。要不要把"凭记忆答对"算 fail 是产品决定,Claude 建议算。
- 顺带逮到的产品坑(未修):① `runEngine` spawn 不钉 `PYTHONIOENCODING`,中文 Windows 上引擎 stdout 是 cp936,
  工具输出里已有 U+FFFD;② netlist 工具对非 STM32 料号传 `part` 时报 "--stm32kernel needs a part number; pass --part",
  误导;③ 裸模式 10,000 字符截断太狠(RP2040 只到 pin 20),非 STM32 板上 agent 每题多花 5–8 次 bash 翻原始文件。

## 6. 用户的质疑与承认的问题(重要)

用户:"这些 eval 都是你自己写的,而且全部一次性通过,你自己就是 AI,这靠谱吗?"

Claude 承认的实锤:

1. **参考答案与被测工具同源(循环论证)**:答案是子 agent 跑 `controller_map.exe` / `board_ir.exe` 得的,
   被测 agent 的 netlist 工具调的就是它们。引擎错则一起错,eval 照样绿。`p031-fanout` 的 note 自己写着"从引擎输出推出"。
2. **题按"工具能吐什么"反推**,不是按"用户会遇到什么";prompt 有暗示(p031 提醒"别把调试器的脚当成 nRF52840 的")。
   100% 的真实含义只是:工具没坏、agent 会调它、会读 10k 输出、听格式。
3. **出题 AI 对难度的预测全错**(点名 4 道会错的全过)→ 不知道悬崖在哪;一套从没红过的 eval 没证明过自己。
4. `grounded` 的 needles 偏弱(`U1`、`J3` 到处都是),多数题退化成"调过工具"。
5. 只读了 90 条 transcript 里的 3 条。

站得住的:grader 是精确匹配、可审计、不是 AI 判 AI;selftest 反向 15/15;off 档那个 fail 是真实逮到。
作为**回归集/冒烟**有效,作为**能力评估**无效。

**随后用户确认:`engines/controller_map/tests/check.py` 的断言也是模型生成的。** 于是 15 题的参考答案
全部是 AI 来源,没有一个人类确认过(不等于错,但等于未经确认)。

## 7. 调整后的计划(尚未执行)

真值只认两种来源:

- `construction`:变异夹具 / 植入 bug —— 例如把 RP2040 网表里 GPIO0 从 `J3.4` 挪到 `J3.7`,答案按构造就是 `J3.7`,
  与引擎无关;引擎答不出是引擎 bug。顺带防住公开板子在训练数据里。L2 植入 bug 固件同理。
- `raw-excerpt`:原始网表原文片段(行号 + 原句,grep 级查询摘出,不经引擎)+ 人过目。网表本身是人能读的扁平列表,
  十几秒扫一条。STM32 复用表事实锚到数据手册。

引擎输出与 check.py 一律降为旁证;`reference` 加 `source` 字段;现有 15 题全部补原文证据,站不住的删。

执行顺序(Claude 建议,用户尚未点头):

1. 变异题(真值按构造)
2. selftest 的坏解升级为三种像样的失败:答对没调工具 / 调了工具答错 / 答对但碰 flash
3. 对 eval 本身做变异测试:拔掉 netlist 工具、换弱模型,套题必须掉分
4. 正反平衡与去暗示:删 p031 的提示句;加"不存在"题(悬空脚问接哪)、"前提错误"题(不存在的 R5)、"料号撒谎"题
5. `grounded` 加 `within` 邻近约束,换弱 needles
6. `transcript` 子命令,把失败 trial 压缩打印

必须用户来做:提供 10–20 个真实失败会话(`%APPDATA%/Yoma/sessions`)并用原话写 prompt;决定"凭记忆答对算不算 fail";
读 transcript。不建议:上 LLM judge 来审题(再叠一层 AI 判 AI);先扩到 50 题(刻度没校准前多量无意义)。
