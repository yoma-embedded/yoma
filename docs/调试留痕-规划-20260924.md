## 1.5 结论先行

1. **状态行**:内核在 `session.status` 的 busy 里带上 `activity`(此刻在干什么 + 从何时开始),**只在阶段变化时推**;界面自己走表。
   「思考中」那一行变成:等待模型响应 12 秒 / 思考中 23 秒 · 4.1k 字符 / 正在写 bash 调用 3 秒 / 正在运行 bash 45 秒 / 等你确认 flash 8 秒。
2. **工具卡片**:在跑的通用卡片显示命令(副标题)和已跑时长 —— 由并行的 tool-display 分支做,这里不重复(§2.3)。
3. **系统提示词**:有 grep / find / ls 工具时,守则里明说用它们找文件、别用 shell 递归扫 node_modules / 构建产物 / 整个盘。
4. **轨迹文件**:内核往本次启动的日志目录写 `trace.jsonl`,一行一个关键节点(会话、轮次、模型请求的发出 / 响应头 / 首字 / 结束 /

5. **分析**:`npm run trace -- <会话文件或 id>` 读会话 JSONL(必有)+ 同一 userData 下的 trace(有就合并),打时间线、标出慢的那几步
   并给一句判断。"Export logs" 的 zip 里多了 trace 与最近 24 小时的会话。

### 2.2 此刻在干什么(内核 → 状态行)

**类型**(`kernel/src/types.ts`,浏览器安全):

```ts
export type SessionActivity =
  | { phase: "waiting"; since: number }                 // 请求已发出 / 工具刚跑完,模型还没吐第一个字
  | { phase: "thinking"; since: number }                // 推理在流
  | { phase: "writing"; since: number }                 // 正文在流
  | { phase: "calling"; since: number; tool: string }   // 模型在写工具调用的参数
  | { phase: "tools"; since: number; tools: string[] }  // 工具在跑(since = 这一批最早开跑的那个)
  | { phase: "confirm"; since: number; tool: string }   // 等用户在确认条上点
export type SessionStatus = { type: "idle" } | { type: "busy"; retry?: ModelRetry; activity?: SessionActivity } | { type: "compacting" }
```

**状态机**(`kernel/src/host/activity.ts`,纯类,注入 `now`):

| 事件 | 变成 |
|---|---|
| `run_start` | waiting(since = 现在) |
| `message_start`(assistant) | 保持 waiting(since 不动 —— 用户等的是"请求发出之后";pi-ai 的 start 事件在响应头到了之后才发) |
| `message_update` 的 thinking_* / text_* / toolcall_* | thinking / writing / calling(工具名取 `message.content[contentIndex].name`) |
| `tool_start` / `tool_end` | tools(维护在跑集合);集合空了 → waiting(since = 现在) |
| 确认条挂起 / 结算 | confirm(tool);结算后由下一个事件接管 |
| `run_end` | 清空 |

**只在阶段变化时推**:一个 step 大约 5–10 条 `session.status`,不是逐 delta。`setStatus` 的去重从"type + retry 引用"扩成
"type + retry + activity 引用"。`host/stream.ts` 的 StreamSink 把**同一会话相邻的两条 busy** 合成后一条(idle 不合 —— 通知靠它)。
bench 对 busy 只做 `cancelSettle`,多几条无害;app 的归约是 `reconcile`,行的 memo 只读 `status().type` 与 `retry`,
activity 变化不重建行(用 `timeline-projection.test.ts` 的计数闸门钉住)。

**界面**(`app/src/pages/session/timeline/`):

- (合并后,见 §8)那一行以 tool-display 的「按阶段说话」为准(`timeline/activity.ts` + `activity-row.tsx`):内核给了 activity 就用它
  (带起点),后面跟已过时长,一秒一跳,思考时跟推理字符数,等确认时说「等待确认 …」;没有 activity(过渡瞬间)按 part 推断、不走表;
  写正文、写调用参数时不出字。**行的结构不变**(`rows.ts` 不动,Thinking 行出现 / 消失的条件原样),只换行里的字。推理字符数由组件读
  这一轮最后一个 reasoning part 的长度 —— 是组件在读,不是行的 memo(规矩 1)。
- 文案用 ui 包里 tool-display 建的 `ui.sessionTurn.status.*` 那一组,这边只加 `waitingConfirm` 与 `thoughtChars` 两条。
- 时长格式与子 agent 坞一致:`45 s`、`2 min 05 s`。

### 3.3 模型请求的 HTTP 探针(`host/trace/model-probe.ts`)

- `resolveModel` 里套在看门狗**里面**:`withStreamGuard(withModelTrace(createModels(…), trace))`。看门狗在外层先注入它的 fetch,
  探针在内层把它再包一层 —— 链是 探针 → 看门狗 → 真 fetch,正文从真 fetch 经看门狗到探针再到 SDK。反过来的话,探针先占住
  `options.fetch`,看门狗就不注入了(它只在调用方没给 fetch 时注入)。
- 每次调用建一个 fetch:记请求(host / path / 字节数 / 模型)、响应头(状态码、TTFB、请求 id 头)、逐块统计正文(总字节、块数、
  **`:` 开头的 SSE 注释行 = keep-alive**、第一行 `data:` 的时刻、最大块间隔),结束时一行 `http.end`;响应头到了 30 s 还没数据就先写
  `http.wait`(正排队的那一刻就留下证据,哪怕随后用户把 app 关了)。
- 看门狗触发时探针看到的是一条带 "model stream idle timeout" 的错误,记成 `outcome: "error"`。

### 3.4 内核卡死

- 内核里:1 s 一拍的漂移检测,堵 ≥ 1 s 写 `kernel.lag`(只能在恢复之后写)。
- main 里:内核 5 s 发一次心跳(`parentPort.postMessage({type:"heartbeat"})`),main 20 s 没收到就在 `kernel.log` 记
  `kernel unresponsive`,恢复时再记一条带时长的;main 自己的计时器也晚了(main 被堵)那一拍不算。纯逻辑放 `main/kernel-heartbeat.ts` 配单测。

### 3.5 "Export logs"

`main/logging.ts` 的 `exportDebugLogs` 多收一个目录:`<userData>/sessions` 里 24 小时内改过的会话(沿用现有的 24 小时 / 单文件 50 MB
规则),manifest 里注明带了会话。trace 在日志目录里,本来就会被收进去。**会话里有对话全文**:导出包是本机文件,给别人之前用户自己把关。

### 3.6 分析脚本

- `npm run trace -- [会话文件 | 会话 id 前缀] [--slow 秒] [--trace 文件]`;不给会话就取最近改过的那个。会话在 Windows 的
  `%APPDATA%/com.yoma.desktop{,.dev,.beta}/sessions`、macOS 的 `~/Library/Application Support/…`、Linux 的 `~/.config/…` 里找;
  trace 在同一 userData 的 `logs/*/trace*.jsonl` 里按会话 id 筛(子会话的一并带上)。
- 只读:自己按行解析 JSONL,不经上游的 `JsonlSessionRepo`(它打开一个尾行撕裂的会话会**改写文件**)。
- 输出:时间线(用户消息、每次模型请求的耗时 / 首字 / 推理与正文字数 / tok/s / 调了哪些工具、每个工具的耗时与摘要、重试、
  中止、失败),再加一段汇总与判断:模型 vs 工具各占多少、最慢的几步、有没有排队(keep-alive)、有没有重试、内核有没有被堵。
  慢工具的命令像递归扫描(du / grep -r / find / ls -R / Get-ChildItem -Recurse)时标出来。
- 逻辑在 `kernel/src/host/trace/report.ts`(只用 node:fs / node:path),经新的叶子门 `@yoma-desktop/kernel/host/trace-report`
  给 `scripts/trace.ts` 用;测试用 faux 模型真跑一段会话(真 JsonlSessionRepo 写盘 + 真 trace),再让报告去读 —— 上游一改会话格式它先红。
