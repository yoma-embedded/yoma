## 一、这个仓是什么

同一个产品(面向嵌入式调试的 agent),换掉了整个后端,并把两个仓库合成了一棵树。

`88e2efe` 用 `--allow-unrelated-histories` 把 **my-pi**(33 条提交)与 **yoma-desktop 谱系**(58 条)合并。合并理由:两半从不独立发布 —— 打包时 esbuild 把内核源码整个 inline 进 `out/main/kernel.js`,用户装的包里没有"内核这个包"。

`packages/` 下 **10 个包**(不是 `CLAUDE.md` 写的 7 个):内核三包 `ai`/`agent`/`coding-agent`(约 3.1 万行)+ 桌面端七包 `desktop`/`app`/`kernel`/`ui`/`session-ui`/`util`/`bench`(约 9.7 万行)。

### 内核换了什么

| | 旧(opencode 内核) | 新(my-pi + pi-ai) |
|---|---|---|
| agent 循环 | Effect 服务 + Vercel AI SDK `streamText` | 自研 `agentLoop` + `AgentHarness` 相位机 |
| 会话模型 | MessageV2 消息/分片,落库 | append-only 条目树 + JSONL,`leaf` 条目即光标;压缩改的是**投影**不是历史 |
| 数据面 | 本地 HTTP sidecar + 端口/密码 + SSE + 生成 SDK | MessagePort 直连 utilityProcess,无 HTTP;`packages/sdk` 整个删掉 |
| provider | models.dev 目录 + 20 多个 `@ai-sdk/*` | pi-ai 直连 Anthropic/OpenAI 两套 HTTP API;产品侧 `PROVIDERS` 表只有 deepseek 与 moonshotai-cn |
| 凭据 | opencode 数据目录 auth.json | `~/.my-pi/auth.json`,条目必须带 `type:"api_key"`,缺了被静默忽略 |
| 工具 | 24 个 + `ctx.ask()` 权限门 | **12 个**,无权限门 |

新工具集(`tools/index.ts:233,252`,顺序即嵌入式流水线):编码六件 `read`/`bash`/`edit`/`write`/`toolchain`/`examples` + 嵌入式六件 `netlist`/`datasheet`/`stm32config`/`flash`/`log`/`gdb`。

### 旧仓有、新仓没有的

- **cmd 真终端页**在 `31fcbf2` 随 `terminal.tsx` 一起删掉,没有替代 —— `NodeExecutionEnv.exec` 是一次性 spawn 不是 pty。而 `@lydell/node-pty` 的依赖和 6 个平台包还钉在 `packages/desktop/package.json:53,60-65`,vite 配置里还为它留了 externalize 路径,**全仓零源码引用**。这条尾巴该剪。
- **datasheet 本地 RAG 四工具**(含 `download_manual` 与 LanceDB+bge-m3 本地管线)重写成一个工具三动作,全部按需打 `YOMA_DATASHEET_SERVER`;`engines/` 里不再有 `RAG_yoma`。

### 新长出来的三条线(旧仓完全没有)

1. **bench 无人值守调试台 + 信箱闭环**(`packages/bench`,41 文件)。两台机器,唯一通道是一个 git 仓;状态由文件存在性推断不落状态文件;`pull = fetch + reset --hard + clean -fd`。`mailbox/loop.test.ts` 是整套协议的可执行说明书。
2. **例程库**(`core/examples/`)。离线索引 esp-idf + stm32cube-f1/f4/h7 四份语料共 2654 条,全量模型富化成足迹卡片,`examples` 工具给 `search`/`info`/`seed`/`preflight` 四个动作。
3. **工具链清单**(`core/toolchain/`)。三份文件:提交进库的零绝对路径声明、不提交的项目覆盖、本机账本;七档探测;`side` 参数让工位端不对 cmake/arm-gcc 一路报 MISSING。

### 这个仓的工程特色:结构化复制 + 编译期闸门

`host/details-check.ts`(工具 details,而且专门论证了为什么必须是 `Expect<T extends true>` 而不是 `as never` —— 后者是不会响的闸门)、`bench/mailbox/view-check.ts`、`mypi-alias.test.ts`(四份路径映射)、`thinking.test.ts`(拿真 pi-ai 对答案)、`host/auth.test.ts`(逼问式 provider 名单核对)。

**这套模式是这个仓最有价值的资产,下面所有建议都是它的推广。**

## 三、结构性债:没有闸门的地方

这是整份文档最要紧的一节。规律只有一条:

> **凡是有闸门的地方,AI 写的代码没有失控;凡是没有闸门的地方,都已经漂了。**

`details-check.ts`、`mypi-alias.test.ts`、`thinking.test.ts`、`auth.test.ts` 覆盖的东西一律干净 —— 因为漂了就编译失败或测试红。反过来:

### CI 一行测试都不跑

`.github/workflows/` 只有两个文件,**都是 `workflow_dispatch` 手动触发**:

- `desktop-win.yml`:bun install → (可选)构建引擎 → `bun build:desktop` → `package:win` → 用 magic bytes 检查 `.engines-stage/bin` 是 PE → 上传 artifact
- `engines.yml`:构建/发布三平台引擎产物

**没有 `bun run test`、没有 `bun typecheck`、没有 `bun lint`。** 对这两个文件搜 `smoke|e2e|typecheck` 零命中。也就是说:改坏内核、typecheck 变红、单测变红,**都不会有任何东西响**。`.github/` 里也没有 dependabot / CODEOWNERS / PR 模板。

### `packages/desktop` 的 10 个测试文件从不被任何命令跑

desktop 的 `package.json` 没有 `test` 脚本(只有 `smoke`/`e2e:*`),根 `test` 脚本逐包枚举时也跳过它。这 10 个里包含 `electron-builder.config.test.ts`、`mailbox-controller.test.ts`(守护状态机/退避)、`mailbox.test.ts`、`index.test.ts`(main 初始化编排)、`updater-*.test.ts` —— **全是 main 进程的核心逻辑,写了但从不执行**。

全仓 181 个测试文件的分布:app 77、coding-agent 27、agent 16、ai 15、bench 15、desktop 10、kernel 10、session-ui 10、ui 1、util 0。

### typecheck 只覆盖 7/10 个包

只有 `app`/`bench`/`desktop`/`kernel`/`session-ui`/`ui`/`util` 有 `typecheck` 脚本。`packages/agent` 与 `packages/coding-agent` 的 `package.json` **完全没有 `scripts` 字段**;`packages/ai` 有 test(vitest)但无 typecheck。内核代码只有被 kernel/bench 编译单元 import 到的部分被顺带检查 —— `core/examples/cli.ts` 是公认盲区,`docs/施工指南-例程库.md:212-214` 自己写了"改动后手动核"。

## 四、上下文预算:"RAG 会不会把 prompt 搞乱"

**方向对了一半,名字起错了。**

### 假问题:语义污染

系统提示词是**会话创建时快照一次**拼出来的(`session-manager.ts:505-510`),`datasheet`/`examples` 的返回值只作为 `toolResult` 消息进对话历史(`agent-loop.ts:728-739`),**永远碰不到系统提示词一个字节**,也没有任何把工具输出回灌进 prompt 的路径。这一层架构上就不可能发生。

### 真问题:体量 + 没有保底 + 压缩醒得太晚

**固定底噪**(实测,不是估算):

| 来源 | 字符数 |
|---|---|
| `buildSystemPrompt`(身份 + 原则 + 证据规则 + 安全 + 12 个工具的 snippet/guidelines) | 5,754 |
| 12 个工具的 description | 20,374 |
| 12 个工具的 JSON schema | 14,907 |
| 项目上下文文件(原文,**无任何截断**) | 本仓自己的 `CLAUDE.md` = 23,989 |

在本仓开一个会话、一个字还没说,固定开销已经约 **65,000 字符**(保守 25–30k token)。最大的单块是 `CLAUDE.md` 本身 —— `resources.ts` 里没有任何 `slice`/`truncate`/`maxBytes`,整份原文逐字拼进 `<project_instructions>`。

**三个完全没有上限的口子**:

| 口子 | 现状 | 证据 |
|---|---|---|
| `datasheet search` | `hits.slice(0,k)` **只夹条数**(topK ≤ 20),每条命中的 `h.text` 原样拼进结果 —— 长度**完全由服务器的 chunk 策略决定**,客户端一个字符都不截。"chunks are short (~512 tokens)" 只写在给模型看的描述里,代码零保证。服务器把 chunk 改成页级 → 本仓零改动零报错,一次调用从 ~46k 字符变 ~120k 字符 | `tools/datasheet.ts:340-346`、`:136-140`、`:236` |
| `examples search` | `limit` 只判 `Number.isFinite`,**不 clamp**。模型写 `limit: 99999` 就把整个语料索引渲染进上下文,百万字符级;`examples.ts` 全文没有一处截断 | `core/examples/search.ts:82`、`tools/examples.ts:198` |
| `view_figure` | `MAX_FIGURE_BYTES = 8 MiB` → base64 后 **11,184,811 字符**进一条消息;而压缩估算器把**任何**图片一律记成 4,800 字符 ≈ 1,200 token —— **防线和计价两边都看不见它** | `tools/datasheet.ts:230,456-469`、`compaction/compaction.ts:221` |

**对照组**:`log.ts` 是教科书级的 —— 四层截断(行数 clamp 1..500、单行 400 字符裁窗、单次节选硬顶 24,000 字符、超预算走"头 5 行 + TRIPWIRE 命中行 + 尾"骨架采样并显式报省略),而且全量永远落盘。同一个仓里,`log` 什么都做对了,`datasheet`/`examples` 什么都没做,`flash` 完全裸奔(probe-rs 的 stdout+stderr 原样返回),**中间没有任何全局闸门** —— `agent-loop` 拿到什么就原样塞进历史。

**最要命的是时序**:自动压缩挂在 `agent_end`(`session-manager.ts:617`),也就是整轮跑完之后;而 `agent-loop.ts:164-168` 的工具循环**没有步数上限**。

> **最危险的场景**:用户问一句跨外设的寄存器问题。模型照着自己的 promptGuidelines(`datasheet.ts:299` 明写"回答寄存器问题前必须先 search")对 TIM1/DMA/RCC/NVIC 各搜一遍、每次 topK=20、每次再 `read_section` 一次(≤40k 字符)—— **8 次调用就是 40 万字符 ≈ 100k token,全部压在同一轮里,压缩一次都不会触发,第 9 次请求直接撞窗口。**

所以准确的说法不是"prompt 被搞乱",是 **"一轮之内可以被一个不设防的工具打爆,而唯一的善后机制要等到那一轮结束才醒"**。

### 修法:约 50 行

## 五、最小评测:下一步该做的事

### 为什么是它

现在的困境不是"细节没做完",是**没有刻度** —— 没有用户告诉你做对没有,没有评测告诉你工具好用没有,没有闸门告诉你代码坏没坏。缺了刻度,任何"下一步"都只能靠感觉选,而事后无法判断哪个是对的。

一套最小评测同时解决四件事:

- "gdb 到底行不行" → 表格第一列
- "AI 完善会不可控" → 评测进 CI,改坏了当场就红
- "不知道是真有用还是自我意淫" → 10 个真实故障里过了几个,是一个不由主观决定的数
- "需要板子,开源门槛太高" → **QEMU case 能进 CI,意味着别人没有板子也能 clone 下来跑起来看到它工作**

而且**评测集的第一个 case,就是 demo 视频的第一个镜头**。

**(1) 判据层不用重新设计,原文还在 git 里。**

```
  cases/e-001.json          # spec
  fixtures/                 # 或指向外部固件仓的固定 ref
  verify/e-001.sh           # 退出码即答案
```

```jsonc
// cases/e-001.json
{
  "id": "e-001-badptr",
  "title": "精确 BusFault:定位越界写的那一行",
```

`verify/e-001.sh` 就是把 agent 的结论跟已知答案对一下(`CFSR=0x00008200`、`BFAR=0xf0000000`、源码行号),退出码 0 = 过。

### 第一次跑之前必须知道的坑

1. **`cost` 那一列可能静默是 0**。`projector.ts:394` 是 `cost: usage?.cost?.total ?? 0` —— 花费全来自 pi-ai 的定价表,provider 没有价目条目时不报错、直接 0。第一次跑完**必须人工核"钱 ≠ 0 且量级合理"**,否则表里第三个数是假的。token 数是可靠的。
2. **`model` 和 `thinking` 必须钉死在 case 里**。不钉,`pickAvailableModel`(`job.ts:152`)会挑"这台机器上第一个有凭据的",两个人跑出来的数不可比;`thinking` 不填会落到 `DEFAULT_THINKING_LEVEL = "max"`(`job.ts:136`),**三倍花费差,而且看不见**。
3. **provider 抽风不进 `stopReason`,只进 `TurnResult.errors`**(内核把 provider 失败当数据、自动重试 3 次;`turn.test.ts:141-154` 明确断言 stopReason 是 undefined 而 errors 里有 503)。只看 pass/fail 会把"网络抽风"记成"模型不行"。`errors.length` 必须进表。
4. **必须加一个 `maxRounds`**。现在整个 bench 没有任何轮数上限(`job.ts:8-10` 明写"没有轮数/token/墙钟上限",那是产品决定),评测必须有。另外 `turn.ts:262` 的 60 分钟硬超时要调小(`TurnOptions` 已经开了 `hardTimeoutMs` 这个口子)。
5. **"几轮"在这个仓里有三个意思**:mailbox 的一轮是跨机器往返;`turn.ts` 的一轮是一次 prompt→idle(里面可能几十次工具调用);评测想记的是第三个 —— "agent 试了几次才过判据",这个数只有自己的 `run-case` 循环知道。
6. **并行跑多个 case 必须各给各的 workspace**。`runTurnInChildProcess` 的输入/输出文件名是 `${job.id}-${prompt.length}`(`runner.ts:152`),同 id 同长度提示词会撞名 —— 单进程靠"先 rm 旧输出"兜住,并行会**静默错账**。
7. **QEMU 与真板的分数不能直接比,要分两张表**:QEMU 上观察点会永久挂死模拟器(代码已在 `SERVER_CAPS` 当场拒绝并有测试钉住)、不建模硬件断点预算(塞 512 个全 `^done`)、不能 reset。所以 agent 在 QEMU 上被推着用断点、在真板上会用观察点。
8. **QEMU 的两个收尾坑**:固件跑到 semihosting `SYS_EXIT` 会终止整个 qemu 进程,gdb 侧看到的是 `Remote communication error`(要停住必须 `break test_done`);`infloop` 场景永不退出,任何自动跑必须带超时,而且**绝对不要 `pkill -f qemu`**(那个模式会匹配到发起它的 shell 命令行本身)。
9. **`gdb start` 每次都会打一行 `image: UNVERIFIED`**(工作区没有 `.my-pi/flash-state.json` 时的默认分支)。这段文字进 agent 上下文、会影响它的措辞;QEMU case 里恒常出现,真板 case 里 `flash download` 之后变成 verified —— **判据里不要匹配到这句**。
10. **DWARF 里是构建机的绝对路径**,仓里的 `.elf` 是别人机器上编的。能工作全靠 `gdb.ts:1368-1403` 的 `fixSourcePaths` 按后缀反推 `set substitute-path`,**前提是 cwd 必须是放着 `main.c` 的那个目录**。case 换了 cwd,映射会失败,行号就不能当证据用了。
11. **`mailbox sim` 不是评测入口**。它起两个真子进程 + 两个克隆 + 一个裸仓,要求有项目检出和 mother/runner 分工,还有 60 分钟看门狗。拿它当跑批器会非常慢且难归因。
12. **信箱那条路上的"通过"是模型说的,不是判据说的**。`verdict.outcome` 是研发端 agent 的判断,不能直接当评测的 pass 列 —— 那正好是"没有刻度"的根源。评测的 pass 必须来自新写的 `verify.ts` 的退出码。
13. **faux 不能当评测夹具**。`packages/ai/src/providers/faux.ts:248` 把 cost 全部硬写成 0,token 是 `length/4` 估的;而且用 faux 评的是自己写的脚本不是 agent。它的正确用途是给评测框架**自己**写单测。
14. **纯 node 下等内核事件会把进程放空**。`turn.ts:228` 那个 keepalive interval 是承重的(内核事件批处理的定时器是 unref 的),别去掉,也别在自己的循环里制造同样的状态。
15. **要先拍板一件不是代码的事**:评测必须用真模型,意味着要挂 key、每次跑要花钱、结果不是位级可复现。建议把评测拆成单独的 nightly 或手动 job,用已经选好的 `deepseek-v4-flash`。

## 六、路线与开源时机

目标是 **B(真实产品)为主、C(开源作品集)兜底**。这给出一把筛选下一步的尺子:**这件事对 B 和 C 是不是都有价值?**

| 事情 | B | C |
|---|---|---|
| 一组能重跑的评测 + 三个数字 | ✅ 唯一能说服人的材料 | ✅ README 第一屏 |
| 补 CI / 闸门 | ✅ 两个人还能继续加东西 | ✅ 别人能跑起来 = 开源的真门槛 |
| 一个 90 秒 demo 视频 | ✅ | ✅ |
| 找 5 个真有板子的人来用 | ✅✅ | ➖ |
| 再加一个工具 / 再完善一个细节 | ❓(因为没刻度,说不清) | ❌ |

最后一行就是迷茫的根源:**现在能想到的"下一步",恰好是唯一一件对 B 和 C 都说不清价值的事。**

### 开源时机

**"仓库 public"是一个状态,"launch"才是一次性的事件 —— 两者无关。**

- 仓库 public 本身不产生任何流量,也不消耗任何机会。担心"用掉第一次机会"这个前提不成立。
- 真正只有一次的是 launch(一条视频、一篇帖子、一次转发),而它需要素材,跟仓库何时 public 无关。
- **产品需要板子**,这决定了开源获客的天花板:刷到的人里有 STM32 + ST-Link 在手边、并且此刻正在调 bug 的比例极低。真正需要的不是 500 个 star,是 **5 个手上真有板子的人** —— 这靠 launch 抽不到,得去嵌入式的地方一个个找。
- **憋大招的悖论**:需要用户告诉你什么叫"亮眼",才能憋出亮眼的大招。

**建议:现在就 public,但不 launch。** 不发帖、不投稿,README 老实写"早期、需要硬件、欢迎来聊"。好处是可以给人看了(找用户、请人牵线、给新人接手、放简历),零成本,且完全不消耗 launch 机会;副作用是好的 —— 它逼你们做本来就该做的事:**让别人能跑起来**。

launch 留到手里有三样:① 90 秒 demo 视频;② 一组评测数字;③ 一句话价值主张。其中 ① 和 ③ 都由 ② 派生。

### 对外沟通(请教时的提纲)

不要问"下一步做什么" —— 那必然得到"继续完善细节"。带一个**具体的、可被反驳的判断**去,收获高一个量级。

**开场不要讲功能列表,讲一个坑**。这两个例子能让人瞬间明白这个领域的难点是"证据链"而不是"代码生成":

1. **改了代码没烧录,然后 gdb 上去调**:行号、调用栈、变量值全都看着合理,模型会写出一份完全自洽但完全虚构的根因分析,而且**没有任何一条错误信息**。解法是 `flash download` 成功后落 elf 的 sha256,gdb 启动时回算校验,对不上就拒绝启动。
2. **中文 Windows 上子进程按 GBK 输出**:判据全过、退出码正常,证据却是 `xTickCount@0x200002a8: 24920 -> 25665 | ????????`。坏掉的恰恰是这套系统唯一的产品 —— 证据,而且一声不吭。

**然后问四个问题**:

1. **定性** —— 论文 / 产品 / 作品集,该往哪边走?(这个问题不定下来,后面全是空谈)
2. **验证** —— 我们最没底的是"看起来能用"和"真的有用"之间的距离。这类工具的评测怎么定?有没有可比的 baseline?
3. **场景** —— 能不能对接 1–2 个真实在做嵌入式的团队/实验室,哪怕只让他们用两周、骂我们一顿。**这是我们自己拿不到、而您能给的东西。**
4. **人** —— 两个人的工程量已经到顶。是招人、带新人接手,还是砍范围?

**开源那条不要说成"暂时不想开源"**(那是决定不是问题,放进去只会让人觉得在护着什么),改成"我们在想开源能换来什么、代价是什么",并且放在第 1 条之后问 —— 定性定了,答案自然出来。

## 附:一条贯穿全篇的规律

三节看似不相干的内容 —— `CLAUDE.md` 漂移、CI 空转、`datasheet` 没有输出上限 —— 是同一条规律的三个实例:

> **有闸门的地方,AI 写的代码没有失控;没有闸门的地方,谁写都会烂。**

`details-check.ts` / `mypi-alias.test.ts` / `thinking.test.ts` / `auth.test.ts` 覆盖的东西一律干净;`log.ts` 有输出预算所以十几处输出规规矩矩,`datasheet.ts` 没有所以一处也没有;CI 不跑测试所以 desktop 的 10 个测试文件写了从不执行。

**所以"AI 完善会不可控"的解法从来不是少用 AI,是先花 20 行装一道会响的闸门。** 装闸门比人工审查每一次改动便宜一万倍,而这个仓已经很擅长做这个 —— `details-check.ts` 里那段"为什么必须写成 `Expect<T extends true>` 而不是 `true as never`"的论证就是范本。

按这条规律排,下一步的优先级是:

1. **给 `packages/desktop` 加 `test` 脚本并接进根 `test`,把 `test + typecheck` 挂上 push 触发的 workflow**(躲不掉,而且最便宜)
2. **四个 smoke/e2e 的 Electron 路径改成三平台**(照抄 `mailbox-smoke.ts:40-48`)
3. **`wrapToolDefinition` 的全局输出闸门**(~20 行,所有 12 个工具立刻有底线)
4. **评测框架 + 3 个 QEMU case,拿到第一张 CSV**
5. 拿这份文档的结论回写一遍 `CLAUDE.md` 对账
