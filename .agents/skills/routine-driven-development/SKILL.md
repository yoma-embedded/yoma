# 例程驱动开发

**例程不是偷懒,是配置空间里一个已被验证的点。** 一句"UART 跑 DMA 115200"无法确定
时钟树、引脚复用、DMA 通道映射、中断优先级、链接脚本、编译宏 —— 一份能跑的官方例程,
就是这几百个耦合决策的压缩证明。从它出发做加法,失败模式是"我刚改了什么"(可回退);
从零生成,失败模式是"几百个猜测里错了哪个"(不可归因)。

总纲:**永远从一个已验证的绿点出发,每次只走一小步,每步都能被证伪,走不通就退回
上一个绿点。**

## 六个环节

1. **先锁死目标清单。** 芯片确切型号、SDK 与版本、工具链、构建系统、RTOS —— 全部
   固定下来再动手(toolchain 工具核对本机)。最常见的失败不是逻辑错,而是混用不同
   SDK 版本的 API:代码看着全对,就是编不过。
2. **把需求拆成能力单元,逐个检索。** "温湿度上报"拆成 Wi-Fi、MQTT、I2C、NVS —— 用
   examples 工具**分别查**,不要把整句需求一把梭。芯片是硬约束:结果里 targets 不含
   你芯片的,再像也不用。
3. **定底盘,其余当供体。** 底盘选把最多"环境"配好的例程(事件循环、网络栈、分区表)
   且必须可编(buildableOnly);供体只摘外设初始化和任务体,不摘它们的 main。
   环境比业务逻辑难移植得多。
4. **seed 之后先立绿点。** 一行业务代码都不写,把底盘例程原样构建、烧录、跑通
   (flash/log 工具拿运行时证据),提交并标记 green-0。这一步不绿绝不往下走 ——
   它证明工具链、分区、启动这整套环境是通的,之后任何失败都只可能来自你自己的改动。
   第一步改动几乎总是引脚重映射:你的板不是官方板。
5. **一次只加一个能力,每步选最便宜的验证层。** 编译过 → 烧录成功 → 运行时证据
   (日志/gdb),过了就提交成新绿点。例程自带的验收素材(esp-idf 的 pytest、
   Zephyr 的 harness regex)是现成的判据参考。
6. **失败回滚,不在废墟上修。** 某步挂了,回到上一个绿点提交,把失败日志当新证据
   重新规划 —— 一路往下修补丁只会越修越乱。这是例程驱动与"普通改到能跑"的根本区别。

## 落到工具

- `examples search`:硬过滤检索(芯片/生态排除式,外设至少命中,小种子优先)。
- `examples info`:整卡(依赖、Kconfig、验收素材、本机语料根)。
- `examples seed`:拷进工作区 + `.yoma-seed.json` 出处(随工程提交)。
- 没有索引时,工具会打印 CLI 索引命令 —— 转告用户在放语料的机器上跑。
